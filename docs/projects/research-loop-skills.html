wrencanfly/research-loop-skills

一句话定位

一组七支零依赖的 Markdown 技能（外加一个 11 KB 的 Python 校验器），用来给 agent 装上一条纪律：把研究问题变成可追溯的主张、可复现的检查，和一个有用的下一步决定 —— 并且知道什么时候停。

它解决的问题

⭐⭐⭐⭐⭐ 它的问题陈述写得比多数项目都准，这是本档案把它排在 35⭐ 的原因：

Agents are good at producing confident research prose. They are less reliable at showing which source supports which claim, what test could have proven them wrong, and when to stop.

⭐⭐⭐⭐⭐ 三个失效模式：主张没有出处、没被证伪过、以及不知道何时停。 ⭐⭐⭐⭐⭐ 而第三个 —— 「什么时候停」—— 是绝大多数 agent 工作流规范完全不提的那个。

⭐⭐⭐⭐ 第二个被解决的问题是「每个宿主一套流程」。 ⭐⭐⭐⭐⭐ 它的做法是：技能是纯 Markdown，遵循 Agent Skills 格式，因此可以 cp -R skills/* ~/.claude/skills/，也可以直接让任何有工作区访问权的 agent 读 skills/research-loop/SKILL.md。⭐⭐⭐⭐ 「与框架无关、与模型无关、与宿主无关」是本日报在 solo-to-team-skills（11-08 建档）里已经记过一次的原则，这里它被推到了更彻底的形式 —— 连依赖都没有。

⭐⭐⭐⭐⭐ 第三个是「纪律要有可执行形态」。 ⭐⭐⭐⭐⭐ 它不只给一套流程，还给一个校验器（scripts/research_run.py 11,056 B + tests/test_research_run.py 7,883 B）—— ⭐⭐⭐⭐ 「让 agent 留痕」这件事如果只靠 prompt，最终一定会退化；而把留痕的格式做成机器可检查的，就多了一道闸。

为什么值得关注（2026-11-09）

⭐⭐⭐⭐⭐ 本日它是「35⭐ 与 400⭐」这个反差里最值得单独拿出来的那一个 —— 因为它同时打败了两种噪声。

第一种噪声是本日 141 个 400⭐ 的投递仓库：⭐⭐⭐⭐⭐ 那些仓库的 README 里写着「请关闭杀毒软件的实时保护」然后跑一个混淆的 PowerShell。⭐⭐⭐⭐ 而 research-loop-skills 的 README 里写着「你的 agent 带来推理、检索和工具，本仓库带来研究方法」 —— ⭐⭐⭐⭐⭐ 同样是「一个仓库 + 一段话 + 一个安装指令」的形态，一个是要你关掉防护，一个是给你一套纪律。

第二种噪声是本日 141 个真实项目的 star 数字：⭐⭐⭐⭐⭐ 35⭐ 在今天的榜单上几乎看不见 —— 排不进前 100。⭐⭐⭐⭐⭐ 但本日报连续六天记录的核心命题就是「热度不等于价值」，而今天这个项目把这条命题从「方法论」变成了「可操作的筛选动作」：⭐⭐⭐⭐⭐ 在你决定收录哪个仓库之前，⭐⭐⭐⭐⭐ 先看它有没有「不可执行的自我描述」—— research-loop-skills 的 README 通篇没有一句索取 star 的话，⭐⭐⭐⭐⭐ 它的 35⭐ 与它 40 个文件、7 支技能、1 个带测试的校验器的比例，反而比很多 400⭐ 的仓库更接近「一个真实项目该有的样子」。

⭐⭐⭐⭐⭐ 而它最值得抄的一处，是它把「不该由我来做」显式写出来。

Inspired by Anthropic's study How researchers use Claude. The workflow is our own design proposal: it was not validated by that study and is not affiliated with Anthropic.

⭐⭐⭐⭐⭐ 并且它给了这个来源一个单独文件（docs/source-notes.md）。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 这一条在本日报本日记录的语境里格外重要：141 个投递仓库的整个策略就是「伪造权威来源」（SEO 关键词、假下载页、假徽章）；⭐⭐⭐⭐⭐ 而这个 35⭐ 的项目做的是相反的事 —— ⭐⭐⭐⭐⭐ 明写「我借鉴了这份研究，但这个流程是我们自己的设计提议，没有被那份研究验证过，也不代表 Anthropic」。 ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 「区分借鉴与原创」正是 11-08 的 solo-to-team-skills 记下的一条启发（「借鉴的是方法思路；交付的是改写后的中文协作包，外加两支原创技能」），⭐⭐⭐⭐⭐ 今天有两个互不相识的项目各自独立地做了同一件事 —— ⭐⭐⭐⭐⭐ 这说明「来源声明」正在成为 agent 生态的一种普遍实践。

⭐⭐⭐⭐⭐ 还有一处结构上的巧妙：它的 README 自己带了一张 Mermaid 图，⭐⭐⭐⭐⭐ 而且图里那个 {{Verify the claims}} 节点用虚线边框画出来，并明确画出两条回边（evidence changes the question → 回到 Frame；another check is worthwhile → 回到 Test）。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 「可回退的流程图」本身就是一个设计声明：研究不是直线，而是带回边的循环。

关键技术亮点

  1. 七支纯 Markdown 技能 + 一个零依赖校验器 skills/research-loop/SKILL.md（5,418 B，编排者）、research-evidence（3,507 B）、research-frame（3,454 B）、research-verify（3,420 B）、research-hypothesize（3,274 B）、research-synthesize（3,201 B）、research-execute（3,636 B）+ scripts/research_run.py（11,056 B）+ tests/test_research_run.py（7,883 B）。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 「编排者 + 六个阶段」的分工意味着每一步可以单独被调用 —— README 明写「Each stage skill also works on its own. To audit an existing analysis, for example, point the agent at research-verify directly.」⭐⭐⭐⭐⭐ 这是一个「可组合的检查点集合」而非一条不可分割的流水线，而它直接对应「从任何已有分析开始」这个真实需求。**

  2. 把「停止条件」写进流程，而不是留给模型 README 的入门提示词里直接给了预算与停止规则：「Spend at most 3 research iterations; stop earlier if another step is unlikely to change the answer.」⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 两条停止规则（迭代上限 + 「下一步不可能改变答案就停」）并行，且后者是判断性的 —— ⭐⭐⭐⭐⭐ 这比单纯的「最多做 N 步」高一个层次，因为它规定了「不值得做」而不是「做太多」。**

  3. 「负面或不确定的结果是合法的结束方式」被明写

    A negative or inconclusive result is a legitimate way to finish.

⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 这一句直接针对 agent 最顽固的失败模式：为了「交付一个结论」而制造一个结论。 ⭐⭐⭐⭐ 本日报记录的 poki「In one landscape game, taps on button coordinates had no effect… The cause is unknown.」是同一原则在工具层面的表达（把「不知道」设计成一个合法输出）；⭐⭐⭐⭐⭐ 而这里是在方法论层面表达。

  1. 零依赖 + 有测试 pip 层面零第三方依赖（README 徽章写 dependencies-none），⭐⭐⭐⭐⭐ 而一个 11 KB 的脚本居然配了 7,883 B 的测试文件 —— ⭐⭐⭐⭐⭐ 对比本日 141 个 400⭐ 仓库（有测试：0 个）。

  2. 可复现的示例与「缺证据」样例 examples/retrieval-demo/run.json（5,128 B）、examples/evidence-demo/evidence-map.md（3,071 B）、examples/evidence-demo/decision-brief.md（2,946 B）、以及 examples/walkthrough-meeting-notes/ 下的 input.md / output-ok.md / output-missing.md / register-lines.md。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 「有一个『缺证据』的样例与『通过』的样例并排」是本日报在本仓库里反复见到的正确做法（对照 KohakUnlock 的结果表明确写出「没赢的地方」、solo-to-team 的「不够的」那一栏）。**

架构启发

⭐⭐⭐⭐⭐ 启发一：「停止规则」应当与「执行预算」并列成为流程的一部分。

本日报收录过的绝大多数 agent 规范、skill、框架，都只规定了「做什么」和「做几步」。⭐⭐⭐⭐⭐ research-loop 同时给了「最多 3 轮」与「如果下一步不太可能改变答案就提前停」。 ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 后者是判断性的而非计数性的 —— 它把停止从「用完了额度」提升到「不值得继续」，⭐⭐⭐⭐⭐ 而这正是 agent 任务里最常见的浪费来源（继续做一堆不会改变结论的检索）。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 而「负面或不确定的结果是合法的结束方式」这一句，与这条停止规则构成一组： 它们一起把「完成」重新定义成「问题已被回答」，而不是「我交出了一个看起来完整的报告」。

⭐⭐⭐⭐⭐ 启发二：可组合的检查点集合，比不可分割的流水线更实用。

七支技能里有一支是编排者、其余六支是阶段，而每支都能被单独调用（README 明写「Each stage skill also works on its own」）。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 这意味着「审计一段已有的分析」不需要先跑完整流程 —— 你直接把 agent 指向 research-verify。 ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 这是一条通用的架构启发：⭐⭐⭐⭐⭐ 当一个方法被编码成技能/模块时，⭐⭐⭐⭐⭐ 「能不能单独调用其中一段」决定了它是工具还是流程图。 ⭐⭐⭐⭐⭐ 流程图让人从第一步开始，工具允许从中间进入。⭐⭐⭐⭐⭐ 真实工作的起点往往在中间。

⭐⭐⭐⭐⭐ 启发三：「来源声明」是 agent 生态的基础设施，而不是礼仪。

它把 Anthropic 的研究作为 inspiration，同时明写「it was not validated by that study and is not affiliated with Anthropic」，并给出单独的 docs/source-notes.md。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 在本日的语境里这件事的分量变了：⭐⭐⭐⭐⭐ 141 个 400⭐ 的仓库在用伪造的权威与假徽章换关注，⭐⭐⭐⭐⭐ 而这个 35⭐ 的仓库在用一句明确的免责把「我借鉴了什么」和「我证明了什么」分开。 ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 因此「显式声明来源与边界」不只是诚实 —— 它在一个伪造普遍的环境里，是少数还能被机器检查的信号之一。

⭐⭐⭐⭐⭐ 启发四：本日报连续六天的命题今天拿到了它的最强版本 —— 「35⭐ vs 400⭐」和「130⭐ vs 35⭐」同时成立。

⭐⭐⭐⭐⭐ 同日之内：141 个 400⭐ 的仓库是投递广告，而一个 35⭐ 的仓库有 7 支技能、1 个带测试的校验器、1 份中文文档和一份来源声明。 ⭐⭐⭐⭐ 跨日之内：同一品类（agent 技能包）在 11-08 拿到 130⭐、在 11-09 拿到 35⭐。 ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 这两条合起来说明：⭐⭐⭐⭐⭐ 绝对星数与品类热度都是环境函数，而「仓库里有什么」才是稳定量。 ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 对一个每日趋势研究仓库来说，这条原则的含义是直接的：⭐⭐⭐⭐⭐ 收录的价值不来自「当天排第几」，而来自「把这一天的环境记录清楚，供以后比较」。**

定位判断

工具型项目（agent 方法论层的一个认真样本，但市场容量有限）。

⭐⭐⭐⭐ 它在生态里的位置：「给 agent 装一条研究纪律」这件事的独立实现，⭐⭐⭐⭐⭐ 与 solo-to-team-skills（11-08 建档）、wshobson/agents（本仓库 7-21 建档）、research-execute 类 skill 家族同属一个正在成形的品类。⭐⭐⭐⭐⭐ 而它的差异化在两点：(a) 零依赖纯 Markdown（比带运行时依赖的方案更可移植）；(b) 带一个机器可查的校验器与测试（比纯 prompt 的方案更可验证）。⭐⭐⭐⭐⭐ 这两点恰好是本日报 11-08 记录的 solo-to-team-skills 没有的（它没有校验器，只有规则文本）—— ⭐⭐⭐⭐⭐ 因此这两个项目构成了同一品类的两种取舍：一个靠规则文本的清晰，一个靠机器校验的强制。

⭐⭐⭐⭐⭐ 在 2026 年的语境里，它的位置是「Agent Skills 格式的一个参考实现」 —— ⭐⭐⭐⭐⭐ 它不实现任何宿主，只提供内容；而这恰恰是它最有价值的形态：⭐⭐⭐⭐⭐ 当一个生态还在争「技能该写成什么格式」的时候，一个把自己完全押注在一个开放规范（agentskills.io/specification）、同时明写「我这样做的加载行为没有在所有客户端和模型上充分测试」的实现，本身就是对这个规范的推动。

⭐⭐⭐⭐⭐ 它同时是本日「低星高质」这条线的最强样本 —— 而本日报必须诚实地指出：⭐⭐⭐⭐⭐ 35⭐ 意味着这个项目在 GitHub 的注意力竞争中处于劣势。 ⭐⭐⭐⭐ 它的价值不在于它火，而在于它是本日唯一一个可以被逐条核验为「真」的、且与 141 个投递仓库形成直接对照的 agent 类项目。

风险 / 局限 / 泡沫点

  • ⚠️⚠️⚠️ 纯 Markdown = 无强制力：⭐⭐⭐⭐⭐ 这是它最大的结构性弱点，也是它最大的优点 —— 但缺点是真的。 ⭐⭐⭐⭐⭐ 技能本质是提示词：模型可以遵守，也可以不遵守；⭐⭐⭐⭐⭐ 而 research_run.py 只校验「记录写没写对」，不校验「研究做得对不对」。 ⭐⭐⭐⭐ 一个 agent 完全可以写出格式完美、来源齐全、而实质错误的报告。 ⭐⭐⭐⭐⭐ 所以这套东西的真实效果取决于宿主是否把技能当回事 —— 而这一点 README 自己都承认（「Loading behavior across clients and models has not been exhaustively tested」）。
  • ⚠️⚠️⚠️ 市场容量小且已被验证：⭐⭐⭐⭐⭐ 同类项目在 11-08 拿到 130⭐（solo-to-team-skills）、本日拿到 35⭐。 ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 这意味着「agent 方法论仓库」是一个注意力极不稳定的品类 —— ⭐⭐⭐⭐⭐ 而对任何想在 agent 生态里做事的团队来说，这条判断比「哪个项目更好」更重要：做这类东西，不要指望 star。**
  • ⚠️⚠️ 无人使用的证据为零：releases 0、contributors 1 人、oi 0、⭐⭐⭐⭐ subs 1。⭐⭐⭐⭐ 也就是说：除了作者自己，没有人在 GitHub 上对它说过一句话。 ⭐⭐⭐⭐⭐ 本日报不主张它无效，但必须明确：⭐⭐⭐⭐⭐ 「35⭐ 的仓库」与「35⭐ 且零第三方信号」是两种完全不同的状态，后者意味着它的效果完全未被外部验证。
  • ⚠️⚠️ 与 Anthropic 研究的边界未核验：⭐⭐⭐⭐ docs/source-notes.md 的正文本窗口未取回；⭐⭐⭐⭐ README 的免责声明（「未被该研究验证」「不代表 Anthropic」）是自述，不能替代对来源的实际核对。 ⭐⭐⭐ 一个专门讲「可追溯」的项目，其自身的来源链条应当被同等对待地核验。
  • ⚠️⚠️ 七支技能的一致性无自动校验：⭐⭐⭐⭐ 编排者 research-loop 链接到六个兄弟技能（README 明写「Keep all seven folders together, because the orchestrator links to its siblings」），⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 而这意味着安装方式（cp -R skills/*）本身就可能装坏 —— ⭐⭐⭐⭐⭐ 只复制 research-loop/ 会得到一个断链的编排者，而 README 只在安装步骤里用一句话提了这个约束。
  • ⚠️ topics 空数组、订阅数 1：⭐⭐⭐ 在 GitHub 的发现机制里几乎不可见 —— ⭐⭐⭐ 这与它 35⭐ 的 star 是同一个问题的两面：对「需要一个研究纪律的 agent 团队」这个极窄的人群，它的分发渠道接近于零。
  • ⚠️ 中文 docs/principles.md 与英文 README 的内容关系未核验：⭐⭐⭐ 两者是否等价、是否同步维护，未核验。

与同类项目的关系

  • vs dabingfy-dot/solo-to-team-skills（11-08 建档）：⭐⭐⭐⭐⭐ 本日最值得摆在一起的一对 —— 同一品类、零相互关系、两种取舍。 solo-to-team 把纪律写成规则文本 + 反例清单 + 「该停一下的信号」（靠人的阅读与模型的遵守）；research-loop 把纪律写成七支可组合技能 + 一个机器可查的校验器（靠工具的检查）。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 两者的 star 分别是 130（11-08）与 35（11-09）—— ⭐⭐⭐⭐⭐ 而本日报的判断是：这个落差主要反映投放环境而非质量（11-08 那天的 162 个候选里有 85 个是空壳，而本日 171 个里有 141 个是投递仓库，但 11-08 的「真项目」只有 4 个而本日有 30 个）。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 换言之：solo-to-team 的 130⭐ 是在一个「几乎全是噪声」的榜单上拿到的相对优势，而 research-loop 的 35⭐ 是在一个「噪声更多、真项目也更多」的榜单上拿到的。 ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 这是一条本日报此前没有明确写出、今天由这两个数字共同给出的结论：⭐⭐⭐⭐⭐ 绝对星数受环境影响很大，而同一品类在不同日期的星数差值，几乎无法用来比较项目质量。
  • vs 本仓库 7-21 建档的 wshobson/agents（38,581⭐）：⭐⭐⭐⭐⭐ 一个数量级的对照，且它把本档案的判断彻底钉死：wshobson/agents 是 38,581⭐ 的插件市场（聚合数百个技能，覆盖六大 Agent 平台）；research-loop-skills 是 35⭐ 的七支技能。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 「分发枢纽」的价值远大于「单份方法」—— ⭐⭐⭐⭐⭐ 这不是质量判断，而是形态判断：一个市场可以靠网络效应自我放大，一份方法不能。 ⭐⭐⭐⭐⭐ 因此本日报的结论不是「research-loop 不值得做」，而是「⭐⭐⭐⭐⭐ 做方法的人需要一个分发渠道，否则方法再好也只值 35⭐」。**
  • vs 本日的 141 个投递仓库：⭐⭐⭐⭐⭐ 同日、同为「一个仓库 + 一段话 + 一个安装指令」的形态，⭐⭐⭐⭐⭐ 一个的安装指令是「请关闭杀毒软件实时保护后运行此脚本」，另一个是「把 skills/ 复制到你的 skills 目录」。 ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 形态相同、内容相反 —— ⭐⭐⭐⭐⭐ 这说明「仓库的表面形态」同样不携带任何关于意图的信息，⭐⭐⭐⭐⭐ 而判据必须落在文件内容、账号元数据、时间分布这些更深的层面上。
  • vs 本仓库记录的 poki（11-07 建档）：⭐⭐⭐⭐ 方法论层面的同构：poki 的 docs/verification.md 把「触摸写进去了」与「设备确认了」分成两件事，并逐条记录「没赢的地方」（「The cause is unknown.」）；⭐⭐⭐⭐⭐ research-loop 的「negative or inconclusive result is a legitimate way to finish」是同一个原则在流程层的表达。 ⭐⭐⭐⭐ 两者的共同结构是：把「不知道」设计成一个合法的输出，而不是一个需要被掩盖的失败。**

是否值得持续跟踪

值得跟踪，但跟踪的重点应当是「这类项目的分发」而不是「这个项目本身」。 ⭐⭐⭐⭐

⭐⭐⭐⭐⭐ 最值得抄的三件事：(a) 把「停止条件」与「迭代预算」并列写进流程（且停止条件是判断性的）；(b) 把流程拆成可单独调用的检查点（编排者 + 阶段）；(c) 明写「我的流程是自己的设计提议，未被引用的研究验证」。

⭐⭐⭐⭐ 作为参考实现，它的形态是对的：零依赖、可移植、有测试、有双语、有来源声明。⭐⭐⭐⭐ 但 35⭐ 与零第三方信号意味着它目前没有任何外部验证 —— ⭐⭐⭐⭐ 如果一个团队要用这类东西，本日报的建议是：⭐⭐⭐⭐⭐ 直接读它的七支 Markdown（那部分内容本身是自足的），⭐⭐⭐⭐⭐ 不要指望它的 35⭐ 或它的校验器替你做任何事。

⭐⭐⭐⭐ 跟踪它应该盯的是：(a) 该品类的星数是否继续剧烈波动（35 vs 130 的落差需要更多数据点才能判断是环境效应还是质量效应）；(b) research_run.py 校验器的规则是否公开得足够清楚（校验器本身若不可审计，则它的价值会大打折扣）；(c) 是否出现第三方在 issue 里报告实际使用效果（这是从「作者自述」走向「外部验证」的唯一路径）。

后续观察点

  1. ⭐⭐⭐⭐⭐ scripts/research_run.py 的实际校验规则：⭐⭐⭐⭐ 它检查哪些字段、什么算不合格、失败时是否阻断。⭐⭐⭐⭐ ⭐⭐⭐⭐ 一个 11 KB 的零依赖脚本配 7,883 B 测试，说明它是被认真写过的；⭐⭐⭐⭐ 但「被认真写过」与「检查了真正重要的东西」是两回事，本日报未逐行核验。

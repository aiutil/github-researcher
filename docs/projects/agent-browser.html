vercel-labs/agent-browser

一句话定位

一个 Rust 写的浏览器自动化 CLI，把网页压缩成带 ref 的紧凑文本快照，让 agent 用「snapshot → 对 ref 动作 → 再 snapshot」三步循环驱动浏览器 —— 它是本数据集里 issue 密度最高、也最能说明「agent 需要什么形状的浏览器接口」的项目。

它解决的问题

⭐⭐⭐⭐⭐ agent 驱动浏览器的核心矛盾是：网页是人类视觉设计的（导航、卡片、按钮），而 agent 需要的是稳定、可寻址、可验证的结构。

⭐⭐⭐⭐⭐ 传统做法是把整页 HTML 或 accessibility tree 塞给模型 —— ⭐⭐⭐⭐⭐ 代价是上下文爆炸，而且元素引用不稳定。

⭐⭐⭐⭐⭐ 本项目的解法（实测 README 原文）：

agent-browser is a native Rust CLI that gives an AI agent a browser it can drive one command at a time. snapshot returns the page as compact text with a ref such as @e1 for each element. The agent acts on a ref, reads the page again to check the result, and repeats. The browser stays open between commands, so each step is one short shell call.

⭐⭐⭐⭐⭐ ⭐⭐⭐ 三个设计要点：① snapshot 是紧凑文本而不是完整 DOM；② 每个元素有稳定 ref（@e1）；③ 浏览器在命令之间保持打开，因此每一步都是一次短的 shell 调用。

关键技术亮点

  1. ⭐⭐⭐⭐⭐ 紧凑文本快照 + 稳定 ref ⭐⭐⭐⭐⭐ snapshot -i 返回带 @e1 式 ref 的紧凑文本，⭐⭐⭐⭐⭐ ⭐⭐⭐ 这同时解决了上下文预算与元素寻址两个问题 —— ⭐⭐⭐⭐⭐ 注意它选的是「可寻址的紧凑表示」而不是「完整的 accessibility tree」。

  2. ⭐⭐⭐⭐⭐ 浏览器跨命令保持打开 ⭐⭐⭐⭐⭐ 「The browser stays open between commands, so each step is one short shell call」⭐⭐⭐⭐⭐ ⭐⭐⭐ 这让整个交互变成一串短 shell 调用，⭐⭐⭐⭐⭐ 而不是每次都重开浏览器 —— 对延迟与状态保持都是关键。

  3. ⭐⭐⭐⭐⭐ 分层 doctor 子系统（8 模块，含自动修复 fix.rs） ⭐⭐⭐⭐⭐ 覆盖 chrome · config · daemon · environment · ffmpeg · launch。⭐⭐⭐⭐⭐ ⭐⭐⭐ 带 fix.rs 意味着它不只是报告问题，还能修 —— ⭐⭐⭐⭐⭐ 这在「agent 面对一个装坏了的环境」时价值极大。

  4. ⭐⭐⭐⭐⭐ WebMCP 支持 ⭐⭐⭐⭐⭐ 实测 commit fix(webmcp): accept invoke params after the tool name (#2591) ⭐⭐⭐⭐⭐ + skill-data/webmcp-gen/SKILL.md（⭐⭐⭐⭐⭐ 生成 WebMCP 定义的技能）⭐⭐⭐⭐⭐ —— ⭐⭐⭐⭐⭐ 即它把「让 agent 通过 MCP 调用浏览器」做成了一等能力。

  5. ⭐⭐⭐⭐⭐ 协议定义作为数据文件随仓库分发 ⭐⭐⭐⭐⭐ cli/cdp-protocol/browser_protocol.json + js_protocol.json ⭐⭐⭐⭐⭐ —— ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这让 CDP 协议的变化可以通过更新数据文件而非改代码来处理，⭐⭐⭐⭐⭐ 也让协议本身可被审阅。

  6. ⭐⭐⭐⭐⭐ browser_security.rs 与 ca_bundle.rs 独立成文件 ⭐⭐⭐⭐⭐ 一个要下载并驱动真实浏览器的工具，⭐⭐⭐⭐⭐ ⭐⭐⭐ 把安全与证书链单独成模块，说明「被 agent 驱动」这件事的信任边界被显式考虑过。

  7. ⭐⭐⭐⭐⭐ skill-data/ 把开发知识也封装成 Skill ⭐⭐⭐⭐⭐ 10 个目录覆盖 core / agentcore / derive-client / dogfood / electron / slack / vercel / vercel-sandbox / webmcp-gen / modern-web-guidance。⭐⭐⭐⭐⭐ ⭐⭐⭐ 即「如何开发这个项目」本身是可被其他 agent 消费的 Skill。

架构启发

⭐⭐⭐⭐⭐ 启发一：⭐⭐⭐⭐⭐ 「紧凑文本 + 稳定 ref」是 agent 接口设计的一个可复用范式。 ⭐⭐⭐⭐⭐ 与 ffmpeg-skill 的「默认 12 个工具 / 全量 42 个」是同一条思路的两个层面：⭐⭐⭐⭐⭐ 前者压缩「看什么」，后者压缩「调什么」。⭐⭐⭐⭐⭐ 两者都指向同一件事：⭐⭐⭐⭐⭐ agent 的上下文预算是首要设计约束，而不是事后优化项。**

⭐⭐⭐⭐⭐ 启发二：⭐⭐⭐⭐⭐ doctor 应该带自动修复，而不只是报告。 ⭐⭐⭐⭐⭐ 实测 cli/src/doctor/fix.rs 的存在 ⭐⭐⭐⭐⭐ —— ⭐⭐⭐⭐⭐ 对 agent 而言，「环境坏了」是高频事件，⭐⭐⭐⭐⭐ 而一个只会报告的 doctor 要求 agent 自己想办法修，⭐⭐⭐⭐⭐ 一个能修的 doctor 直接把故障消掉。⭐⭐⭐⭐⭐ 本日记录的 last30days-skill 的 doctor 还会误报，⭐⭐⭐⭐⭐ 说明「doctor 要会自测」本身也是一项工程要求。**

⭐⭐⭐⭐⭐ 启发三：⭐⭐⭐⭐⭐ 协议定义应当作为数据文件随产物分发。 ⭐⭐⭐⭐⭐ cli/cdp-protocol/*.json ⭐⭐⭐⭐⭐ —— ⭐⭐⭐⭐⭐ 好处有二：协议变化不需要改代码；协议本身可被审阅与 diff。⭐⭐⭐⭐⭐ 本数据集记录的 docs/contract.md（ffmpeg-skill）、_system/schemas/*.schema.json（boring-marketing-skills）都是同一模式的不同形态。

⭐⭐⭐⭐⭐ 启发四：⭐⭐⭐⭐⭐ 「把开发本项目的知识也做成 Skill」是一种自举式的知识封装。 ⭐⭐⭐⭐⭐ skill-data/ 下 10 个目录 ⭐⭐⭐⭐⭐ —— ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 好处是：新贡献者（不论是人还是 agent）都能用同一套知识上手；⭐⭐⭐⭐⭐ 坏处是这些知识会随代码演进而腐化，⭐⭐⭐⭐⭐ 因此需要一个「知识是否仍然有效」的检查机制 —— ⭐⭐⭐⭐⭐ 本项目有 dogfood 技能，但是否有针对 skill-data 的时效性检查，未核验。**

定位判断

生产可用 —— 在「agent 驱动浏览器」这个具体位置上，它几乎没有竞品。

⭐⭐⭐⭐⭐ 51,996⭐ / 3,628 forks / 114 subs / 100+ release / 5 位真实贡献者 / Rust 实现 / Apache-2.0 ⭐⭐⭐⭐⭐ ⭐⭐⭐ 这些指标说明它已经是一个被依赖的基础设施，而不是实验品。

⭐⭐⭐⭐ ⭐⭐⭐ 但要给它一个准确的定位，需要区分两件事：⭐⭐⭐⭐⭐ 它卖的不是「浏览器自动化」，而是「给 agent 的浏览器接口形状」 ⭐⭐⭐⭐⭐ —— 「紧凑快照 + 稳定 ref + 常驻进程 + 一条短命令一步」这套约定，⭐⭐⭐⭐⭐ 实际上定义了 agent 该如何与网页交互。⭐⭐⭐⭐⭐ 这个约定的扩散速度，比代码本身更有长期影响。

风险/局限/泡沫点

  1. ⭐⭐⭐⭐⭐ ⭐⭐⭐ 589 个 open issue 相对 3,628 forks 是偏高的：⭐⭐⭐⭐⭐ ⭐⭐⭐ 这更可能是「被广泛集成 + 大量边缘场景」的结果，⭐⭐⭐⭐⭐ 但也意味着维护压力与响应延迟 —— ⭐⭐⭐⭐⭐ 未核验 issue 的平均响应时间与关闭率。
  2. ⭐⭐⭐⭐⭐ ⭐⭐⭐ 依赖浏览器二进制：需运行时下载 Chrome for Testing，⭐⭐⭐⭐⭐ ⭐⭐⭐ 在受限网络/容器环境下会失败；⭐⭐⭐⭐⭐ doctor 正是为此存在，但它是否覆盖所有场景未核验。

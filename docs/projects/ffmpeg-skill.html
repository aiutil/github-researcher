kajisho5/ffmpeg-skill

一句话定位

一个把 42 个 FFmpeg 工具封装成 Agent Skill 的项目 —— 它最值得研究的不是功能，而是它证明了「100 个 release」既可以是假的（11-16 的 steam-library-bridge），也可以是真的，而区别只在于「tag → commit → 代码 diff」这条链是否闭合。

它解决的问题

视频编辑的门槛不在 FFmpeg 本身，而在于参数组合的组合爆炸：裁剪、拼接、去静音、等比缩放、字幕与卡拉 OK、叠加与动效、HDR→SDR 与 LUT、音频清理与动态、同步与漂移校正、多机位、响度标准化、交付检查、整片渲染工程、批量文件夹 —— ⭐⭐⭐⭐⭐ 每一条都对应一组互相影响的 FFmpeg 参数组合。

⭐⭐⭐⭐⭐ 而 coding agent 面对 FFmpeg 的真实问题是：它知道命令语法，但不知道「哪些参数不能一起用」「什么样的输出其实是对的」。 ⭐⭐⭐⭐⭐ 本项目给出的答案是一个固定工作流（probe → 尽可能无损地编辑 → check → verify） ⭐⭐⭐⭐⭐ 加上 42 个封装好的工具，⭐⭐⭐⭐⭐ 加上 一份机器可读的契约。

⭐⭐⭐⭐⭐ ⭐⭐⭐ 它还解决了一个更隐蔽的问题：agent 的上下文预算。 42 个工具全部塞进 tools/list 会挤占客户端上下文，⭐⭐⭐⭐⭐ 而本项目的解法是「默认只暴露 12 个核心工具」—— 详见「关键技术亮点」第 4 条。

为什么值得关注（2026-11-17）

⭐⭐⭐⭐⭐ 因为 11-16 日报刚刚用 atlas7283/steam-library-bridge 证伪了「release 多 = 有发布历史」这条判据；本日这个项目从反面给出了同一条判据的正面样本，并让判据本身变得可执行。

关键技术亮点

  1. ⭐⭐⭐⭐⭐ 「默认 12 / 全量 42」的分层工具暴露（最值得抄的一条） 实测 README 原文：

    Every tool is also callable as an MCP tool (tools/list advertises a core 12 by default to keep client context small, with FFMPEG_SKILL_MCP_FULL=1 listing all 42; every tool is reachable by name through tools/call either way)

⭐⭐⭐⭐⭐ ⭐⭐⭐ 这把「工具太多会撑爆客户端上下文」从抱怨变成了可配置的契约：默认给 12 个，其余按环境变量开启，但每个工具按名都可达。

  1. ⭐⭐⭐⭐⭐ SKILL.md 的两层结构 实测 README 原文：SKILL.md is two-tier (1.11.0): the file the agent loads every session keeps the workflow, the … ⭐⭐⭐⭐⭐ 即「每次会话都加载的那份」与「按需查阅的那份」被显式分离 —— 这是上下文预算在 prompt 层面的对应做法。

  2. ⭐⭐⭐⭐⭐ 机器可读的契约文件 docs/contract.md 在每次 release 中被同步更新（+2/-2），⭐⭐⭐⭐⭐ 意味着工具契约本身是被版本化管理的对象，而不是文档里的自然语言描述。

  3. ⭐⭐⭐⭐⭐ 固定工作流而非工具列表 probe → edit losslessly where possible → check → verify，⭐⭐⭐⭐⭐ workflow 与工具集是两层：工具负责「怎么做」，workflow 负责「按什么顺序做、什么时候停」。

  4. ⭐⭐⭐⭐⭐ 诚实的评测记录 evals/results/iteration-22.json 等文件记录每次评测，⭐⭐⭐⭐⭐ 且 README 里那张表把没测出来的也写上（「Three refused honestly rather than fabricate a number」）—— ⭐⭐⭐⭐⭐ 即「agent 诚实地拒绝编造」被当作正面结果记录。

  5. ⭐⭐⭐⭐⭐ 4 套 harness 清单并存 .claude-plugin/ · .cursor-plugin/ · gemini-extension.json · server.json（MCP）—— 同一个包面向 4 种加载方式。

架构启发

⭐⭐⭐⭐⭐ 启发一：把「数量」判据升级为「链路」判据，是本日最具迁移价值的一步。 11-16 说「release 多不等于有发布史」，本日说「release 多也可能真的等于有发布史」⭐⭐⭐⭐⭐ —— 两条合起来才是完整判据：不是看数量，而是看 tag → commit → diff 这条链断没断。⭐⭐⭐⭐⭐ 这条判据可以直接迁移到 commit 数、push 频率、版本号多样性、star 增速 —— 它们全都是「数量」，也都需要一条对应的链路来验。

⭐⭐⭐⭐⭐ 启发二：分层暴露（默认子集 + 开关）是能力与预算的通用解。 tools/list 默认 12 个、开关打开 42 个、每个按名可达 ⭐⭐⭐⭐⭐ —— 这个模式可以原样搬到任何「工具/插件/数据集」超过客户端预算的场景，⭐⭐⭐⭐⭐ 且它没有牺牲能力，只是改变了默认暴露面。

⭐⭐⭐⭐⭐ 启发三：把「release commit」与「功能 commit」分开，是一个低成本的工程纪律。 本项目实测的形态是：fix:/feat: 提交改代码 → chore(release): bump version to X.Y.Z [skip ci] 提交只改版本号与文档 → tag 打在这个 release commit 上。⭐⭐⭐⭐⭐ ⭐⭐⭐ 这条纪律的直接收益是：任何第三方都可以用「tag 的父 commit 有无源码 diff」来判断这个版本是否值得安装 —— ⭐⭐⭐⭐⭐ 不需要信任发布者的自述。**

⭐⭐⭐⭐⭐ 启发四：把「我测不出来的东西」写进文档，本身就是一种质量信号。 实测 README 里那句「the fixture has no real speech to transcribe, confirmed by installing faster-whisper mid-eval and re-testing by hand」⭐⭐⭐⭐⭐ —— ⭐⭐⭐ 这与本数据集此前记录的 pydtcpip 的「Verified / Unverified (profile implemented) / Not applicable」三档、hikaku-extension 的「把模型真实失败率写进 docs/MODELS.md」是同一条线索的最高级形态：⭐⭐⭐⭐⭐ 不仅标注「没测」，还写明「怎么确认的没测」。**

定位判断

生产可用 —— 且是本日报里「发布纪律」这一维度的正面标杆。

⭐⭐⭐⭐⭐ 在 Skill 生态里，本项目属于「把 Skill 当软件工程制品」的一端：⭐⭐⭐⭐⭐ 8 个 CI 工作流、ClusterFuzzLite、CodeQL、Scorecard、机器可读契约、版本化的 eval 结果、诚实的失败率记录。⭐⭐⭐⭐⭐ 与之相对的是 boring-marketing-skills 那一端：6 个 commit 交付 32 个技能。

⭐⭐⭐⭐⭐ ⭐⭐⭐ 这两端不是高下之分，而是两种不同的产品形态：⭐⭐⭐⭐⭐ 一端卖「可安装的能力」（ffmpeg-skill 卖 42 个工具 + 一套工作流），⭐⭐⭐⭐⭐ 另一端卖「可复用的知识包」（营销技能包）。⭐⭐⭐⭐⭐ 但本日从「分发适配层」的视角看，⭐⭐⭐⭐⭐ 前者已经解决了适配层成本（4 套清单 + 分层工具暴露），⭐⭐⭐⭐⭐ 后者还在起步（1 套清单）。

风险/局限/泡沫点

  1. ⭐⭐⭐ ⚠️ 100 个 tag 只抽样了 12 个：⭐⭐⭐ ⚠️ 「每个版本背后都有真实代码 diff」是抽样结论，未全量核验。
  2. ⭐⭐⭐ ⚠️ 0 / 100 个 release 带 asset：⭐⭐⭐ ⚠️ 因此 11-16 判据的第二段「release 资产是否随版本变化」在本仓库不适用，⭐⭐⭐ ⚠️ 也意味着无法用 asset 变化做独立交叉验证。
  3. ⭐⭐⭐ ⚠️ 单 owner 主导：⭐⭐⭐ ⚠️ kajisho5 322 commits，外部真人贡献仅 2 人（claude 4 / rymalia 2），⭐⭐⭐ ⚠️ 关键人风险仍在。
  4. ⭐⭐⭐ ⚠️ 高频发布本身是风险：实测中位间隔 2.42 小时、最小 0.3 小时，⭐⭐⭐ ⚠️ 即使每次都有真实 diff，版本粒度过细也意味着下游几乎不可能逐一验证 —— ⭐⭐⭐ ⚠️ 实质上把信任问题从「版本是假的」转成了「我该信哪个版本」。
  5. ⭐⭐ ⚠️ 未核验项：npm 包内容与仓库是否一致、42 个工具的实现质量、clusterfuzzlite 的实际覆盖范围、eval 的可复现性、README 中的自评数字。

mirkobrombin/raven

一句话定位

在 Linux 上跑 Windows 应用——不用虚拟机、不用 winetricks、不用 DLL 覆盖：程序代码直接跑在宿主 CPU 上，在不能触达 Linux 的沙箱里执行，它对 Windows 内核的每一次调用都由 Raven 自己应答（进程与线程、文件、注册表、窗口与输入）。

⭐⭐⭐ 而 2026-10-26 是这个项目最重要的一天：它在 24 小时内被彻底重写并重新许可——Go → C++、MIT → GPL-3.0-or-later、目录结构全换。 本档案 2026-10-25 记录的所有代码结构描述自今日起全部作废，详见「最近动态」。

它解决的问题

Wine 的经典使用姿势是「用 winetricks 逐个塞 DLL、用 winecfg 改注册表、用一个 prefix 装所有东西」——每个应用都要手工调教，且共享 prefix 时互相污染。

raven 的主张是把这一整套隐式约定变成显式的兼容层：

You install them with their own installers, the same ones you would use on a PC, and they start: no virtual machine, no winetricks, no DLL overrides. The program's code runs directly on your CPU, inside a sandbox where it cannot reach Linux. Every call it makes to the system is answered by Raven, which plays the part of the Windows kernel and its services: processes and threads, files, the registry, windows and input.

⭐ 而它针对的第二个问题是「兼容到什么程度」这个问题的可度量性。 大多数兼容层只说「能跑」或「不能跑」，而 raven 把它拆成四段并给出百分比。

  2. review 是一等字段——reviewed 与 requires-release-inventory 并存，即清单自己声明了「哪一部分还没核完」；

## 架构启发
⭐⭐⭐ 最值得迁移的一条：把「我凭什么这么说」写成机器可读的清单，而不是散落在散文里。

raven 的 LICENSES.json 给了本日报一个可以直接抄的模板：顶层有 schema_version（格式版本）、review_date（时效声明）、original_code_license（总体判断）、license_references（引用外部许可文本的方式）；每条组件有 paths（精确到文件而非目录）、license（该组件的实际条款）、review（该条是否已核完）、provenance（从哪来）。 ⭐⭐⭐ 而最巧妙的两个细节是：① review 是一等字段，所以「还没核完」这件事可以被机器读出来；② review_date 是一个日期，所以「这份清单会过期」这件事被写在了结构里而不是文档里。

⭐⭐⭐⭐ 第二个启发（本日报认为本日最值得单独指出的一条）：重新许可的正确做法是「分层 + 历史存续」，而不是「追溯改许可」。

raven 没有假装自己一直是 GPL，也没有宣布过去的 MIT 授权作废，而是明写「Earlier MIT grants remain valid」并把 guest adapters 单独列为 MIT。 ⭐⭐⭐⭐⭐ 这条做法对任何需要改变许可的项目都成立：它同时满足了「新贡献受新条款约束」与「历史使用者的既有授权不受影响」，而且把这个区分写成了结构化条款而不是一句解释。

⭐⭐ 第三个启发：主动作废自己的数据，比隐藏它更可信。 「These replace the earlier ClassiCube series; its scene configuration was not verified against the retained samples.」——它没说「之前的数字有问题」，也没删掉，而是说明作废原因并把旧数据留在仓库里对照。 这与本日报 10-24 记录的 hatchzip「Every number in the README and docs is measured on real hardware, never estimated」是同一条纪律的两个方向：一个禁止编造，一个禁止掩盖。

⭐⭐ 第四条：它对「可复现性」与「性能」的取舍是选软件 Vulkan，明说硬件 GPU 会抬高所有 runtime 的数字。 这意味着它给出的绝对 FPS 数字是偏低的——但换来了「任何人都能在同样的条件下重跑」。这是一个把「结论的可复现性」置于「结论的好看」之上的选择。

⭐⭐⭐⭐ 而关于 fork 比例，它提供了本日最实用的一条读法。 它的 fork/star 只有 2.1%，本批最低。但这不是「没人要它」——fork 一个 18.5 MB、678 个 commit、20 个上游组件、且宿主部分是 GPL 的兼容层，成本与 fork 一份 26 KB 的 Markdown 差了两个数量级。 因此在评估「有多少人在真的改造这个项目」时，fork/star 必须先按「改造单位成本」分层，再在同一层内比较。

⭐⭐⭐⭐⭐ 而本日最有价值的一条元数据教训，来自这个项目本身： 它的 created_at 在一次 14 个月的改名后仍然指向改名当天；在一次彻底重写后仍然指向同一天。 ⭐⭐⭐⭐ 即：created_at 记录的是「这个 GitHub 对象何时被创建/命名」，与「项目何时开始」「项目现在多活跃」三者完全独立。 ⭐⭐⭐⭐⭐ 而本日报 10-25 建立的「用 commits API 的最早时间戳交叉验证 created_at」这条规则，在本日再次得到验证。

定位判断

「Windows on Linux」赛道的第三种技术路线，且是本日最值得当作方法论样本的一个。

现有路线大致是：虚拟机（隔离最强、性能最差）、Wine（复用成熟实现、但依赖 winetricks 式的隐式调教）、以及自建兼容层（成本最高、控制力最强）。raven 走的是第三条——这意味着它的兼容面完全由自己的工作量决定，而不受上游 Wine 进度牵制；代价是每一个未实现的 API 都是它自己的负债。

⭐⭐ 而它今天真正的价值可能不在兼容层本身，而在它的三份「诚实工程」文档： 兼容评分表、benchmark 的作废与交替说明、测试跳过条件的公开。这三样都可以被任何做兼容性工作的团队直接抄用，而与 Windows 无关。

⭐⭐⭐⭐ 而本日它新增了第四样，而且这一样与前三样同源：那份机器可读的许可清单。 ⭐⭐⭐⭐ 四份加起来构成了一个完整的「工程诚实」样本——它对性能、测试、数据、许可四个维度都选择了「宁可说难看也不说好看」。 ⭐⭐⭐⭐⭐ 而本日最值得强调的是：这四份文档在一次彻底的重写之后全部存活了下来——即它的方法论与实现语言无关，而这一点只有经过一次重写才能证明。**

⭐⭐⭐⭐⭐ 而商业影响必须被明确记录：宿主运行时从 MIT 变为 GPL-3.0-or-later，这对以 MIT 假设做过集成规划的使用者是一个重大条款变更。⭐⭐ 「Earlier MIT grants remain valid」指的是历史授权的存续，而新的贡献与分发适用 GPL——这两件事不可混为一谈。**

风险 / 局限 / 泡沫点

  • ⚠️⚠️⚠️ 最大的元数据风险未变：created_at 不可信。 任何自动化流程——包括本日报自己的「今日新项目」筛选——若只用 created_at，会把这个 14 个月的项目当成 4 小时前的新项目。本日报 10-25 起把「用 commits API 最早时间戳交叉验证 created_at」加入筛选规则；10-26 再次验证该规则有效（一次彻底重写没有改变 created_at）。
  • ⚠️⚠️⚠️⭐ 许可变更的商业影响（本日新增）：宿主运行时从 MIT 变为 GPL-3.0-or-later。 ⭐ 对以 MIT 假设做过集成规划的使用者，这是一个重大条款变更。 README 明写「Earlier MIT grants remain valid」，但那指的是历史授权的存续，而新的贡献与分发适用 GPL。

与同类项目的关系

  • vs Wine：最直接的对照。 Wine 是「复用 Wine 的实现，用 winetricks 补洞」；raven 是「自己实现 Win32 语义，按自己的兼容度表说话」。⭐ 二者的关键差异在可核验性：Wine 的兼容性靠社区与发行版测试网，raven 靠一张自己维护的评分表——后者对单次评估更有用，前者对生态更有用。
  • vs Soda / WineD3D 等实验性兼容层：raven 与 Soda 的 benchmark 被放在同一张表里四轮交替比较——这本身就是一种罕见的做法：把自己的项目放在竞品的基准表里，而不是单发一个自己的数字。
  • vs 虚拟机方案（QEMU/KVM + Windows）：性能与兼容性上 raven 明显占优（直接执行机器码），但隔离性与「什么都能跑」上虚拟机占优。 raven 的沙箱是「不能触达 Linux」的单向隔离，不是完整虚拟化。
  • vs CrossOver / Wine Proton：它们是打包好的商业发行版，raven 是从源码构建的工程——因此它的使用门槛完全不同：Proton 装完即用，raven 需要 CMake + C++20 + MinGW + 一堆图形依赖。
  • ⭐⭐ vs 本日报 10-26 同日的 trailofbits/brotli-checker（LICENSES.json / verified_on / SECURITY.md）： ⭐⭐ 两者是同一条工程原则在两个维度的实现 —— raven 的 LICENSES.json 把许可边界结构化并配 review_date，brotli-checker 的 fingerprints.json 把安全指纹结构化并配 verified_on。⭐⭐⭐ 而两者都做了一件关键的事：都没有假装自己是完整的（raven 有 review: "requires-release-inventory"，brotli-checker 有 SECURITY.md「snapshots, and an old checkout does not automatically receive new guidance」）。**
  • ⭐⭐ vs 本日报 10-26 同日的 KohakuBlueleaf/KohakUnlock（NOTICE.md 溯源链）： ⭐⭐ 同样是把「来源与许可」结构化 —— KohakUnlock 的 NOTICE.md 记录代码来源链（haohervchb/Turing-unlock → PZH1gdmu/CMP40HX-Unlock → CMP 90HX → Jon Pry），raven 的 LICENSES.json 记录文件级许可归属。⭐⭐⭐ 而两者都做了一件关键的事：都没有假装自己是原创的（raven 明写「Earlier MIT grants remain valid」，KohakUnlock 明写「Public availability is not by itself redistribution permission」「No upstream endorsement implied」）。
  • vs songjianyang/xss-audit（本批）：唯一的共同点是都在处理「一个已经存在的东西的兼容性」，且都在文档里明确列出「什么还不支持」。

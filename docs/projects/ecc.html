ECC

最近动态（2026-11-23）

⭐⭐⭐⭐⭐ 本日对本项目做的是口径审计复测，结论是：11-18 日报的头条发现「1,087 文件 / 330 身份 = 3.30×，最大单一技能被复制 10 份」需要按三层重新解读，⭐⭐⭐⭐⭐ 而其中「被复制 10 份」这一条经实测是不准确的。

可核验事实一：两套口径在同一棵树上并置（2026-11-23 CST）。

⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 决定性事实：11-18 说「verification-loop / tdd-workflow / security-review / frontend-patterns / coding-standards / backend-patterns 各被复制 10 份」—— 本日实测 backend-patterns 是 10 份副本 / 9 个不同 blob sha、coding-standards 是 10 份副本 / 9 个不同 blob sha，⭐⭐⭐⭐⭐ 即「10 份」是同名身份出现在 10 个目录，⭐⭐⭐⭐⭐ 而这 10 份里有 9 份是各自不同内容的 harness 变体，只有 1 份是原始件。⭐⭐⭐⭐⭐ 因此「被复制 10 份」这个说法在内容层面不成立。

⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 而这个修正不是贬低 ECC，反而解释了它为什么好：⭐⭐⭐⭐⭐ 9 个 harness 目录（.agents / .claude-plugin / .codebuddy / .codex-plugin / .cursor / .gemini / .grok-plugin / .kiro / .opencode）⭐⭐⭐⭐⭐ 意味着每个技能都要针对 9 个 harness 各写一份 —— ⭐⭐⭐⭐⭐ 「变体」正是适配层的必要产物，⭐⭐⭐⭐⭐ 而 11-18 把这种必要产物误读成了「复制放大」，⭐⭐⭐⭐⭐ 由此得出的「ECC 的内容层与适配层投入比（3.30×）值得被持续观测」这一条推论也随之失效 —— 因为它的内容冗余倍数只有 1.15×，是本队列中第二低的。⭐⭐⭐⭐⭐ 修正后的正确表述是：ECC 的内容层（944 个不同技能内容）与适配层（1,089 个文件）之比是 1.15，⭐⭐⭐⭐⭐ 而「273 个技能有 9 套变体」才是它支持多 harness 的真实代价。**

⭐⭐⭐⭐⭐ ⭐⭐⭐ 第三点（本日的新事实）：它已离开 Trending 榜单。 ⭐⭐⭐⭐⭐ 实测 11-18 的 25 个仓库中只有 15 个留在 11-23 榜单上，⭐⭐⭐⭐⭐ ECC 是离榜者之一（11-19 快照 306,433⭐ 后未再出现）。⭐⭐⭐⭐⭐ 本日报不主张它的热度下降 —— 305,425 → 306,433 的 6 日净增仅 +1,008（约 +0.3%），⭐⭐⭐⭐⭐ 远低于它此前 11-17 记录的 +66,998，⭐⭐⭐⭐⭐ 但「此前 11-17 的 +66,998 是两个快照点之差而非时间序列增速」这一保留仍然成立，⭐⭐⭐⭐⭐ 本日无法用现有数据判断这个落差是趋势还是快照噪声。

⭐⭐⭐⭐⭐ ⭐⭐⭐ 第四点：它的分发纪律部分未受影响。 ⭐⭐⭐⭐⭐ 实测 15 个 CI 工作流仍在（含 generator-generic-ossf-slsa3-publish.yml / pr-burst-guard.yml），⭐⭐⭐⭐⭐ 9 套 harness 目录不变，⭐⭐⭐⭐⭐ 19 release / 20 tag 不变，⭐⭐⭐⭐⭐ 且实测到 scripts/sync-ecc-to-codex.sh / scripts/dev/generate-skill-triggers.js / scripts/lib/codex-legacy-sync.js 等 23 个生成/同步脚本路径 —— ⭐⭐⭐⭐⭐ 即「变体是被脚本生成的」这一点有文件名层面的证据，⭐⭐⭐⭐⭐ 但本日报未读取这些脚本，⭐⭐⭐⭐⭐ 因此不主张它们生成的是「变体」还是「副本」以外的任何东西。

一句话定位

Agent harness 的「操作系统」—— 本日它最有价值的一条发现不是它有多少技能，而是「1,087 个 SKILL.md」这个数字本身需要被拆开：实测其中 272 个技能身份（占 1,029 个文件）在 3–10 个 harness 目录下各存一份，真实的独立技能身份只有 330 个。

它解决的问题

Coding Agent 生态的碎片化有两个层面：① 能力层（技能、记忆、约束、安全策略该由谁提供）与 ② 适配层（同一套能力要能在 Claude Code / Codex / Cursor / OpenCode / Gemini / Grok / Kiro / CodeBuddy 上都成立）。⭐⭐⭐⭐⭐ ECC 同时打这两层：它把 Skills / Instincts / Memory / Security / Research-First Development 打包成一套跨 harness 配置层，以 npm 包（ecc-universal、ecc-agentshield）、GitHub App（ecc-tools）、插件 slug（ecc@ecc）三种形态分发。

为什么值得关注（2026-11-18）

⭐⭐⭐⭐⭐ 因为它是本数据集里第一个能被完整量化的「多 harness 适配层」样本 —— 也因此，它是第一个暴露「适配层计数会被复制定义放大」这个陷阱的样本。

可核验事实三：release 链条是「真实但慢」的形态。 19 个 release 从 v1.8.0（2026-03-05）到 v2.2.3（2026-10-01），⭐⭐⭐⭐⭐ 版本号语义连续、每个 release body 都写明该版本做了什么（实测 v2.2.3 body 首句：「a naming and release-reliability update」；v2.2.1 body 明确写「keeps the published v2.2.0 history immutable」—— 即它把「发布历史不可变」写成了发布说明）。⭐⭐⭐⭐⭐ 与 ffmpeg-skill 的「每天 2–3 次」形成鲜明对比：ECC 是「少而实」，ffmpeg-skill 是「多而实」，11-16 的 steam-library-bridge 是「多而假」。⭐⭐⭐⭐⭐ 但 ECC 的 19 个 release 里 13 个是 0 asset，且本日报抽样 12 个 tag 时看到 v2.2.3 的 tag commit 改了 205 个文件、其中 36 个是源码，其父 commit 只改 31 个文件 —— ⭐⭐⭐⭐⭐ 与 ffmpeg-skill 正好相反：这次是 tag commit 本身是功能 commit，父 commit 是上一个功能。⭐⭐⭐⭐⭐ 这说明「功能 commit 在 tag 上」还是「功能 commit 在 tag 的父上」都不是判据，⭐⭐⭐⭐⭐ 判据仍然是「这条链上是否存在真实代码 diff」。**

热度来源判断

⭐⭐⭐⭐⭐ 判断：热度是真实需求 + 长期工程积累的结果，但「30 万星」这个体量需要与「330 个独立技能」这个分母一起读。

支撑的可核验事实： 1. ⭐⭐⭐⭐⭐ 贡献者结构真实且多元：affaan-m 1,778 之外，haelyra 882、montjeffrey 179、L4XB 84 —— 有真实的第二/第三贡献者，不是单人刷量。 2. ⭐⭐⭐⭐⭐ 9 套 harness 目录 + 15 个 CI 工作流 + SLSA3 发布工作流 —— 这是持续工程投入的结构证据。 3. ⭐⭐⭐⭐⭐ 官方渠道声明（README 原文）—— 主动防御第三方重上传，是成熟项目的典型特征。 4. ⭐⭐⭐⭐⭐ 19 个 release 的版本号连续、body 具体，且明确承诺「发布历史不可变」。

⭐⭐⭐⭐⭐ ⚠️ 不作主张的部分：本日报未做 star 增速的时间序列统计，所有 ⭐ 数为快照绝对值；⭐⭐⭐⭐⭐ 1,495 个 subs 与 44,975 个 forks 的比值（3.3%）在本数据集里属正常区间（对照 google-research/paper-orchestra 0.87%、google/elephant-goldfish-model 0.4%），未见异常。⭐⭐⭐⭐⭐ 本日报不主张「1,087 个 SKILL.md」代表 1,087 项能力 —— 实测独立技能身份只有 330 个。

关键技术亮点

  1. ⭐⭐⭐⭐⭐ 跨 harness 适配层是「一份内容 + N 份清单」而不是「N 份实现」 实测 9 个 harness 目录与 1,029 个复制文件构成一个矩阵：⭐⭐⭐⭐⭐ 同一份 SKILL.md 内容以相同 blob sha 存在于 3–10 个 harness 路径下（138 个 blob-sha 组有 >1 份副本）。⭐⭐⭐⭐⭐ 这比 11-17 记录的 EGM「6 套清单」更进一步 —— EGM 是 6 个目录，本项目是 9 个目录且带 10 份复制。**

  2. ⭐⭐⭐⭐⭐ 发布链有「可复现的不可变性」承诺 实测 v2.2.1 release body 原文含「It keeps the published v2.2.0 history immutable」⭐⭐⭐⭐⭐ —— 即它把「历史不可变」当作版本策略的一部分写出来，⭐⭐⭐⭐⭐ 这与 11-16 记录的 steam-library-bridge（1 个 commit → 4 个语义无关版本号）形成正反对照。

  3. ⭐⭐⭐⭐⭐ SLSA3 供应链 provenance 工作流 generator-generic-ossf-slsa3-publish.yml 的存在 ⭐⭐⭐⭐⭐ —— 即它把「发布物的来源证明」做成了 CI 阶段，这在本数据集的 25 个 Trending 仓库里是唯一见到 SLSA3 命名工作流的。

  4. ⭐⭐⭐⭐⭐ 面向「harness 性能」而非「harness 能力」的产品定位 项目自述「The agent harness performance optimization system」（README description 实测）⭐⭐⭐⭐⭐ —— 注意这与 google/elephant-goldfish-model（评审范式）、ffmpeg-skill（确定性工具调用）、kajisho5/ffmpeg-skill（工作流纪律）分属不同象限。

  5. ⭐⭐⭐⭐⭐ 18 种语言的 README 本地化 实测 README 头部列出 English / العربية / Português (Brasil) / 简体中文 / 繁體中文 / 日本語 / 한국어 / Türkçe / Русский / Tiếng Việt / ไทย / Deutsch / Español / Українська / Polski / বাংলা / Italiano ⭐⭐⭐⭐⭐ —— 分布型项目的国际化投入。

  6. ⭐⭐⭐⭐⭐ 发布前有专门的「PR 爆发守卫」 pr-burst-guard.yml + issue-submission-guard.yml ⭐⭐⭐⭐⭐ —— 即它在流程层面对「突然出现的大量 PR/issue」有显式防护，⭐⭐⭐⭐⭐ 这恰好是本数据集 11-13 ~ 11-17 反复遇到的那类攻击面的镜像防御。

系统边界 一个「跨 harness 配置/技能包 + 一条分发链」。内容边界 = SKILL.md 契约 + 技能本体；分发边界 = npm（ecc-universal / ecc-agentshield）+ GitHub App + ecc@ecc 插件 slug + ecc.tools。不含模型、不含 harness 本身 9 个 harness 目录、15 个 CI 工作流、README 的 18 语言头部与官方渠道声明；npm 包内容、GitHub App 行为、插件 slug 的实际分发物均未核验

最小 PoC 在单一 harness（建议 Claude Code）用引导安装器装 ECC → 只启用 1–2 个技能 → 跑一次真实任务并记录 token 占用 → 换第二个 harness（建议 Codex）装同一版本 → 比对两次行为差异与安装目录差异 → 最后才评估扩到第 9 个 harness 的边际成本 PoC 范围与退出路径由本档案推导；具体 token 阈值、安装器交互、跨 harness 行为一致性均未核验

架构启发

⭐⭐⭐⭐⭐ 启发一（本日的核心）：任何「跨 N 个 harness」的计数，必须先做身份去重，否则会把分发层的工作量误读成内容层的产出。 ECC 的 1,087 → 330 就是这个比值。⭐⭐⭐⭐⭐ 这条规则可直接迁移到：多语言文档数、多端适配层数、多租户配置项数、多镜像副本数。⭐⭐⭐⭐⭐ 本日报把这称为「复制放大型计数」（multiplication-inflated count）—— ⭐⭐⭐⭐⭐ 它不是造假，而是同一个东西的多个物理副本被当成了多个东西。

⭐⭐⭐⭐⭐ 启发二：「tag → commit → diff」判据的第三种形态出现了。 11-16 的 steam-library-bridge（4 版本号 / 1 commit / 无 diff）是假；11-17 的 ffmpeg-skill（100 版本号 / 父 commit 有 diff）是真，且功能 commit 在父上；本日 ECC（19 版本号 / tag commit 自身有 36 个源码文件 diff）是真，且功能 commit 在tag上。⭐⭐⭐⭐⭐ 三种形态同表，说明「功能 commit 在前还是在后」不是判据，「链上有没有真实 diff」才是。

⭐⭐⭐⭐⭐ 启发三：适配层的成熟形态是「复制 + 目录矩阵 + 自动化守卫」三件套。 ECC 同时具备 9 套目录、SLSA3 provenance、pr-burst-guard ⭐⭐⭐⭐⭐ —— 而 11-17 的 EGM 还停留在「连打包时怎么定位 Claude 根目录都要专门修」的状态。⭐⭐⭐⭐⭐ 两者差距不在内容，在分发纪律。**

⭐⭐⭐⭐⭐ 启发四：被模仿得多的项目会开始自己声明「什么渠道是真的」。 ECC 的「Official sources only」警告 ⭐⭐⭐⭐⭐ 是本数据集里第一次由被投放/被模仿的一方主动做出的防御（此前 11-13 ~ 11-17 的记录中，防御动作都在观测者一侧）。**

gavamedia/deltafin

一句话定位

实验性项目，探索在单台 Apple Silicon Mac 上运行远超内存容量的 2.8T 参数 Kimi K3 MoE 模型——MXFP4 专家按需经 HTTP 流式加载到本地磁盘缓存，融合 NEON 内核 + Metal 计算。

它解决的问题

2.8T 参数模型的权重远超任何单机的内存（即便是 192GB 工作站）。但 MoE 的稀疏性（每 token 仅激活 896 专家中的 16 个 = ~104B）意味着同一时间实际需要的专家子集很小。deltafin 探索：能否利用这种稀疏性，把不活跃的专家留在远端/磁盘，按需流式加载？

为什么值得关注（2026-07-30）

  • 范式验证：证明超大 MoE 的"专家按需加载"在原理上可行——不是能不能跑，而是跑多远。
  • 随 Kimi K3 发布同步出现：是 K3 权重开源后的第一个本地推理运行时尝试。
  • 诚实的性能标注：明确标注 M1 Max 64GB 实测 0.0687 token/s（14.6s/token），并说明这是"初代机器参考值，非新硬件上限"——没有夸大。

热度来源判断

好奇心 + 话题驱动，非实用需求。 "在你的 Mac 上跑 2.8T 模型"是极强的标题党，但 14.6s/token 无法用于任何交互场景。热度（2 天 308⭐）合理——它是一个引人注目的工程实验，而非生产工具。项目方对性能局限的诚实标注是加分项。

关键技术亮点亮点

  1. MXFP4 专家按需流式加载：专家权重经 HTTP 流式下载到本地磁盘缓存，磁盘做有界缓存（可超磁盘容量），重复专家命中本地。
  2. 融合 NEON 内核 + Metal/MPS 计算：Apple Silicon 上用 MPS 做 resident 模型路径，配合原生 MXFP4 专家内核。
  3. 跨平台自动选择：macOS arm64 选 MPS，Linux x86-64/aarch64 选 CUDA 或 CPU，自动匹配兼容内核。
  4. 贪心解码、可复现：greedy decoding，结果可精确复现——这对调试/实验有价值。

架构启发

deltafin 验证了一个有价值的工程方向：MoE 稀疏性使"专家按需加载"成为可行的超大模型部署范式。2.8T 中每 token 仅需 16 个专家，如果缓存命中率高，磁盘/远端带宽可以承载。这对边缘、离线、低频批量场景的超大 MoE 部署有启发。Trade-off：交互式场景（低延迟）不可行，专家加载延迟（磁盘/网络）是硬瓶颈。

定位判断

观察型实验项目，非生产工具。 它的价值在于范式探索与启发，而非当前可用性。对架构师的启发是：未来超大 MoE 的本地/边缘部署，"专家缓存 + 按需加载"是值得认真对待的方向。

风险 / 局限 / 泡沫点

  1. 性能不可用：14.6s/token（M1 Max 64GB）无法用于交互；即便在更高内存机器上也难达实用吞吐。项目方自己也标注为"参考值"。
  2. 专家缓存命中率未知：按需加载的有效性高度依赖专家局部性（同一专家是否被连续调用），项目未给出命中率数据。
  3. 强依赖磁盘/网络带宽：首次加载专家的 HTTP 下载延迟在真实网络条件下可能远高于实验室环境。
  4. License 为 NOASSERTION：需确认实际许可条款。

与同类项目的关系

  • vs llama.cpp / MLX：主流本地推理框架针对能放进内存的模型优化；deltafin 针对"放不进内存"的超大 MoE，是不同问题域。
  • vs 云端 K3 推理服务：deltafin 是本地/离线探索，云端服务在吞吐与延迟上完全不在同一量级。

是否值得持续跟踪

有限跟踪。 作为范式探索值得关注，但短期内无生产价值。若出现更高内存硬件（如 256GB+ Mac）上的实测数据，或专家缓存命中率数据，则值得重新评估。

后续观察点

  1. 在更高内存硬件（M3 Ultra 192GB+）上的实际吞吐与专家缓存命中率。
  2. 是否启发主流本地推理框架（MLX/llama.cpp）增加"专家按需加载"支持。

google-research/paper-orchestra

一句话定位

Google Cloud AI Research 的多 agent 论文写作框架 —— 它的研究价值不在功能（56 个文件、8 个 commit 的极薄仓库），而在于它是本日实测的一个反例：一个「star 增速高 + 100 个 fork 集中涌入」的仓库，其 fork 群体的结构与 GitHub 上最成熟的仓库几乎一样。

它解决的问题

⭐⭐⭐⭐⭐ 从「未成文的原始材料」到「可投稿的 LaTeX 稿件」之间的整条流水线。 README 原文（实测）：

PaperOrchestra is a multi-agent framework for automated AI research paper writing. It flexibly transforms unconstrained pre-writing materials (ideas and experimental logs) into submission-ready LaTeX manuscripts, including comprehensive literature synthesis and generated visuals, such as plots and conceptual diagrams.

⭐⭐⭐⭐⭐ 它编排五个专职 agent（README 原文）：Outline / Literature Review / Section Writing / Content Refinement / Plotting。 ⭐⭐⭐⭐⭐ 仓库结构与之一一对应（实测 methods/agents/ 下 5 个文件）：outline_agent.py / literature_review_agent.py / section_writing_agent.py / content_refinement_agent.py / plotting_agent.py。

为什么值得关注（2026-11-18）

⭐⭐⭐⭐⭐ 因为本日实测它的 fork 群体，并做了一件此前 11-12 ~ 11-17 日报从未做过的事：把它和 torvalds/linux、rust-lang/rust、golang/go 放在一起做对照。⭐⭐⭐⭐⭐ 结论是反直觉的，也是本日最重要的方法论产出。

⭐⭐⭐⭐⭐ ⚠️ 不作主张的部分：⭐⭐⭐⭐⭐ 本日报不主张这 100 个 fork 是刷的（见事实三的对照实验）。⭐⭐⭐⭐⭐ 本日报也不主张 star 增速的真实构成 —— 只记录 Trending 页面的日榜增量 +1,175。⭐⭐⭐⭐⭐ 本日报未运行该框架、未消耗任何 LLM API key、未核验它生成的 LaTeX 是否真的可编译。

关键技术亮点

  1. ⭐⭐⭐⭐⭐ 五个专职 agent 的一一对应实现 实测 methods/agents/ 下 5 个文件与 README 声明的 5 个角色精确对应 ⭐⭐⭐⭐⭐ —— 「多 agent」不是营销词，而是有明确文件边界的分工。

  2. ⭐⭐⭐⭐⭐ 「autoraters」作为独立的质量门禁层 实测目录 autoraters/ 下有 agent_review.py / citation_f1.py / lit_review_quality.py / sxs_lit_review_quality.py / sxs_paper_quality.py ⭐⭐⭐⭐⭐ —— ⭐⭐⭐⭐⭐ 即它把「评审」实现成可编程的评分器（含 F1 这种确定性指标），⭐⭐⭐⭐⭐ 而不是让另一个 LLM 自由发挥。⭐⭐⭐⭐⭐ 这与 11-17 NVIDIA/SkillEvaluator 的「把评估做成多 tier 流水线」是同一方向的不同实现。

  3. ⭐⭐⭐⭐⭐ 会议模板作为一等公民 实测 templates/cvpr2025/（template.tex / preamble.tex / cvpr.sty / ieeenat_fullname.bst / references.bib / guidelines.md）与 templates/iclr2025/（template.tex / fancyhdr.sty / natbib.sty / math_commands.tex / iclr2025_conference.bst）⭐⭐⭐⭐⭐ —— ⭐⭐⭐⭐⭐ 即输出目标不是「一份 LaTeX」，而是「一份符合某个会议投稿规范的 LaTeX」。⭐⭐⭐⭐⭐ 而 issue #43 正是「默认 CVPR 模板应改为双盲评审模式」—— ⭐⭐⭐⭐⭐ 说明模板细节是真实使用中的高频摩擦点。

  4. ⭐⭐⭐⭐⭐ LLM provider 可插拔，且只要求实际用到的那个 key 实测 utils/llm_backend_utils.py / openai_utils.py / gemini_utils.py / paper_banana_utils.py，⭐⭐⭐⭐⭐ 以及 commit Only require API keys for the LLM provider actually used（2026-11-15）⭐⭐⭐⭐⭐ —— ⭐⭐⭐⭐⭐ 即一个外部贡献者在 11-15 刚修掉「要求配齐所有 provider 的 key」这个上手门槛，⭐⭐⭐⭐⭐ 而这正是 Trending 爆发的前一天。⭐⭐⭐⭐⭐ 这个时间关系值得注意，但本日报不主张这是流量的原因。

  5. ⭐⭐⭐⭐⭐ 检索层有多个来源 实测 utils/scholar_utils.py + utils/gemini_utils.py，⭐⭐⭐⭐⭐ README 的 .env 示例里同时列出 SEMANTIC_SCHOLAR_API_KEY 与 OPENAI_API_KEY / VERTEX_AI_* / GEMINI_API_KEY ⭐⭐⭐⭐⭐ —— 文献综述依赖 Semantic Scholar，生成依赖 LLM provider。

  6. ⭐⭐⭐⭐⭐ 前端用 Gradio 风格的服务 实测 frontend/app.py + frontend/examples/cvpr_example.json + frontend/examples/cvpr_example_figure.png ⭐⭐⭐⭐⭐ —— 有可交互 demo 与示例产物。

定位判断

1. Herdr 协调器对话 + 并行 worker 线程（趋势分 88）

  • eliasstravik/herdr-projects（1 天 140⭐ / fork 4 / fork/star 2.9% / Rust / MIT / 151 KB）——「Run a whole project across your coding agents without handing each one its task or keeping track of who is doing what」；定位 Herdr 0.9.1+ 插件；架构 一个协调器对话（coordinator conversation）+ 多个 worker 线程（parallel worker threads）+ 共享 memory（shared memory）+ 任务 need 概览（overview of what needs you）；协调器 永不亲自干活永远可对话——只负责路由 + 用户沟通；每个任务 独立 agent 跑在独立 git worktree + 独立分支（无仓库时单文件夹）；所有线程共享同一份指令 + 项目级 memory；侧栏按 5 组聚合 ready-for-review / waiting-on-you / working / landing / idle——ready-for-review 等待人工 review，waiting-on-you 卡权限提示 > 30 秒自动归类，working 在跑，landing 收尾合并中，idle 空闲；threads 状态 ticker 跟 PR + 例行 routine；lessons under ## Remember 流回 memory 给下一个 thread——这是「agent 上下文复用」的工程化形式；README 表头 9 项对比（Herdr Projects vs Briefing agents by hand vs One long agent session vs Cloud projects products）——Herdr 在「No extra software fee」「Parallel tasks on separate branches」「Same instructions and memory for every task」「One conversation that stays free to answer」「Threads grouped by what needs you」「Runs on your own machines」「Adopts an agent pane you already started」「Works with the agent CLI you already use」8 项 ✅，仅「Runs with no machine of yours switched on」❌（vs cloud projects products）；支持 macOS + Linux + Herdr 0.9.1+；自托管无 hosted service；不需预装 Node.js（wallpaper / install 脚本直接跑）；MIT License。
  • 核心价值定位： 当前 Coding Agent 多 agent 协作的痛点是 「5 个 agent 各跑各的 + 用户必须给每个 agent 单独简报 + 还得自己跟 5 个 PR 的状态」 ——Herdr Projects 用「一个协调器对话 + N 个 worker 线程 + 共享指令 + 共享 memory + 5 组 sidebar」是「用户决策层 + worker 执行层 + 项目级 memory 层」三层的工程化形式；协调器永不亲自干活 是「决策路由 vs 工作执行」分离的工程化形式——协调器永远有空回答用户；每个 task 独立 git worktree + 分支 是「worker 隔离 + 不污染主分支」的工程化形式——多个 worker 同时跑不会冲突；所有线程共享同一份指令 + 项目级 memory 是「agent 上下文复用」的工程化形式——一个 worker 学到的教训流回 memory 下一个 worker 直接用，避免每个 worker 都从零开始；5 组 sidebar 聚合 + waiting-on-you 自动归类 是「用户注意力集中」的工程化形式——用户只看「需要我做什么」不用管「5 个 agent 在干嘛」；对个人开发者：可在一个项目里并行跑多个 worker（如重构 A 模块 + 写测试 + 修 bug）只看 ready-for-review；对小团队：可分配不同任务给不同 worker + 共享项目规约 + 共享教训；对企业：自托管 + 无 hosted service + 适配现有 agent CLI 是「不绑定云服务」的具体路径。
  • 架构亮点： coordinator + worker threads 架构——coordinator 永远对话用户，worker threads 跑具体任务，两者通过 brief / report / ## Remember lessons / sidebar groups 解耦；每个 task 独立 git worktree + 分支——避免多 worker 冲突 + PR 自然产生；项目级 memory + lessons 流回——agent 上下文复用 + 跨线程知识积累；5 组 sidebar——ready-for-review / waiting-on-you / working / landing / idle 把「用户需要做什么」聚合在一处；waiting-on-you 自动归类——卡权限提示 > 30 秒自动从 working 移到 waiting-on-you，避免用户漏看权限请求；threads 状态 ticker——后台跟 PR + 例行 routine（如 nightly test）每个变化落到 coordinator inbox；自托管 + 无 hosted service——数据不外传 + 无 SaaS 锁定；适配现有 agent CLI——Herdr Projects 是「Herdr 之上的插件」不重写 agent 本身；MIT License——明确许可。
  • 价值判断： 它解决的是「多 agent 协作 + 用户注意力管理 + 项目级 memory 共享」的真痛点；MIT + Rust + 151 KB + Herdr 0.9.1+ + coordinator / worker 分离 + 5 组 sidebar + lessons memory + 自托管 macOS / Linux 是「严肃多 agent 编排插件」形态；140⭐ / fork 4 / fork/star 2.9% / 1 天 反映早期严肃信号（fork/star 2.9% 与昨日 dsh-computer-use_codex-style 0% / agent-skills 0% / hexis 1.4% 接近，低于 clawback 11.8% / cortisal-stack 16.1%——说明「多 agent 编排」是观察学习阶段而非企业 fork 阶段）；决定长期价值的是「Herdr 平台本身的活跃度 + coordinator / worker 协议是否被其他工具采纳 + 项目级 memory 在跨线程复用的实证效果」 ——Herdr 平台本身是 1 人项目还是公司维护 + coordinator / worker 协议是否成为开源标准 + memory 流回是否真的让下一个 worker 更聪明是关键；对个人开发者：适合「一个大任务分多个 worker 并行」的场景（如同时重构多个模块 + 写测试 + 修 bug）；对小团队：可作为「不绑 SaaS 的多 agent 协作工具」；对 Herdr 生态：Projects 插件是 Herdr 平台的关键扩展，把「单 agent 对话」升级到「多 agent 项目」。

2. 验证驱动 AI 软件迭代引擎（趋势分 86）

  • indada/repopilot（1 天 95⭐ / fork 6 / fork/star 6.3% / TypeScript / MIT / 378 KB）——「Verification-driven software iteration, powered by the OpenAI Codex SDK and hosted on your own worker」；架构 OpenAI Codex SDK + 自托管 worker + 独立 Docker runner；输入 GitHub Issue + PR；流程 Issue / PR → 需求驱动测试生成 → 失败复现 → 代码修复 → 独立 Docker runner 验证 → 维护者保留 merge 决策；关键约束 修复前冻结测试 + 候选必须保留测试身份 + 通过独立执行 + 通过 policy 重检；环境失败 有界重试（避免无限循环）；不稳定 / 不完整证据 阻断自动修复；输出 本地 JSON / Markdown 报告——findings + test outcomes + repair attempts + publication state；规约 AGENTS.md 项目规约 + Codex 语义审查 + 引用规则 + 代码证据——静态规则 + 语义审查 + 证据链三件套；README 4 章 Why RepoPilot? / What problem does it solve? / Who is it for? / Architecture 给出清晰范围声明「broader autonomous iteration is a project vision; unattended product development, merging and deployment are not current capabilities」——「范围边界 + 维护者最终 merge gate」是「严肃 AI Coding 工具」的关键工程化形式；MIT License；中英 README 双语（README.zh-CN.md）。
  • 核心价值定位： 当前 AI Coding Agent 工具的痛点是 「Issue 描述了 bug 但没 regression test / PR 改了行为但旧 test 没覆盖 / AGENTS.md 项目规约 agent 容易漏 / 建议修复没可复现验证 / 环境失败看起来像代码缺陷 / 审查证据散落在 log + patch」 ——RepoPilot 把这 6 个痛点合并成一个闭环：Issue → test → 失败复现 → 修复 → 独立验证 → 报告；修复前冻结测试 是「测试身份不被修复改动」的工程化形式——避免「修复同时改 test 让 test 永远 pass」的作弊；候选必须通过独立 Docker runner 执行 + policy 重检 是「修复不是 self-claim」的工程化形式——独立进程跑测试 + 独立验证项目规约；环境失败有界重试 + 不稳定证据阻断 是「环境问题不污染代码判断」的工程化形式——避免「环境 race condition」被当成「代码 bug」修；维护者保留 merge 决策 是「人机协作最终 gate」的工程化形式——agent 提议 + 维护者合并，避免「AI 自动 merge 引入 bug」；对企业：CISO / 合规团队可在不绑定 SaaS 前提下用 AI 做仓库级 Issue / PR 验证迭代；对开源维护者：可处理「我自己维护不过来的 Issue / PR」+ 保留最终 merge 决策；对小团队：可作为「AI 同事」处理 backlog + 维护者合并。
  • 架构亮点： OpenAI Codex SDK + 自托管 worker ——Codex SDK 是 OpenAI 官方 SDK（与 Codex CLI 同一模型），自托管意味着数据不外传；独立 Docker runner ——验证与修复分离的工程化形式，Docker 隔离环境避免污染；修复前冻结测试 ——tests are frozen before repair 是「测试身份不变」的工程化形式——避免「agent 修代码同时改 test 让 test 永远 pass」；候选必须保留测试身份 + 通过独立执行 + 通过 policy 重检 ——三件套：测试身份不变 + 独立进程执行 + 静态规则 + 语义审查；环境失败有界重试 ——避免「环境 race condition」无限重试；不稳定 / 不完整证据阻断自动修复 ——「证据不全不修」的工程化形式；本地 JSON / Markdown 报告 ——findings + test outcomes + repair attempts + publication state 四类记录可独立审查；AGENTS.md 项目规约静态规则 + Codex 语义审查 + 引用规则 + 代码证据 ——三件套证据链 + 项目规约集成；README 明确范围声明——「broader autonomous iteration is a project vision; unattended product development, merging and deployment are not current capabilities」是「严肃边界声明」的关键工程化形式；MIT + TypeScript + 378 KB ——可独立部署的中等规模迭代引擎。
  • 价值判断： 它解决的是「AI Coding Agent 仓库级 Issue / PR 验证迭代闭环」的真痛点；MIT + TypeScript + 378 KB + OpenAI Codex SDK + 独立 Docker runner + 冻结测试 + 三件套证据链 + 范围声明 是「严肃 AI Coding 工具」形态；95⭐ / fork 6 / fork/star 6.3% / 1 天 反映严肃工程信号（fork/star 6.3% 与昨日 thruwire/foreman 6.4% 接近，反映「严肃 AI Coding 工具」早期 fork 率特征——明显高于纯 awesome-list 但低于企业级合规工具）；决定长期价值的是「OpenAI Codex SDK 稳定性 + 独立 Docker runner 在多 OS / 多语言项目上的通用性 + 冻结测试机制的可靠性 + 维护者接受度」 ——Codex SDK 变更 / Docker runner 在复杂 monorepo 的可靠性 / 冻结测试是否被新 test 绕过 / 维护者是否愿意信任 AI 提议是关键；对企业：可作为「AI Coding 同事」处理 Issue / PR + 维护者最终 merge gate；对开源维护者：可处理 backlog + 保留最终 merge 决策；对小团队：可作为「AI 同事」分摊 backlog。

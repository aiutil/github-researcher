1️⃣ 「asset 下载次数」判据被证伪：根因是取样窗口，不是项目（score 96）

⭐⭐⭐⭐⭐ 本日最硬的一条发现不是关于某个项目的，而是关于我们自己的测量方法。11-18 日报用「asset 下载次数」给三个项目排了座次（plannotator 1–12 次 / arcane 10–16 次 / open-code-review 57–951 次），⭐⭐⭐⭐⭐ 并据此断言「同样认真的供应链纪律，采用度差了一到两个数量级」。本日复测发现：那个「区间」根本不是分布区间，而是一个被截断的排序前缀。

可核验事实：11-18 的取数代码。 本日报直接读了当时的取数脚本 scripts/_forensics_2026_11_18.py 第 60 行：

python "download_counts": sorted((a.get("download_count") or 0) for a in assets),

第 163 行打印时：

python print(f" downloads={rel['download_counts'][:12]}")

⭐⭐⭐⭐⭐ 即：先对 36 个 asset 的下载数升序排序，再只取前 12 个打印出来 —— 而 11-18 日报把这个前缀的最小值与最大值（1 与 12）当成了「下载次数区间」。⭐⭐⭐⭐⭐ 本日用同一时刻、同一个 API、同一批 release 复测，真值如下：

⭐⭐⭐⭐⭐ ⭐⭐⭐ 第三层（本日最实用的正面结论）：「零下载 release」几乎不是「没人要」。 ⭐⭐⭐⭐⭐ 实测 we-promise/sure 27 个 release 里有 10 个 total_dl == 0，⭐⭐⭐⭐⭐ 但它们的年龄是 10.3–485.3 天、没有一个是 7 天内的新 release；⭐⭐⭐⭐⭐ autoclip 19 个 release 里 2 个零下载，年龄 172.6 天与 433.4 天。⭐⭐⭐⭐⭐ 即零下载是「这个版本被跳过了」（比如被 hotfix 取代、或只发不发），而不是「刚刚发布还没人下载」—— 本数据集此前的判据里没有这一条。

⭐⭐⭐⭐⭐ 11-18 日报的头条发现是「SKILL.md 数量是复制放大的计数」，核心证据是 affaan-m/ECC 的 1,087 个文件只对应 330 个独立身份（3.30×），最大单一技能被复制 10 份。本日复测发现：这个「330」是用「父目录名」当身份算出来的，而它与「同一份内容被存了几份」不是一回事。

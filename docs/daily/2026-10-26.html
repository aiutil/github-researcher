今日重点趋势（按排名）

趋势 1：同一个 CVE 上，两条方向相反的检测路线——主动探测与离线盘点，都把「不确定」设计成独立的输出状态（趋势分 91）

本日最重要的观察不是「又多了几个 PoC」，而是两个由安全厂商自己写的检测工具，在同一 CVE 上选择了互斥的路线，而它们各自都拒绝把「测不出来」说成「安全」。

⭐ assetnote/node2shell-scanner（18.5 小时 48⭐ ⑂6，fork/star 12.5%，subs 1，oi 0，Python，MIT，11 KB，Organization assetnote（创建于 2018-01-09，40 个公开仓库，995 followers），仅 1 个 commit，contributors API 返回 1 人，releases API 返回 0 个）

它是主动式的：README 明写「The scanner sends four one-byte controls to learn how the endpoint handles valid Brotli JSON, malformed Brotli, requests without a JSON content type, and unsupported encodings. It then streams a 23,068,764-byte Brotli probe and repeats the valid control.」

⭐ 而它的判定条件是三条同时成立，而不是「探测成功 = 漏洞」：

A target is reported vulnerable only when the full probe reaches the valid route-response class, the malformed-response class is distinct, and the final control confirms the endpoint remained stable. This matches Assetnote's internal postmodule detection logic and does not execute a command.

这三个条件对应三个可被证伪的断言：① 探针真的被解码到路由（而非被中间层吞掉）；② 畸形输入的响应与之相异（而非两者都返回同一个 200 空体）；③ 端点没有因探针而崩掉（排除「打崩了所以看起来不一样」）。

⭐⭐ 代码层面这些约束是硬编码的、可逐行核验的：scanner.py 共 1,163 行，其中 PROBE_BYTES = 23_068_764、PROBE_REPETITIONS = (1 << 21) - 1、PROBE_PREFIX / PROBE_UNIT（f5a8473dea518f7ad4a31e）/ PROBE_SUFFIX 三段拼接，并有一条自校验断言保证拼接长度恰好等于 PROBE_BYTES；四个对照请求在 request_evidence() 里被固定登记为 "ff (Content-Encoding: br; no Content-Type)" / "3b (Content-Encoding: br; Content-Type: application/json)" / "ff (Content-Encoding: br; Content-Type: application/json)" / "x (Content-Encoding: x; Content-Type: application/json)"；比较函数 same_exact() 要求双方 error is None、未截断、状态码相同、content-type 相同、body 逐字节相同（另有仅比状态码的 status 模式）；scan_url() 在多路径场景下只要有一个路径判为 vulnerable 就立即返回 true，否则回退到第一个「非 inconclusive」的结论。

⭐⭐⭐ 而它对「测不出来」的处理是本日报最值得抄的一处：

输出态 触发条件 证据
vulnerable: true 三条判定同时成立 完整请求/响应证据（含被脱敏的敏感头）
vulnerable: false 探针未到达有效路由且响应类相异 同上
vulnerable: null / verdict: INCONCLUSIVE 网络错误、超时、无响应等 result["error"] 记原因

退出码是 raise SystemExit(1 if vulnerable_count else 0)——即「没有发现漏洞」以 0 退出。 ⭐ 这个设计与本日报记录的 mcreplay 的 0/1/2/3 退出码、brotli-checker 的 0/1/2/3 退出码属于同一族：把「判定结果」编码成 CI 可断言的离散状态，而不是一句警告。

⭐⭐⭐⭐ 而它对自己造成的网络影响是写进 README 的可复算数字，不是免责套话：

Each tested endpoint receives five one-byte requests and one 23,068,764-byte probe. The probe uses Expect: 100-continue, so a proxy can reject its advertised size before the body is uploaded.

⭐ Expect: 100-continue 这一行是真正的工程细节——它让代理可以在上传 23 MB body 之前就按 Content-Length 拒绝该请求，因此这个「23 MB 探针」在有代理的环境里可能根本不会上传。这是把「检测器的副作用」主动交还给部署方的网络层去裁决。

⭐ trailofbits/brotli-checker（2.3 天 44⭐ ⑂3，fork/star 6.8%，subs 0，oi 0，Python，MIT，6,858 KB，Organization trailofbits（298 个公开仓库，3,297 followers），26 commits，contributors API 返回 2 人 + 1 bot，releases API 返回 3 个）

它是离线式的，与前者的主动探测完全相反：README 明写「The scanner finds suspect parts; Trailmark helps show how the code connects. The assistant checks whether those connections apply to the running app.」

⭐⭐ 而它最有价值的一段，是 SKILL.md 里把结论拆成两级的那一句：

Finding vulnerable source establishes source containment. Build selection, shipment, attacker-controlled input reaching that decoder, and exploitability are separate conclusions. Keep a result for each copy; one fixed copy cannot clear other copies.

⭐ 这四个被拆开的结论——「源码里有受影响的副本」/「被构建选中了」/「被发布了」/「攻击者可控输入能到达它」——正是 10-25 记录的 mcreplay 把 33 个官方工具逐条列 A?/B?/C?/W 等级的同一族做法。

⭐⭐⭐ 它的退出码表是本日报见过最完整的「四档判定」：

Exit 含义（docs/usage.md 原文）
0 Reported items meet a known source or upstream-version fix rule, with no recognized scan gaps.
1 Affected source/code or potentially affected source/version evidence was found.
2 Invalid arguments or code-reference catalog.
3 Review is needed: no matches, unresolved candidates, fixed-code-only evidence, or scan gaps.

⭐⭐⭐⭐ 而紧跟着这两行，是本日报今日最该抄的一句：

Affected evidence takes precedence over gaps: exit 1 can include incomplete coverage. A fixed copy does not clear another, and exit 0 does not establish that the running app is fixed.

「exit 0 不等于运行中的应用是安全的」——这是对「扫描器返回 0 就万事大吉」这个最常见误用的正面否定。 ⭐ 本日报已连续多日记录「边界要写进可核验的位置」，而这一句是把它写进了退出码的语义本身：0 不是「安全」，0 是「在我能看到的范围内没有命中，且没有已识别的扫描盲区」。

⭐⭐⭐⭐⭐ 它对「上游已经修了」这件事的处理，是本日最值得单独指出的技术细节——references/advisory.md 明写：

The CNA record has disjoint Brotli version ranges. A single comparison against 1.2.1 would incorrectly warn on fixed 1.0.10 and 1.1.1. Other Node branches, forks, prereleases, and custom builds need decoder-specific evidence. The helper does not assert that every historical Node release contains an affected decoder.

即：它拒绝用一个版本号覆盖不连续的受影响区间。 其版本表逐行列出：Brotli 1.0.3–1.0.9 → 1.0.10；1.1.0 → 1.1.1；1.2.0 → 1.2.1；Node 22.x → 22.23.4；24.x → 24.22.1；26.x → 26.12.1（本日报已逐条核验这些上游版本号与发布日，全部属实）。它还明写「An older version can contain a vendor backport… Do not compare distro revisions as upstream SemVer or transfer one provider's fixed revision to another」与「An updated host package does not establish the state of a container, native extension, or statically linked executable」。

⭐⭐ 而 fingerprints.json 把「指纹是怎么来的」也结构化了：schema_version / cve / verified_on: "2026-10-23" / upstream_fix / inventory_revision / verification（原文：「Fetched upstream releases and pinned inventory source; verified Git blob and SHA-256, and compared block-switch handling with upstream fix. Source-file evidence only.」）+ 逐条指纹的 sha256 / git_blob / size / state: "vulnerable" / sources。⭐ verified_on 是一个日期而不是一个「最新」标签——即它承认这份快照会过期，并在 SECURITY.md 里明写「Advisory rules and compiled references are snapshots, and an old checkout does not automatically receive new guidance」。

⭐⭐⭐ 本日两者最值得并置观察的一点：它们连「同一次 CVE」的入口都不相同。 scanner 走 HTTP 网络面（一个 URL + 四个对照 + 一个探针），brotli-checker 走 文件系统与源码面（目录、依赖、应用包、已解包的容器文件系统、源码指纹、ELF 二进制反汇编）。⭐⭐ 而 brotli-checker 明确划出了自己够不到的地方：「HTTP headers cannot establish the decoder's patch status」「Do not send malformed streams or exploit probes」——即它放弃了主动探测，转而要求用户拿本地访问权限或服务器访问权限。

⭐⭐⭐⭐ 而两者的边界声明合起来，恰好构成今日这条趋势的完整形状：

scanner：我能在网络上证明「这个端点的解码器可被触发到越界写」，但我无法证明它可被利用（does not execute a command）。 brotli-checker：我能证明「这个部署里有受影响的解码器副本」，但我无法证明它可达（a fixed copy does not clear another；HTTP headers cannot establish patch status）。

⭐⭐⭐⭐⭐ 「主动探测能证明可达但不能证明可利用，离线盘点能证明存在但不能证明可达」——本日两个工具加起来仍然没有回答「这台机器现在安不安全」，而两个工具都把这个缺口写进了自己的输出状态，而不是留给读者去脑补。这才是本日最值得记的东西。**

风险与机遇

机会

  1. ⭐⭐⭐⭐ 立刻可用且证据完整的两件：brotli-checker（MIT，3 个 release，纯标准库的独立扫描器 + uv 做源码发现）与 scanner（MIT，仅 h11 + tqdm 两个依赖）。 ⭐ 二者都在各自 README 的第一屏就写清了边界，而边界之内是可用的。

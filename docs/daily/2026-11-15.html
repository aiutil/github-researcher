最值得关注的方向

⭐⭐⭐⭐⭐ 方向一：判据的「可被自动化制造性」检验。 本日三个发现（auto-commit 工作流 / 加密载荷撑大体积 / 人工订阅农场）指向同一个方法论升级：任何单点信号在使用前，都必须先回答「这个信号能否被一个自动化脚本或一次人工操作单独制造？」 README 文本可以，commit 数可以，push 频率可以，仓库体积可以，subs 数可以，甚至 fork 数也可以。⭐⭐⭐⭐⭐ 真正难伪造的，是需要真实工程投入才能产生的信号 —— 比如 hikaku-extension 的 87 个文件与 docs/MODELS.md 里的 548 张 Reddit 基准、kraken-mount 的 19 个 open issue、ScanDot 的 CI 配置与 build.gradle.kts 里的 lint { abortOnError = true }。

⭐⭐⭐⭐⭐ 方向二：把「不确定性」写进产物，而不是写进 README。 四个真项目里有三个做到了同一件事，但层次不同：hikaku-extension 把它做进数据结构（declaration 与 estimate 两条独立路径）；ScanDot 做进文档结构（第二段就划清手机端与工作站端）；kraken-mount 做进规格结构（DESIGN.md 的「Supported sources (nothing else)」）；islandcn 做进协作结构（AGENTS.md 的路径归属与许可约束）。⭐⭐⭐⭐⭐ 共性是：边界被写在了会被机器读到的地方，而不是只写在会被机器跳过的散文里。

⭐⭐⭐⭐⭐ 方向三：分发协议正在取代 clone。 islandcn 走 shadcn registry（/r/island-core.json）、hikaku-extension 走 Chrome/Edge/Firefox 与 AMO 三条发布通道并提供 hikaku-bench 独立基准仓库、ScanDot 走 GitHub Release 的 preview APK、kraken-mount 走 GitHub Release 的 .elf + 仓库内 ps5/build.sh（需 Docker）。⭐⭐⭐⭐⭐ 这与 11-13 记录的 open-orange 把 conformance 结果做成逐日可 diff 是同一条线索：产物应该可被机器消费与复现。

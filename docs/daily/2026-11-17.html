风险与机遇

⭐⭐⭐⭐⭐ 风险一：占位仓库指纹一旦被广泛使用，投放方会立刻换结构。 本日报的对照实验证明这条判据很强（100% vs 6.25%），⭐⭐⭐⭐⭐ 但正因如此它也会被针对 —— 改掉占位仓库只需一次自动化操作。⭐⭐⭐⭐⭐ 这不削弱它的价值：它至少把「发现这类投放体」的成本从「逐仓库读 README」降到「一次 owner 列表请求」，⭐⭐⭐⭐⭐ 而且它能被历史数据回溯 —— 本日报已经用它把本日族和 11-15 族连成同一套流程。**

⭐⭐⭐⭐⭐ 风险二：养号制度化让所有基于时间的判据同时失效。 本日三批账号分别养了 1、2、5 个月。⭐⭐⭐⭐⭐ 11-16 日报已经因为「账号当天新建」不成立而作废了那条判据；本日的证据说明投放方不是「碰巧不当天新建」，而是「刻意提前建好」。⭐⭐⭐⭐⭐ 推论：判据库必须以结构与行为为主键，时间只能作为辅助排序。

⭐⭐⭐⭐⭐ 风险三：把「release 多」一刀切判为造假，会误伤真正在做发布纪律的项目。 ffmpeg-skill 有 100 个 release、0 asset、release commit 只改元数据 —— ⭐⭐⭐⭐⭐ 只看这三个数字，它和 11-16 的 steam-library-bridge 几乎一样。⭐⭐⭐⭐⭐ 但它的每个版本背后都有一个触及源码的父 commit。⭐⭐⭐⭐⭐ 如果不追到「tag → commit → diff」这一层，就会把一个每天发布 2–3 次、每次都带真实功能的项目误判为造假。

⭐⭐⭐⭐⭐ 风险四：Skill 生态的「自举」正在制造评估真空。 SkillEvaluator 的用户自己报出「Tier 1 安全扫描只扫 bundled skills，hooks 和 bin/ 永远不被扫描」⭐⭐⭐⭐⭐ ——即当前最权威的 Skill 评估器之一，存在一个已知且未修的扫描盲区。⭐⭐⭐⭐⭐ 同时 17 个仓库里只有 4 个带 ≥3 套 harness 清单，安装协议没有标准 —— ⭐⭐⭐⭐⭐ 这意味着一份 Skill 会被装到哪、怎么装、装到哪个目录，目前仍然不统一，而 Derive Claude root source in packaging 这类 commit 说明差异会渗进打包逻辑。

⭐⭐⭐⭐⭐ 风险五：本日族把「游戏外挂」当载荷名，但载荷本身未核验。 族内 8 个仓库的 README 都列出了 aimbot / ESP / radar / 无敌 等功能表，⭐⭐⭐⭐⭐ 但本日报未下载任何载荷，因此「这些功能表描述的是否与实际载荷一致」完全未知。⭐⭐⭐⭐⭐ 同样未知的是 modbay.live 是否托管了其他品类 —— 本日报只在这 9 个 README 里看到它。

⭐⭐⭐⭐⭐ 机遇一：「占位仓库」可以直接做成一零成本巡检项。 一次 users/{owner}/repos 请求 → 检查是否存在 README 恰好等于 # <仓库名> 的单 blob 仓库。⭐⭐⭐⭐⭐ ⭐⭐⭐ 更好的用法是反查：拿到一个可疑仓库 → 拉它的 owner 的全部仓库 → 若发现占位仓库，则该 owner 的其他仓库全部进入复核队列。⭐⭐⭐⭐⭐ 这比逐仓库读 README 快一个数量级。**

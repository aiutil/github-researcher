证据边界： 本日全部元数据取自 2026-10-29T22:02Z–22:30Z 之间的多次 GitHub REST / Search API 调用（gh CLI 认证），字段包括 stargazers_count / forks_count / subscribers_count / open_issues_count / size / language / license.spdx_id / topics / created_at / pushed_at / owner.type / description / homepage / archived；另用 git/trees/HEAD（根树）与 ?recursive=1（检查返回的 truncated 字段）、commits（用 Link 头 rel="last" 取精确总数）、contributors、releases、issues、contents/{path}（取 .sha 与 Accept: application/vnd.github.raw 原文）、users/{owner}。 ⭐⭐⭐ 关于「增速」表述： stargazers 端点对本 token 持续返回 404，因此星标时间分布无法核验，所有「涨了多少」都是两次快照之间的总量差，不是当日新增，也不能读作「用户数」。本日报在明确标注快照时刻的地方给出差值，未标注处只给当前值。 ⭐⭐⭐ 关于本日对投放载荷的处理纪律： 本日报下载了 https://git-software.cc/ps/Setup.ps1（8,899 字节）并仅做静态文本分析，从未执行、未解密其载荷。本日报不复制其载荷内容，只记录其结构性特征（PSObfuscator 风格的封装：Base64 → 长度与对齐自检 → HMAC-SHA256 完整性校验 → AES-256-CBC 解密 → gzip/deflate 解压 → Parser::ParseInput 语法校验 → GetScriptBlock()）。本日报无法判断该脚本最终会执行什么，本日报也不做这个判断。 ⭐⭐ 关于「同构簇」的判定方法： 本日报今日不再只依赖文件数/体积/owner 名/创建时间窗这类间接统计，而是逐个取 contents/README.md 原文并检索投放指令字符串，并对样本中的簇取 contents/README.md 的 .sha（git blob 哈希，内容寻址） 做比对。⭐ 而本日必须说清一个方法论修正：blob SHA 相同是「同一份内容被复制」的强证据，但本次簇内 README 的 SHA 各不相同（因为只替换了软件名），所以「blob SHA 相同」这条判据本日不适用 —— 真正适用的是「同一条投放 URL 在 N 个不同 blob 中出现」。 ⭐ 关于「独立路径」的判定： 本日报对四个静态重编译项目逐一检索了对方项目名（ultratears / totk-pc-recomp）与共同上游名（LASRecomp / MacNativeGames / SavageWindRecomp），核验结果是：ultratears 的 README 未提及 totk-pc-recomp，totk-pc-recomp 的 README 提及 LASRecomp / MacNativeGames / d2r-mobile / nxnative / SavageWindRecomp / Ryujinx / deko3d / hactool 但未提及 ultratears。 即两个打同一款游戏的项目互不知晓；但它们都建立在同一批上游项目之上——这是「共享上游 ≠ 共享代码」的区分，本日报明确记录。

今日重点趋势（按排名）

趋势 1：静态重编译在同一天出现四个互不相识的实现，其中两个打同一款游戏却走完全不同的技术路线（趋势分 94）

⭐⭐⭐ 本日最重要的观察不是「哪个移植更强」，而是：同一天之内，四个互不相识的团队，各自把「把主机游戏代码变成原生 PC 程序」这件事推进到了可运行状态，而其中两个在做同一款游戏——却既没有使用彼此的代码，也没有承认对方存在。

⭐⭐⭐⭐ 这为什么重要？因为它是本日报见过最干净的一次「技术难度被独立确认」样本。 本日报此前记录过多次「两个互不相识的项目撞上同一个核心难度」（10-23 的 UniXNU 与 Macintosh 撞上 16 KiB→4 KiB 页表翻译与 Apple 私有输入处理；10-25 的 KohakUnlock 用一次真机失败换来了「分区号是易变量、GUID 是稳定标识」这条纪律）。而今日这一例的分量更重，理由是它有三条独立的旁证同时成立：

  1. 四个项目互不知情（本日报逐一检索了对方项目名，结果见上方证据边界）；
  2. 其中两个做同一款游戏却走完全不同的图形与 CPU 路线（见下表）；
  3. 四个项目的 issue 区都在收「真实用户按文档操作后失败」的报告，说明它们都进入了真实使用阶段，而不是停在 demo。

⭐⭐⭐⭐ 而 totk-pc-recomp 的架构文档是本日最值得单独读的一份 —— 因为它是本日报见过最诚实的「我用了谁、没用什么、为什么」三段式拆解：

docs/architecture.md 原文：

MacNativeGames cannot run on x86-64 as it is: its CPU path executes ARM64 code natively. LAS Recomp's host only covers what Link's Awakening calls. The port takes the CPU half from LAS Recomp and the game half from MacNativeGames, and writes the parts neither has: a lifter that scales to TotK, and a Vulkan back end for the NVN front end.

⭐⭐⭐⭐⭐ 「取 LAS Recomp 的 CPU 半边、取 MacNativeGames 的游戏半边、自己写两者都没有的部分」—— 这是一句把「复用」拆到零件级的工程声明，而多数项目只说「基于 X 项目」。

⭐⭐⭐⭐⭐⭐ 而同一份文档里还有一条本日最值得抄的供应链纪律：

jump tables resolved by our own symbolic pass instead of Unicorn, which keeps GPL code out of the shipped generator

⭐⭐⭐⭐⭐⭐⭐ 即：它没有使用 Unicorn（GPL），而是自己写符号遍历来解析跳转表 —— 理由是「把 GPL 代码挡在交付产物之外」。 本日报连续多日记录「许可元数据问题」（10-22 php2shell-poc、10-23 UniXNU/Snapintosh、10-25 raven 的 GPL 重许可），今日这一例是本日报第一次见到「因为许可原因而选择不依赖某个知名工具」的设计决策。 ⭐⭐ 这比事后补一份 LICENSES.json 更难，也更彻底。

⭐⭐⭐⭐⭐⭐⭐⭐ 而它的需求声明同样把「跑不起来」的成本写在前面：

Requirements: Windows 10 or later, an x86-64 CPU with AVX2, a GPU with Vulkan 1.3 and VK_EXT_external_memory_host, about 36 GiB free during setup (20 GiB after).

⭐⭐⭐⭐⭐⭐⭐⭐⭐ 36 GiB 的安装期占用 + AVX2 + Vulkan 1.3 + VK_EXT_external_memory_host —— 这三个条件共同决定了「谁能用」。 ⭐⭐ 而「哪些人不能用」正是本日这批项目共同的隐含边界：totk-pc-recomp 的 32 条 issue 里，#28 Can't finish the install process? 明确停在「Somewhere during \"Translating code to C\"」、#31 Vulkan out of device memory (-2) on AMD Radeon 610M、#34 GPU Timeouts —— ⭐⭐ 即用户是「照文档做了、在第 4 步断了」的具体人，而不是点赞的人。

⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐ 而这正是本日报今天最想说的一句：在这批静态重编译项目里，issue 区的信息密度与 star 数完全解耦 —— ultratears 只有 3 个 commit、424⭐、30 条 issue，其中 #37 Shader step: 82 of 28,769 vertex shaders fail to translate 与 #34 Black "shadow box" ahead of Link: shadow compares need Dref clamped to 0..1 (D16 stored as D32F) 是具体到 API 语义的技术报告，而 #29 error in step 4 when compile the dumped game 是具体到步骤编号的失败点。

⭐⭐ interplains/Zero-Breach-Toolkit（3,543⭐ ⑂381 · subs 33 · 55 commits · 14 个 release · Apache-2.0 · 1,113 KB）

⭐⭐⭐⭐ 它最硬的一处，是把「我的扫描器干净」与「你安全」这两件事明确切开—— 而且是用三个并列的句子切开的：

  • Read-only. It does not modify source evidence or system settings. It writes only temporary database snapshots and the reports you ask for.
  • No network requests during a scan. It never looks up spyware addresses and has no upload feature. Python network calls are blocked and redirected paths are refused. This is not an operating-system network sandbox; see PRIVACY.md.
  • States its limits. Every report says what was found, how strong the evidence is, and what could not be checked. A clean result is never presented as proof that you are safe.

⭐⭐⭐⭐⭐ 而 PRIVACY.md 里那句自我设限是本日报今日见过最诚实的一处技术声明：

These guards are not an operating-system network sandbox: POSIX network mounts and concurrent filesystem changes remain limitations. Use operating-system network isolation when strict offline execution is required.

⭐⭐⭐⭐⭐⭐ 即：它明说「我的『无网络』保证有已知的逃逸口，请用操作系统级隔离来补」。 ⭐⭐⭐⭐ 这与本日报 10-28 记录的 nyxis「a passing integration test is never a substitute for a formal proof」是同一条纪律的两种形态 —— 两者都在说「我的保证有边界，边界我写下来了」。**

⭐⭐⭐⭐⭐⭐⭐⭐ 而它的验证路径是本日报今日最值得抄的一份文档 —— docs/VERIFYING.md 给出两条互相独立的验证，并明确要求「Use both」：

① 签名验证（对照一个你已经信任的密钥）： gpg --show-keys --with-fingerprint archivegenocide-signing-key.asc gpg --import archivegenocide-signing-key.asc gpg --verify SHA256SUMS.txt.asc SHA256SUMS.txt sha256sum -c SHA256SUMS.txt 完整指纹写死为 C24E C92B 12D6 670A 2516 065F 9B4D 5754 99AF A53C，并附「compare that fingerprint with [ArchiveGenocide's verification page] or another record you already trust」，还明写「Never ignore a fingerprint mismatch or a failed verification.」。

② 自行复现构建（不依赖发布者）： git checkout v0.1.13 python build/bundle.py sha256sum dist/zero-breach-toolkit.py 原文：「The build is deterministic, so a mismatch means something is wrong, not merely different.」以及「Running from source is the other half of the same idea: nothing is compiled, and every line the tool executes can be read in the clone.」

⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐ 而这份文档里最反直觉、也最值得单独抄走的一段，是「为什么没有代码签名」：

Why there is no code signature There is no signed Windows release, and none is planned while the project stays anonymous. Code-signing certificates require a verifiable legal identity, and every signing route, including SignPath Foundation, expects named, publicly identified maintainers and approvers. This project does not have them, by choice. It claims no certificate, signing service or signed binary, and asks nobody to trust a downloaded signature.

⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐⭐ 即：它没有签名二进制，于是它给的是另一条路（可复现构建 + 分离签名 + 指纹对照 + 「从源码运行时没有编译，每一行都能在 clone 里读」），并且明确说明「我们没有代码签名」这个缺口，而不是留白或假装有。 ⭐⭐ 本日报认为这是本日报见过最完整的一次「在受限条件下仍把验证路径做到可复算」的处理。**

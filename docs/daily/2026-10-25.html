今日重点趋势（按排名）

趋势 1：第三方 API 生态的第一周——真问题不是「怎么调用」而是「怎么让输出不会悄悄漂移」（趋势分 90）

YoyoLin008/mcreplay 的 star 数（116）在本日四个项目里不是最高的，但它处理的问题类型在本日四个项目里是唯一的：其他三个都在做「把一个东西做出来」，只有它在做「怎么让一个已经存在的东西的变化能被机器发现」。

这个问题的来源是可核验的。 麦当劳中国官方 MCP（https://mcp.mcd.cn）的官方仓库 M-China/mcd-mcp-server（246⭐ ⑂9，subs 1，组织 M-China 创建于 2025-12-25T01:37:41Z）经 ?recursive=1 全树查询确认只有两个文件：README.md（18,722 字节）与 README_EN.md（19,845 字节）——没有实现代码、没有机器可读的输入输出 schema、没有可运行的 SDK 示例。官方 README 本身是好的（写明了接入地址、Streamable HTTP、Token 申请流程、600 次/分钟限流与 429 错误码、以及「未经书面授权不得商业售卖或引流变现」的条款），但它是一份文档，不是一个契约。

⭐ 而这正好是 mcreplay 的切入点：它先做了一件反常的事——把自己的知识边界写在最前面。

docs/capability-matrix.md 的第一行就是：

Research date: 2026-10-24 UTC. No authenticated calls were possible: this session has no MCP token binding. Terminal connectivity recovered after the initial research; official authenticated calls remain unverified. All reliability judgments below are provisional, not production certifications.

这段话包含三个独立的诚实声明：① 那次研究没有拿到 token，所以官方调用未被验证；② 恢复的只是终端连通性，不是鉴权；③ 下面所有可靠性判断都是暂定的，不是生产认证。 然后它把 33 个官方工具逐条列出并给等级：A?（低复杂度但未测）/ B?（动态或用户数据，需要 schema、空值与错误处理）/ C?（有报告的局限或复杂上下文规则）/ W（真实账号写操作，无独立审批不可测）——并明写「None means production verified」，即没有一个等级意味着已通过生产验证。

Deep Dive 1：YoyoLin008/mcreplay（本批信息密度最高的单项目，也是「热度不等于价值」的第一个反例样本）

项目定位。 把一次麦当劳 MCP 查询变成可复现的本地结构测试，1.2 天 122⭐ ⑂6（fork/star 4.9%），Python，GitHub license.spdx_id 为 NOASSERTION 但 LICENSE 首行为 MIT License（尾部两段自有声明），1467 KB，subs 0，oi 0，仅 8 个 commit，contributors 1 人。

为什么它值得比它的 star 数更多的注意力。

因为它是本日唯一一个「把不知道自己写成了产品的一部分」的项目，而它面对的是一个真实的、正在发生的 API 契约漂移问题。

具体地说：官方 MCP 服务只有一个 README，没有 schema。 一个第三方 Skill 依赖 calculate-price 返回 price（分）、discount、takeWayList、enjoyed，依赖 query-meal-detail 返回 rounds[].choices[].isDefault/quantity，依赖 list-nutrition-foods 返回 name/kcal/protein/fat/carb/sodium/calcium。只要上游改了任何一个字段的类型或封装，这些 Skill 就会静默失效——而 issue 16 已经报告了「wrong code→productCode mapping silently yields price0. Missing/zero price must not be treated as free」。 这是一个已经被真实用户踩到的问题。

mcreplay 的做法是：让「上游改了」变成一个 CI 里会失败的事件。

它的技术亮点：

  1. ⭐ 双路径证据，且两份都留着。 capability-matrix.md 全部标注 provisional；LIVE_VERIFICATION.md 记录三次真实查询的逐项耗时与响应形态。读者能同时看到「我当时知道什么」与「后来验证了什么」。
  2. ⭐ 证据分级到字段级。 S:（二手捕获）/ O:（官方 issue 原文）/ 官方文档描述三档，且明写二手来源的用法限制（「Do not copy this project's implementation or make our own live-test claims from it」）。
  3. ⭐ 退出码即契约。 0 / 1 / 2 / 3 四档，让「破坏性变化」成为 CI 的判定条件。
  4. ⭐ 结构比较覆盖两个编码面。 官方响应同时有「Markdown 后缀 JSON」与 structuredContent，而它的类型变更实验同时定位了两处变化——说明它不是只扫一个面。
  5. ⭐ 真实值不出本机。 业务值替换为占位符；接收文件权限 0600；仓库附带的 official-20261024.json（87,252 字节）经 Gitleaks 8.30.1 校验无泄露。
  6. ⭐ 逐个检视 10 个对手并公开其弱点，同时明写「authors' claims, not independently rerun」与「This is an inspected sample, not a census」。
  7. ⭐ QA 记录完整到可以当模板用：120 项测试（全部合成输入）+ SDK 子进程 19 项（含 25 秒截止）+ ruff + 构建 + 独立环境安装 + pip check + Gitleaks + 对锁文件全部 29 项依赖跑 pip-audit + CI 覆盖 4 个 Python/系统组合。
  8. ⭐⭐ 它自己写下了本日报最需要的结论：参赛样本里有真实实现，把整个生态说成「薄 AI 包装」是不准确的。

风险。

  • ⚠️ subs 0 + contributors 1 人 + 仅 8 个 commit = 一个个人项目在赛事截止日当天的一次集中发布。 没有任何外部贡献者痕迹，也没有外部复现记录。
  • ⚠️ 它的能力矩阵基于未验证的官方文档描述与第三方捕获，「33 个工具」的必填参数没有一条来自官方 schema。 它自己写了这一点（S: 标记 + 「not an output JSON schema」），但读者容易在摘要层丢掉这个标记。
  • ⚠️ 平台限制：Python 3.11+、Linux 或 macOS（无 Windows）；只实现了 3 个工具中的契约回归。
  • ⚠️ 它依赖官方服务的限流额度（600 次/分钟），而官方服务规则第 3、6 条限制自动化访问——这正是它选择离线优先的根因，也是它验证路径的天然边界。
  • ⚠️ license.spdx_id 为 NOASSERTION（尽管 LICENSE 文件是 MIT 且有额外条款）——依赖 license 扫描器的工具会给出错误的默认答案。
  • ⚠️ 官方 MCP 的许可条款禁止未经书面授权的商业使用——mcreplay 的 LICENSE 尾部自己也写了这句（「This license grants no permission to use the official service commercially or outside its rules」），但这意味着依赖该服务的任何商业产品都需要单独审视许可边界。

是否值得跟踪。 值得，且跟踪方式应是「它是否被赛事之外的人采用」，而不是「它能不能获奖」。 观察重点：(1) 是否出现第一个外部 fork（fork/star 4.9% 说明还没到）；(2) 它的工具覆盖是否从 3 个扩展（这是它能力边界最直接的指标）；(3) 是否有人把它的退出码接进 CI 并公开（这会验证「契约回归」这个模式是否真的有用）；(4) 赛事结束后（10-25 23:59 截止）的存续情况——特别是那 122 个仓库里有多少会因为许可或无差异而消失；(5) 官方是否发布正式的 schema（那会改变它的核心价值）。

Deep Dive 2：mirkobrombin/raven（本日最值得警惕的元数据陷阱，也是最扎实的一个工程样本）

项目定位。 在 Linux 上跑 Windows 应用，不用虚拟机、不用 winetricks、不用 DLL 覆盖；但它的 created_at 是 2026-10-24T17:13:42Z——这是一个改名仓库的时间戳，而它实际有 653 个 commit、最早可追到 2025-09-05。

为什么它值得比它的 star 数更多的注意力。

因为它同时提供了两样东西：一份工程上相当扎实的兼容层样本，和一个「created_at 会骗人」的活教材。

它的技术亮点：

  1. ⭐ 直接执行 + 沙箱隔离 + API 全量自实现。 「The program's code runs directly on your CPU, inside a sandbox where it cannot reach Linux. Every call it makes to the system is answered by Raven, which plays the part of the Windows kernel and its services.」
  2. ⭐⭐ 四段 25% 的兼容评分——把「装得上 / 起得来 / 有主窗口 / 能完成真实工作流」拆成可累加的阶段，让「VLC 25%」和「Notepad++ 100%」成为可比较的事实而非印象。
  3. ⭐⭐ 交替运行的 benchmark 设计。 四轮交替 Raven / Wine / Soda，理由写明：「so a change in machine load weighs on both」——这是本日报见过的最基本也最常被省略的 benchmark 纪律。
  4. ⭐⭐ 主动作废自己的一组数据并说明原因（「its scene configuration was not verified against the retained samples」），同时保留旧数据供对照。
  5. ⭐⭐ 公开测试跳过条件（「or those tests are skipped」+ 五个环境变量名），而不是把跳过算进通过率。
  6. ⭐ 为可复现性牺牲性能：选软件 Vulkan，并明说「a hardware GPU raises them for every runtime」。
  7. ⭐ 前缀快照与回退（每个应用一个 RAVEN_PREFIX，每次安装器前快照，--restore-prefix 回退）。
  8. ⭐ 混合上游来源的诚实声明（自建 MIT + ReactOS/Skia/libpng/Unicode 各自许可）。

风险。

  • ⚠️⚠️ 最大的风险是元数据层面的：created_at 不可信。 任何自动化流程——包括本日报自己的「今日新项目」筛选——若只用 created_at，会把这个 14 个月的项目当成 4 小时前的新项目。修正后的原则：必须用 commits API 交叉验证。
  • ⚠️ 单作者（contributors API 返回 1 人）、subs 1、无 release（分发路径是从源码构建）。
  • ⚠️ GPL 义务只在散文里：根 LICENSE 是 MIT，license.spdx_id 也是 MIT，但 native/upstream/ 静态引入了 9 个 ReactOS 组件（GPL/LGPL）——这是本日新增的第五类许可元数据问题：「主许可正确但组合许可被折叠」，扫描器会给出「纯 MIT」的错误默认答案。
  • ⚠️ 它自己列出的限制：只支持 Windows 应用（不是游戏生态）；native/upstream/reactos-user32/ 下只有 bridge.c/register.c/scrollbar_control.c/shim 四个文件，说明 ReactOS 组件是按需挑选的移植而非全量引入（这既是好消息也是限制——未移植的部分如何处理，本窗口未核验）。
  • ⚠️ 性能优势的边界：软件 Vulkan 下 71.5 vs 63.0 FPS 的差距在真实商业应用上未必线性；且这 8 个逻辑 CPU 的环境不具代表性。
  • ⚠️ 未经第三方复现：全部 benchmark 为作者自述。

是否值得跟踪。 值得，且这是本日唯一一个「应当被当作方法论样本而非产品候选」的项目。 观察重点：(1) 兼容矩阵的实际规模（cmd/compat-matrix 与 internal/compat/matrix.go 的数据来源本窗口未核验，这是它最核心也最未知的部分）；(2) 是否发布 release（当前只能从源码构建，对采用是硬门槛）；(3) ReactOS 上游组件清单是否被结构化到仓库里（对应第五类许可问题）；(4) 是否支持 ARM64 宿主；(5) 它是否继续在自己的仓库里维护 docs/benchmarks.json 里被作废的数据——这是「作废数据是否留痕」的一个长期观察点。

Deep Dive 3：songjianyang/xss-audit（本批最高 fork 比例，而它只有 15 KB）

项目定位。 一份 26 KB 的静态 XSS 审计规程（agent skill），4.6 小时 194⭐ ⑂50（fork/star 25.8%，本批最高），MIT，仓库仅 15 KB、仅 1 个 commit、contributors 1 人、无 release、subs 0。

为什么它值得比它的 star 数更多的注意力。

因为它是本日唯一一个「产物是文字」的热门项目，而它的质量控制方式恰好是它自己文档结构的一部分。

它的技术亮点（准确地说，是它的规程设计）：

  1. ⭐⭐ 14 层覆盖的是真实的 sink 分类，包含 mXSS、SVG/MathML 命名空间混淆、JSON-in-script 的 </script> 逃逸、原型污染链、CSS-in-JS 插值、框架信任钩子、模板注入——不是「搜索 innerHTML」的简化清单。
  2. ⭐⭐ 开篇的 Reality check 把清单本身的局限说在前面：「none of these measures guarantees complete protection on its own」。
  3. ⭐⭐ 执行规则把失效模式显式化：不得跳过任何搜索类别、不得因文件名判断安全、必须逐个追数据流、必须按正确上下文（HTML/attribute/URL/JS/CSS）检查消毒。
  4. ⭐⭐⭐ 点名了具体的 URL 校验反例：new URL('javascript://trusted.com/%0aalert(1)').hostname 是 trusted.com——只校验 hostname 是不够的。
  5. ⭐⭐⭐ 要求把「排除项与未读文件」记进报告，并单列 manual-review 区——一份「我检查了哪里、没检查哪里」的账本。
  6. ⭐⭐⭐ 示例报告第一行就写「Fictional example… no reproduction steps were executed」——在一个「输出格式即卖点」的品类里，唯一示例被明确标注为虚构且未经执行。
  7. ⭐ SECURITY.md 把工具的输出流向也管起来：在别的项目里发现的漏洞报给那个项目，不是这个仓库；公开 issue 不含凭据与未脱敏利用报告。

风险。

  • ⚠️ subs 0 + 1 个 commit + 15 KB + contributors 1 人 = 一份被当作 skill 分发的静态文档，尚无社区共建。
  • ⚠️ 它声称的漏洞发现数与 MSRC 排行榜排名本日报无法核验（附了 leaderboard 与 X 主页链接，但排行榜是外部页面）。
  • ⚠️ 静态分析必然有假阳与假阴——README 自己写了（「Static analysis can produce false positives and false negatives, especially for dynamic runtime behavior, build-time transforms, excluded code, and framework-specific execution timing. Review exclusions and verify findings before relying on them. No coverage is guaranteed.」）。
  • ⚠️ 报告可能包含敏感信息——README 自己警告：「Generated reports may contain sensitive paths, source code, internal domains, or credentials. Review and sanitize them before sharing.」
  • ⚠️ 25.8% 的 fork 比例不可读作「质量更高」——它对应的是「改一份 26 KB 的 Markdown 几乎零成本」。

是否值得跟踪。 值得，但作为「规程设计的样本」而非「安全工具」。 观察重点：(1) 是否出现第二个 commit（即是否有人补上更新机制——静态清单会随浏览器 API 演进而腐化，这一点它自己也承认）；(2) 是否有外部使用者发布用它做的真实审计报告（这是判断它是否真的被用的唯一信号）；(3) 14 层是否扩展到它点名但未覆盖的 API（如 Trusted Types 的实际落地路径）；(4) 是否有 fork 改造成支持其他框架/语言的版本——这正是 25.8% fork 比例最可能的去向。

风险与机遇

机会

  1. ⭐⭐⭐ 「未验证」可以是产品的一部分，而不是免责声明。 mcreplay 的 capability-matrix.md 首行写「No authenticated calls were possible… All reliability judgments below are provisional」并仍被发布，同时另一份文档记录了实测。并行保留两份互相矛盾的证据，是本日报见过最难的诚实形式，也是最值得抄的形式——它比「只写一份并标注可信度」更有信息量，因为读者能看见认知的推进过程。
  2. ⭐⭐⭐ 让「破坏性变化」成为 CI 的退出码，而不是一句警告。 mcreplay 的 0/1/2/3 四档退出码 + breaking/review/info 三级分类，是一个可以原样搬进任何「上游 API 会漂移」场景的设计。它与 10-24 记录的 oss-verify oft check（在 Print Assumptions 阶段拒绝越界公理）属于同一族：让检查器真的会拒绝。

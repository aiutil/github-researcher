⭐⭐⭐⭐⭐ 11-16 用 steam-library-bridge 证伪了「release 多 = 有发布史」，11-17 用 ffmpeg-skill 给出了真样本，本日则发现——光有「tag 数」和「release 数」两个数仍然不够，必须加上「链上有没有真实 diff」与「资产是否随版本演进」。

⭐⭐⭐⭐⭐ ⭐⭐⭐ 两条本日新得到的判定规则：

规则一：功能 commit 在 tag 上还是父上，是一个伪命题。 ⭐⭐⭐⭐⭐ 实测 open-code-review 的三个连续版本：v1.13.11 功能在 tag commit（24 文件 / 5 源码）· v1.13.10 功能在 tag commit（21 / 7）· v1.13.9 功能在父 commit（tag 只有 2 文件 / 2 源码，父 12 文件 / 7 源码）⭐⭐⭐⭐⭐ —— ⭐⭐⭐⭐⭐ 同一仓库内两种形态交替出现。⭐⭐⭐⭐⭐ plannotator 同理（v0.28.67 功能在父、v0.28.66 功能在 tag）。⭐⭐⭐⭐⭐ 因此判据只能是「这条链上是否存在真实的源码 diff」**。

规则二：asset 数量与 asset 的信息价值是两件事。 ⭐⭐⭐⭐⭐ arcane 41 个 asset（deb/rpm/apk/zst + 14 个裸二进制）但没有 SBOM 或校验文件；⭐⭐⭐⭐⭐ open-code-review 只有 7 个 asset 但有 sha256sum.txt，⭐⭐⭐⭐⭐ plannotator 36 个 asset 且有 CycloneDX SBOM + 13 个 sha256 清单。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ asset 数相差 5.9 倍，但「可验证性」是 open-code-review 最高。⭐⭐⭐⭐⭐ 最优解不是「asset 多」而是「asset 与分发需要匹配」。

⭐⭐⭐⭐⭐ ⭐⭐⭐ 第三条（本日的意外发现）：真实下载量是发布纪律的外部检验，且与「asset 形态」强相关。 ⭐⭐⭐⭐⭐ 实测 open-code-review 的 asset 下载 57–951 次 ⭐⭐⭐⭐⭐ 而 plannotator 只有 1–12 次、arcane 10–16 次。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 同样是 100 个 release、同样有闭合的 diff，⭐⭐⭐⭐⭐ 谁被真的下载了，差别有 1–2 个数量级。⭐⭐⭐⭐⭐ 「发布纪律」解决的是「版本可信」，⭐⭐⭐⭐⭐ 而「是否有人在用」是一个正交且更难获得的问题。

⭐⭐⭐⭐⭐ ⭐⭐⭐ 第四条：类别 D 的具体形态（本日新增，最值得记）。 ⭐⭐⭐⭐⭐ modern-web-guidance-src 的 10/10 抽样 tag 的 commit message 完全相同（「docs: auto-update recent evals and skill coverage」），⭐⭐⭐⭐⭐ 且都改了 src/rag/gen/guide-chunk-cache.i8 + .json + .scale.f32（⭐⭐⭐⭐⭐ .i8 = int8 量化后的 RAG 向量索引）；⭐⭐⭐⭐⭐ 而其父 commit 才是真正的功能变更（src/build/publish-skills.ts / src/harness/public/builder.ts / guides/**/grader.ts / guides/**/demo.html）。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 也就是说：它把「检索索引」当作编译产物版本化，⭐⭐⭐⭐⭐ 因此每次内容更新都会产生一个 tag —— 100 个 tag 对应的是 100 次内容/索引同步，⭐⭐⭐⭐⭐ 而不是 100 个面向用户的发布。⭐⭐⭐⭐⭐ 而它唯一的那 1 个 release 装的偏偏是审计数据（expectations-coverage.json / eval-defects-pr1998.json）⭐⭐⭐⭐⭐ —— ⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 「把审计产物当 release 发」比「把 release 笔记写好」更有信息量。**

⭐⭐⭐⭐⭐ 风险一：本数据集 11-12 ~ 11-15 建立的账号层面判据，其可信区间此前从未被量化 —— 本日的对照实验给出了区间。 ⭐⭐⭐⭐⭐ 「短期新建账号占比」在 Trending 组是 38.0%、对照组是 40.5%，⭐⭐⭐⭐⭐ 而 linux / rust / go / svelte 高达 71%–88%。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 这意味着：在没有同域对照的情况下，「账号很新」这条信号在 GitHub 上的基线极高，⭐⭐⭐⭐⭐ 用它的绝对值做判断会系统性地把正常仓库误判为异常。 ⭐⭐⭐⭐⭐ 推论：判据库必须从「绝对阈值」改为「相对对照」，⭐⭐⭐⭐⭐ 且对照组应固定为长期不变的成熟仓库（linux / rust / go / svelte）。**

⭐⭐⭐⭐⭐ 风险二：「SKILL.md 数」这个指标正在被生态自己用于宣传，因此必须被防御性解读。 ⭐⭐⭐⭐⭐ 实测 ECC 的 1,087 里 94.7% 是副本。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 推论：引用任何项目的技能数时，都应先除以复制倍数，⭐⭐⭐⭐⭐ 否则会把分发投入误读为内容产出。

⭐⭐⭐⭐⭐ 风险三：「发布很多版本」与「有人在用」之间没有稳定的映射。 ⭐⭐⭐⭐⭐ 实测同样 100 个 release 的三个项目，asset 下载次数分别是 57–951 / 1–12 / 10–16。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 推论：任何基于 release 频率、tag 数、asset 数的「项目成熟度」评分，⭐⭐⭐⭐⭐ 都必须补一个外部检验指标（下载量 / 活跃用户数 / issue 质量），⭐⭐⭐⭐⭐ 否则评的是发布习惯，不是产品。

⭐⭐⭐⭐⭐ 风险四：本日的 Trending 榜单本身不能被当作「质量筛选器」。 ⭐⭐⭐⭐⭐ 本日 25 个 Trending 仓库全部通过了本数据集的全部判据（无投放体），⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 但同时它们中也包含 paper-orchestra 这样的 8-commit 薄实现与 Tencent/LoopForge 这样的 0 套分发清单项目。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 换言之：Trending 榜单在这两日里与「工程质量」没有表现出可测的相关性，⭐⭐⭐⭐⭐ 它衡量的是传播速度，不是实现质量。**

⭐⭐⭐⭐⭐ 机遇一：把四元组版本判据做成一个可复用的脚本。 ⭐⭐⭐⭐⭐ 一次 tags 请求 + N 次 commits 请求 + 一次 releases 请求即可得到：tag 数 / release 数 / diff 闭合率 / asset 形态与信息价值。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 本日报的 scripts/_deep_2026_11_18.py 与 scripts/_forensics_2026_11_18.py 已经实现了这套抓取，⭐⭐⭐⭐⭐ 可直接迁移到任意仓库做历史回溯。

⭐⭐⭐⭐⭐ 机遇二：把「复制倍数」列成 skill 仓库的常规体检项。 ⭐⭐⭐⭐⭐ 一次 git/trees?recursive=1 请求即可计算（用 SKILL.md 的父目录名去重 + 比对 blob sha）。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 本日报的 scripts/_identity_2026_11_18.py 已实现，⭐⭐⭐⭐⭐ 成本一次请求，且能同时暴露「分发冗余」与「复制是否由 CI 保证」这两个问题。

⭐⭐⭐⭐⭐ 机遇四：modern-web-guidance-src 的「索引即编译产物」值得被广泛借鉴。 ⭐⭐⭐⭐⭐ 把「用户实际拿到的检索索引」作为版本化产物，⭐⭐⭐⭐⭐ 能在每次内容变更时自动产出一个 tag，⭐⭐⭐⭐⭐ 从而用「版本数」直接度量「内容同步次数」，⭐⭐⭐⭐⭐ 同时彻底消除「文档更新了但索引没更新」这类漂移。

⭐⭐⭐⭐⭐ 机遇五：SBOM 作为 release 产物，是二进制分发项目最低成本的信任建立方式。 ⭐⭐⭐⭐⭐ 一个 .cdx.json + 13 个 .sha256 的成本几乎为零，⭐⭐⭐⭐⭐ 收益是任何下载方都能独立验证。⭐⭐⭐⭐⭐ ⭐⭐⭐⭐⭐ 这比在 README 里写「我们很安全」有效得多 —— ⭐⭐⭐⭐⭐ 且本日实测证明它的成本远低于多格式分发（arcane 41 asset 无 SBOM vs open-code-review 7 asset 有 sha256）。

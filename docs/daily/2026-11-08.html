最值得关注的方向

方向一：判据的可被攻击性，应该成为研究方法的一部分。

本日报连续多日使用 fork 时间分布、commit 秒字段熵、subs/oi/commits/releases 等判据来识别星标农场。11-08 记录的第一件方法论事实是：这些判据里至少有一个（subs）已经出现在攻击面上，而且攻击成本几乎为零 —— 只要在 README 里加一句「⭐ Star the repo if it helped you.」即可。

⭐⭐⭐⭐⭐ 推论：判据必须成对使用 —— 一个「深度信号」和一个「反向信号」同时检查。本日可用的四元组是：(a) README 是否索取 star/watch；(b) fork 到达的时间分布；(c) 文件 md5 是否与已知农场重复；(d) 代码能否 import / 运行。 这四项在本日全部可自动化，且本日对 162 个候选逐个跑通了。

方向二：「让不确定性可见」正在从文档习惯变成一种可复用的产品形态。

本日报过去五天记录了 vork 的许可声明、poki 的验证文档、hermes-voice 的决策契约。11-08 的四个项目把这个趋势推到了四个新位置：

  • phoneuse —— 测试矩阵入档（逐项写明「Tested with」的版本号）
  • satmux —— 物理下界入档（不可消除的 RTT）
  • ghostclick —— 证据材料化（RMA evidence，而不只是结论）
  • solo-to-team-skills —— 完成声明的门槛化（证据先于声明，且给出反例清单）

⭐⭐⭐⭐⭐ 这四个项目互不相识、互不相关，却都做了同一件事：把「我凭什么这么说」写进产物，而不是写进 issue 讨论。 这比「开源项目有文档」具体得多，也更可检验。

方向三：空壳分销正在接替载荷投递。

11-06 之前，农场投递的是可执行载荷；本日，85 个仓库连 README 都不写，直接在描述里卖外挂。这意味着 GitHub 上「star 数」作为注意力度量的噪声本底已经高到无法单独使用 —— 而这也正是本日值得记录的：在同一份榜单上同时存在「42⭐ 的空壳目录」与「316⭐ 的 7 文件完整实现」，任何按 star 排序的榜单都无法把它们分开。

Top 1 · lxe/phoneuse — 把「这是给我自己搭的」写在第一屏

118⭐ ⑂10 · subs 2 · oi 0 · 85 commits · 594 KB · Python · MIT · 34 文件

它的整个设计围绕一个选择：手机侧零安装。屏幕走 AirPlay 进来，输入走 Bluetooth HID 出去，中间没有任何东西跑在 iPhone 上。ARCHITECTURE.md 首段把这条边界写死：

phoneuse has two independent channels to the phone. The screen comes in over AirPlay, the same way it would go to an Apple TV, and input goes out over Bluetooth, with the PC pretending to be a mouse and keyboard. Nothing runs on the phone.

⭐⭐⭐⭐⭐ 而本日最值得抄的是它对「未验证」的写法。 README 的第一个块就是警告，然后是一张把每个依赖都钉到版本的表：

Tested with Notes
iPhone iPhone 17 Pro, iOS 26 other models: set screen_points (below)
Linux with BlueZ Arch Linux, BlueZ 5.87 the Bluetooth adapter must be in range of the phone
Hyprland 0.56 window geometry and the cursor come from Hyprland's IPC
GStreamer 1.28 NVIDIA decoding used when available, software otherwise

⭐⭐⭐⭐ 注意第三列里那些看起来像抱怨的句子：「the Bluetooth adapter must be in range of the phone」「NVIDIA decoding used when available, software otherwise」——它们不是免责声明，是「我的结论在什么条件下成立」。这比「本项目尽力支持多种设备」有用一个数量级。

⭐⭐⭐⭐⭐ 而它对自己造成的破坏也写出来了：phoneuse install 需要 sudo，会「disable bluetoothd's own input and hostname plugins, so this PC stops accepting Bluetooth keyboards and mice of its own」，并给了一条撤销命令。⭐⭐ 这是本日报见过最诚实的一处权限声明：工具的代价是「你这台机器不再是原来的样子」。

⭐⭐⭐⭐ 架构上最精细的一段是输入映射：mirror_input 把镜像窗口上的 hover / press / drag 翻译成手机触摸，坐标通过 Hyprland IPC 获得（窗口几何 + 光标位置），而不是盲发像素。HID daemon 的 report descriptor 同时声明键盘、相对鼠标与绝对指针三样东西 —— 这解释了为什么它既能做「移动光标」，也能做「在镜像窗口里点一下 = 戳手机屏幕」。

⭐⭐⭐ 对 agent 的入口是双份：bin/phoneuse（CLI）与 bin/phoneuse-mcp（MCP server），视觉侧走 OCR + grounding 支持 phoneuse text/find。⭐⭐ 这与本日报记录的「给 agent 的入口按 token 预算设计」（vork）不同：vork 把帮助文本压到 2,500 token，phoneuse 走的是「CLI + MCP 双通道」，两者都是「让 agent 有一个确定的入口」，但一个压 token，一个压接口。

⚠️ 证据边界：subs 2、contributors 1 人、releases 0、topics 空数组。全部结论基于单一机型（iPhone 17 Pro / iOS 26）与单一桌面（Arch + Hyprland + NVIDIA），本日报未在任何硬件上复现任何一项；unlock.py 与 screen_points 的具体实现本窗口未逐行核验。

Top 2 · Th0rgal/satmux — 把不可消除的物理下界写进 Limits

316⭐ ⑂17 · subs 1 · oi 0 · 7 文件 / 22 KB · Python（纯标准库）· MIT

它的诊断是三段结构而非一句「卫星网慢」：① 客舱网关劫持 :53 并跑透明 :443 split-TCP 代理（PEP），其状态表在负载下丢连接 —— 而非 443 端口原样透传；② 每个新 origin 都要付多个卫星往返才能传第一个字节；③ 丢包让标准 TCP 反复腰斩 cwnd，使每座位的令牌桶额度用不满。

⭐⭐⭐⭐⭐ 而它的实测表把「没赢的格子」也标了出来，这是全表最关键的读法：

ORIGIN (6× PARALLEL) RAW CABIN WI-FI (:443) 1-RTT BBR + ZLIB MUX SPEEDUP
GitHub Repo TIMEOUT 4.66s FIXED ✓
GitHub API TCP RESET 2.66s FIXED ✓
Hacker News TIMEOUT 2.28s FIXED ✓
MDN Docs 12.01s 2.30s 5.2×
Cloudflare 2.97s 1.40s 2.1×
PyPI JSON API 7.09s 2.64s 2.7×

⭐⭐⭐⭐⭐ 前三行的 FIXED ✓ 与后三行的加速倍数，含义完全不同：前三行说明 raw 连接是被超时和 TCP reset 打死的，satmux 的作用是「让失败变成成功」；后三行才是常规意义上的提速。如果只读「5.2×」就会低估这个工具；如果只读「FIXED」就会以为它只是个绕过方案 —— 两者都不是。

⭐⭐⭐⭐⭐ 它的 ## Limits 是本日报最值得整段抄走的一节：

  • Latency floor (~580–650 ms): Speed-of-light propagation to geostationary orbit (35,786 km) does not change; satmux removes extra round-trips, not the physical RTT of one hop.
  • Per-seat shaper (~4–5 Mbps typical): ……already-compressed binaries (.mp4, .zip) stay bounded by the seat cap
  • Single paid session: Uses your authenticated cabin Wi-Fi lease; it does not bypass captive portals.

⭐⭐⭐⭐ 而对照表与 Limits 是配套的：它明写测量条件（Inmarsat GX Ka-band、~620 ms RTT、SITA AS206433 阿姆斯特丹地面站），并没有给出方差或重复次数 —— 这是一处需要读者自己保留的怀疑。

⭐⭐⭐ 安全设计值得记：载波流用 BLAKE2b-512 加密 + HMAC-SHA256 认证，端到端 TLS 在笔记本侧保留（地面 VM 只做 DNS + 已验证的 TLS 1.3 + HTTP 重定向 + zlib 压缩），PSK 用 chmod 600 保存。⭐⭐ 它还给了可直接交给 coding agent 的部署指令，并要求在机上暂停 UDP VPN（「blocked UDP retry traffic competes for cabin airtime」）。

⚠️ 证据边界：subs 1、contributors 1 人、releases 0、topics 空数组。全部性能数字为作者自述的一次性测量，本日报未复现任何一项；方案需在地面站自备付费 VM（$0.01–0.03/h），不是一个「装上就能用」的工具。

Top 3 · MajestyPoemFold/ghostclick-mouse-double-click-fix — 不只给结论，还产出证据

136⭐ ⑂21 · subs 0 · oi 0 · 77 文件 / 12,029 KB · Rust + Tauri 2 · MIT · 1 release

它的产品定义从用户可观察的现象出发，而不是从技术名词出发：「鼠标单击变双击」的机制是 mouse chatter / switch bounce，但它的界面是一张走纸记录仪式的条带图，每键一支笔，6 ms 与 11 ms 的幽灵点击被红笔圈出并标注。

⭐⭐⭐⭐⭐ 而它最有架构价值的一步是「learns a debounce threshold from your real double-clicks」 —— 它不内置固定去抖阈值，而是先让用户自己双击、从真实输入里学出这台设备这只手在这个灵敏度下的阈值。⭐⭐⭐⭐ 这是「把机器拍的参数换成实测参数」的又一种形态，与 poki 的「触摸写进去了 ≠ 设备确认了」同源。

⭐⭐⭐⭐⭐ 而「exports RMA evidence」是本日最值得架构师记的一句：它不只输出结论，还产出一份可提交给厂商退货/换货的证据材料。⭐⭐⭐ 对照本日报近五天的记录 —— vork 把许可边界写进 LICENSE、poki 把「写进去了 vs 确认了」分开、hermes-voice 用 19 条决策记录取舍 —— 这四个项目都是「把边界写进输出」，而 ghostclick 是「把证据造出来」，方向更进一步。

风险与机遇

⭐⭐⭐⭐⭐ 风险一：昨日推荐的判据今日被证伪 —— 这是本日报记录到的第一例「判据被针对」。 11-07 的日报把 subscribers_count 写进 projects/poki.md 的「⭐⭐ subs 是一个噪声极低但样本极小的指标」一节。11-08 实测：两个空壳仓库的 subs 是 25 与 35，高于全部四个真项目（4 / 2 / 1 / 0）。原因就是 README 里两行 ⭐ Star the repo if it helped you.。本日报已把该判据修正为「只在同作者族内可比；跨作者比较前必须先核对 README 是否索取 star/watch」。

⭐⭐⭐⭐⭐ 风险二：空壳仓库的「订阅数」会持续污染任何基于 subs 的自动化筛选。 这是一个「越受欢迎越容易被引用的判据」：一个工具如果开始基于 subs 筛选高质量仓库，它筛出来的会是「README 里写了请给我 star 的仓库」。⭐⭐⭐ 这与昨天记录的「农场会针对判据调整形态」是同一件事，只是这次被针对的是判据而不是 payload。

⭐⭐⭐⭐ 风险三：本日的形态已不是「投递」，而是「外挂分销货架」。 85 个空壳中 84 个带 resp/rpocket 标记，描述直接售卖 Warframe hack、ROBLOX ESP、aimbot、Monero Miner 与 Claude jailbreak prompt。⭐⭐⭐ 对研究者而言，这意味着「GitHub 上新仓库的 star 分布」这个数据源本身已被污染到不能单独用于趋势判断；对使用者而言，空仓库里不会有任何东西可下载，但描述会引导到别处。

⭐⭐⭐⭐⭐ 风险四：一个已归档项目的档案混入了另一个仓库的数据 —— 而它的成因不是「改名」，是「上下游」。 本日报核查持续跟踪项时发现：2026-10-30 日报把 interplains/Zero-Breach-Toolkit 的数据（4,475⭐ / 12,477 KB / fork 473 / subs 42 / oi 7 / v0.1.13）写进了上游 interplains/zero-breach 的档案，并把两者描述为「仓库已由 interplains/Zero-Breach-Toolkit 改名为 interplains/zero-breach（GitHub 会重定向旧路径）」。⭐⭐⭐⭐⭐ 经 id / fork / parent / created_at / release 列表五字段交叉确认，两者是各自独立创建的不同仓库 —— interplains/zero-breach = id 1424399708（创建 2026-10-18T13:22:34Z，1,218⭐，9 个 release v0.1.0–v0.1.8，499 KB，57 commits），interplains/Zero-Breach-Toolkit = id 1433297111（创建 2026-10-25T14:41:34Z，4,553⭐，23 个 release v0.1.0–v2.0.6，12,477 KB，70 commits），两者 fork=False 且 parent=None。⭐⭐⭐⭐⭐ 判定依据是文件存在性：PRIVACY.md 与 docs/VERIFYING.md 只存在于下游 Toolkit，上游两者皆无；⭐⭐⭐⭐⭐ 而 projects/zero-breach.md 的正文自始至终描述的是上游（其 README 引文「no admin, no dependencies」「Tested on Windows, macOS and Linux (Python 3.8–3.12) in CI」「A clean result is not a clean bill of health」均与上游吻合）—— 即：档案的正文是对的，元数据是错的。 ⭐⭐⭐⭐⭐ 本日报已据此更正 projects/zero-breach.md 的 stars 与 stars_delta，并为下游另建独立档案 projects/zero-breach-toolkit.md。 ⭐⭐⭐⭐⭐ 而这次纠错反而证实了 2026-10-30 日报自己记下的那句观察：「上游负责研究，下游负责可用，而 star 记在下游」—— 上游 9 个 release 停在 10-20（19 天无 push），下游 10 天内从 v0.1.0 迭代到 v2.0.6 并新增 27 种语言与 Android / iPhone 备份支持；⭐⭐⭐⭐⭐ 教训与本日报记录的「created_at 会说谎」「改名时间戳」同族：GitHub 的旧路径在改名后仍可解析，因此「旧路径能打开」不能证明「两者是同一个仓库」；判定改名必须比对 id 与 parent，而不是比对路径或描述。

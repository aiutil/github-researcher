# c6lang/c6

## 一句话定位
**TinyCC 的一个分支**：给 C 加上一组系统编程友好的语言扩展（`defer` / `errdefer` / `try-catch` / `async-await` / `module-import` / `interface` / 切片 / 元组 / 泛型 / 闭包 / 宏），**并且用「源文件后缀 `.c6`」作为唯一的开关** —— `.c` 文件的行为与上游 TCC 完全一致。

## 它解决的问题
⭐⭐⭐⭐⭐ **C 的老问题不是「没有函数」，而是「没有作用域退出语义、没有错误传播、没有模块、没有泛型、没有协程」—— 而所有补法都在语言之外。** 现有选项是换语言（Rust/Go/Zig，代价是重写）、用宏库（glibc/Boost，代价是编译期依赖与可移植性）、或者用纪律约束（goto cleanup、setjmp，代价是人会忘）。

⭐⭐⭐⭐⭐ **c6 的赌注是：这些能力可以在编译期被「按文件」加进 C，而不改 C 的语义。** README 写得很明确：**「扩展默认不启用，且是编译期可裁剪的：不定义 `C6_EXT` 构建出的编译器与上游 TCC 行为完全一致」**，且**「开启扩展的唯一开关是源文件后缀 `.c6`：它只对这一个翻译单元生效（每个文件独立判断，`.c` 文件不会因为同一次编译里出现 `.c6` 而被连带开启）」**。

⭐⭐⭐⭐⭐ **这个设计决定是本日最值得架构师抄的一条：它把「语言方言」这个通常需要编译器 flag 全局开关的东西，降级成了一个逐文件的、可组合的、可逐目录推广的特性。** 与之配套的是 **`import NAME;` 优先查找 `NAME.c6`，找不到才回退到 `NAME.c`** —— 即**同一个模块的两种实现可以共存于同一构建中**。

## 关键技术亮点

1. **⭐⭐⭐⭐⭐ 逐文件开关的语言扩展（`.c6` 后缀）：**
   README 明写「**后缀是唯一的开关**：`.c6` 文件开启扩展（并定义 `__C6__`），`.c` 文件永远是普通 C；没有 `-std=c6` 这个选项」；`import` 优先找 `NAME.c6`，再回退 `NAME.c`。**这一个决定同时解决了三件事：默认安全（`.c` 行为不变）、渐进采用（一个目录一个目录地迁）、以及模块级混编（`.c6` 与 `.c` 可以在同一构建中共存）。**

2. **⭐⭐⭐⭐⭐ 编译期可裁剪：** 「不定义 `C6_EXT` 构建出的编译器与上游 TCC 行为完全一致」—— 即扩展不是运行时开关，而是**构建期条件编译**，在不使用扩展的部署里零成本零风险。

3. **⭐⭐⭐⭐ `defer` 的实现选择：注册状态在函数帧里，不需要 TLS。** README 写「`defer { ... }` 作用域/函数退出时逆序执行清理代码（**注册状态在函数帧里，不需要 TLS**）」，并有专门的 `defer_scope.c6`（块作用域与 goto 跨作用域）、`defer_reent.c6`（递归/重入时的 defer 链）、`defer_thread.c6`（线程里的 defer）三个测试文件。**「不需要 TLS」这一句是架构上的关键决策 —— 它避免了线程局部存储带来的初始化顺序与跨线程可见性问题。**

4. **⭐⭐⭐⭐ 错误处理是一条完整链路而非单个关键字：** `errdefer`（仅错误路径）、`return err(id, "msg")`（设置错误槽、就地展开清理并直接返回，且**只能在 `T!error` 函数里写**）、`func() T!error` 声明可能失败的函数、`try` 原样传播、`catch e { ... }` 就地处理并清空错误槽。**类型签名 `T!error` 把「这个函数可能失败」写进类型系统，而不是靠文档约定。**

5. **⭐⭐⭐⭐ 无栈协程 + 真线程是两套分开的机制：** `async`/`await`/`co`/`task` 是**无栈协程**（`co f();` 顶层跑、`task t = f();` 拿句柄），而 `spawn f(...)` 是 **OS 线程**（`pthread_create`）—— README 明写「语句立刻返回、**真并发**」。⭐⭐⭐⭐ **把两者分开是正确且常见的选择：无栈协程不能被 OS 抢占，容易与 FFI 死锁；用 spawn 换来真并行但要付线程代价。** `async_frame.c6` 测试「帧住在任务里：`&local` 跨 await、weak 形参」—— **即它明确处理了协程捕获栈引用这个经典陷阱。**

6. **⭐⭐⭐⭐ 泛型用 `@` 后缀而不是尖括号：** `struct Vect@T { ... }`、`Vect@int`、`Map@(char[:], int)`，函数模板用 `\|T\|` 前缀绑定形参，值形参 `struct Buf@(T, int N)` 进入 mangle（`struct Buf_int_4`）。⭐⭐⭐⭐ **README 写「**单态化**：实例就是普通 `struct Vect_int`、普通函数 `Vect_int_vat`……所以 c99 后端与纯 C 的 TU 零改动**」—— 即泛型在编译期被完全消解，不留运行时类型。** ⭐⭐⭐⭐ **这一条是「泛型系统设计」里最省事也最稳的一条路线：** 不做 type erasure、不做字典查找、导出的头文件就是普通 C。**

7. **⭐⭐⭐⭐ `interface` 用胖指针 + 自动生成 vtable：** 「胖指针（`{void *self; const VT *vt;}`）+ 自动生成的 vtable 接口抽象」。⭐⭐⭐ **这是「C 语言里的接口」最标准的实现方式（等价于 C++ 的非虚接口 + 手写 vtable），没有魔法。**

8. **⭐⭐⭐⭐ 结构体方法用 C 的命名约定实现：** 「`ret f(struct T *self, ...)` 即为 `T` 的方法，可用 `p->f(...)` 或 `v.f(...)` 调用（符号是 `T_f`，不同类型可同名，`f(p)` 仍可用）」—— **即方法 = 带类型前缀的自由函数 + 语法糖，且保持 C 的 ABI。**

9. **⭐⭐⭐ 切片是两个字长：** 「带长度与边界检查的数组视图（`{元素指针, 长度}` 两个机器字）」—— 边界检查是**运行时**的（README 明确写了「带长度与边界检查」），与泛型的编译期消解形成对比。

10. **⭐⭐⭐ 宏按角色定义并自动卫生重命名：** 「像函数一样写宏：`stmt swap(expr a, expr b) { ... }`，开头的角色说清展开结果怎么用；宏体里的局部变量自动卫生重命名（`__local` 仍可手动标注）」。

## 架构启发
⭐⭐⭐⭐⭐ **最值得抄的一条是「用文件后缀而不是命令行开关来选择方言」。** 这是一个看似微小、实则影响全局的设计决定：它把「要不要这个语言特性」的决策粒度从**一次构建**降到**一个文件**，**从而让采用这件事从「立项」降级为「试一个目录」**。⭐⭐⭐⭐⭐ **任何团队在推广新工具时都该问一句：我能不能把采纳的最小单位做到「一个文件」？**

⭐⭐⭐⭐⭐ **第二条是「错误路径写进类型签名」。** `func() T!error` 让「这个函数可能失败」成为类型的一部分，而不是注释里的一句约定。⭐⭐⭐⭐⭐ **这与本日报连日记录的「把边界结构化」是同一条线索的不同层次** —— 11-08 记录 `ex-ussr-kinship-research` 用 `independence_group` 在代码层禁止凭空声明两条记录互相印证，10-26 记录 `raven` 用 `LICENSES.json` 把许可边界结构化，**而 c6 是同一条思路在语言层面的版本：把一条本来靠人遵守的纪律，做进类型系统或编译期。** ⭐⭐⭐⭐ **三者共同指向一个判断：把规则写进机制，比写进文档可靠一个数量级。**

⭐⭐⭐⭐⭐ **第三条关于「自举作为正确性证明」。** 「三条自举路线」意味着编译器用自己的输出编译自己 —— ⭐⭐⭐⭐ **这是编译器领域最强的自证形式之一（比测试更接近「我确实能跑」）。** ⭐⭐⭐⭐ **但也要清醒：自举通过不等于语义正确，只等于「自洽」。** ⭐⭐⭐⭐ **因此 c6 同时保留了 35+ 个按特性划分的测试文件 —— 这两者的组合（自举 + 特性矩阵测试）比任何单独一种都强。**

⭐⭐⭐⭐⭐ **第四条关于「把未完成的部分显式列出」。** commit 「tests: 补齐特性矩阵里 4 处缺口，把有专属用例的特性覆盖补到全量」与 README 里的 `## 已知限制` 章节、文档 `docs/plan.md`（含实现状态）、`docs/grammar.md`（BNF/EBNF 规范）—— **即项目的「完成度」是被当作一等的工程产物来维护的。** ⭐⭐⭐⭐ **这与本日报记录的 `solo-to-team-skills`「证据先于完成声明」、`ghostclick` 的 RMA 证据导出、11-08 记录的 `phoneuse` 用 `[!WARNING]` 主动降级自己，是同一种气质。**

## 定位判断
**基础设施候选（infra-candidate），且是本日唯一一个。** ⭐⭐⭐⭐⭐ **它想成为的东西不是一个库，而是「C 生态的一个方言层」—— 如果它成功，C 的用户可以按文件渐进获得 defer/错误处理/模块/泛型/协程，而不需要重写，也不需要换语言。** ⭐⭐⭐⭐⭐ **这个定位的价值在于它可被证伪：** 「`.c` 文件行为与上游 TCC 完全一致」是一个可以逐条比对上游 TCC 行为的强断言；而「三条自举路线」是一个可以运行的强验证。

⭐⭐⭐⭐ **与同类项目的关系上，它处在一个少见的交叉点：**
- **vs 各类 C++ 替代品（Zig / Rust / Go）：** 那些是**换语言**，c6 是**留在 C 里**；代价是它必须自己实现泛型/协程/闭包/GC 这些 C 缺失的部分（README 的 `gc.c6` / `gc_type.c6` / `gc_drop.c6` / `gc_thread.c6` 说明连 GC 都做了）；
- **vs TinyCC 上游：** 它是 TCC 的分支，**不是替代品** —— README 明写「`tcc/` 源码树：上游基线 + 一个 c6 补丁一个提交」，**这意味着它的长期维护成本与 TCC 上游的演进直接绑定**；
- **vs 各类 C 宏库（如 defer 宏、error-handling 宏）：** 那些是「无编译器改动」的折中，c6 是「改编译器」的彻底方案 —— **而 c6 的 `.c` 兼容性正是为了让宏库方案与它可以共存**；
- **vs 各类 C 方言编译器（GCC 的 C++ 模式、Clang 的扩展、MSVC 的 C）：** 那些靠 flag 全局开启，**c6 靠后缀逐文件开启** —— **这是本日最独特的一处设计差异。**

⭐⭐⭐⭐ **但必须同时给出定位的风险面：** 组织 `c6lang` 是**创建于仓库前 7 分钟、0 followers、1 个公开仓库**的全新实体；`license.spdx_id` 为 **null**（仓库根目录**没有 LICENSE 文件**）—— **一个语言级项目没有许可声明，是一个 serious 的采用障碍**（详见下）。

## 与同类项目的关系
- **vs TinyCC 上游（`TinyCC/tinycc`）：** **父子/分叉关系**，c6 是「上游基线 + 一个补丁」，**不是替代**。⭐⭐⭐⭐ 这条关系决定了两者必须共同演进。
- **vs 其他「C 方言」实验（GCC 的 C2x 提案、Clang 的实验特性）：** 那些是**标准化路线**（进入 C 标准），c6 是**分叉路线**（不等标准）。⭐⭐⭐⭐ **分叉的好处是可以立刻做自己想做的事（`.c6` 后缀 + 自定义泛型语法 `@`），代价是永远要自己维护标准分叉的漂移。**
- **vs 各类 C 宏/库级方案（defer 宏、expected 库）：** 那些不改编译器、可与任何编译器配合；**c6 的 `.c` 完全兼容策略恰恰是让两者可以在同一代码库里共存。** ⭐⭐⭐⭐ **这两条路线不是竞争关系，而是分层关系** —— 这也是本档案认为 c6 定位务实的一个理由。
- **vs Rust / Zig / Go 等「换语言」方案：** c6 的整个价值主张就是「不必换」。⭐⭐⭐⭐ **对一个有百万行 C 代码的存量组织，这是唯一现实的技术路径 —— 也是本日报认为它的潜在影响面远大于其 37⭐ 的原因。**

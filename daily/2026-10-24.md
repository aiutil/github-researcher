### 趋势 1：Apple 内核移植的第三条路径（趋势分 91）

**本日最值得记的结构性观察：48 小时内出现了第三条互不相识的 Apple 内核移植路径，而它在关键决策上与前两条恰好相反。**

**分歧点极清晰：前两条都拒绝碰内核，HackiOS 恰恰选择改内核。** UniXNU 的整条设计哲学是「不 patch 内核而是补齐内核期待的 Apple 平台契约」，Macintosh 是「跑 Apple 官方 kernelcache 默认未修改」——**两者都把「内核保持官方二进制」当作原则，代价是继承全部不兼容与全部漏洞，收益是内核升级时零 rebase。HackiOS 反其道而行：既然 Apple 的 XNU 本身是开源的（APSL 2.0），那就直接编译它、打补丁，然后跑官方未修改的用户态。** 这是一个从法律与工程两个维度都不同的第三条路——**它把「不改内核」的成本（继承不兼容）换成了「每次内核升级都要重新 rebase 补丁」的成本**，而对 iOS 16.5 这个固定版本，rebase 成本为零。

**第三个观察是本日最值得学的一份文档：`docs/checks.md`「How our own checks lie」。**

它的开头就把整篇文档的论点说完了：**「They are written down because eleven of the twelve look the same: missing information reads as a missing problem.」**

这条论点的分量在于它反转了通常的怀疑方向。普通做法是怀疑「检查通过」意味着「检查没问题」；这份文档主张**更常见的失败是「检查根本没跑」而这看起来和「检查跑了并且通过了」一模一样**。它给的十一个例子里最有代表性的三个：

1. **被跳过的检查没有计数。** `continue` 不加总 → 十条 AIR 声明在只比较四个 case 之一后被列为匹配（其余三个卡在无限等待）；`if idx >= len(flat): continue` 静默丢掉短行；`read()` 进固定缓冲区丢掉文件尾部。**总计仍然对得上——68 + 3 + 7 = 78——因为被推迟的那些也被算作匹配。** 它给出的对策不是「检查总数」而是「**一个每个例外都有自己的列与名字和数字的总计**」，并指出最极端的情况是对空集做检查：**「a loop of zero iterations prints '0 of 47' and looks exactly like an honest zero」**——那次是内核列表所在目录在两次会话之间被清理，唯一救回来的是 shell 单独说了「no such file」。**「A denominator lies as quietly as a summand.」**
2. **被静默的命令。** `patch -s --dry-run` 返回 0 却不说话，**沉默被读成「恰好适用」**；去掉 `-s` 才会说 `succeeded at 410 (offset 2 lines)`。
3. **从缺席推断。** 「日志里没有」与「没发生」是两件事——**loader 的日志会丢掉中段**（标记是「size at the limit」加上确切的一行 `the log between the first 256 KB and the last 1 MB was dropped`，而不是「was dropped」这几个字，按钮驱动也打印同样的话）；`grep` 的视野会漏掉二十行之上的守卫（六个 `bin/sh` 匹配全是 `/var/jb/bin/sh`）；**一个从不触发的看门狗只有在同时给出运行次数时才证明任何事**（他们的看门狗是 26 次运行、零漂移）；一次打印零行的测量其实是 `grep` 了一个 `printf` 从不打印的模式。**「A measurement that cannot fire looks exactly like an event that did not happen.」** 那个零不是靠怀疑仪器抓到的，而是靠**与已测到的结论矛盾**抓到的：三个模块靠指针绑定翻译，因此那里不可能是零。

### 趋势 2：把「我证明了什么」与「我没证明什么」做成可执行的形式（趋势分 90）

`theorem-labs/oss-verify-proofs` 的热度很低（92⭐ ⑂6，**subs 0**，**全仓库仅 2 个 commit**，contributors API 返回空数组）。**但它是本批信息密度最高的项目之一**，而且它的信息全部以机器可检查的形式给出。

它做的事一句话说得清：**对 OSS-Fuzz 的 fuzz target 给出机器检验的证明，证明「在陈述的界限内不存在使它失败的输入」**——而且 **「Each proof is about compiled binaries, not source code.」**

**它的边界声明写在最前面，不是最后面。** README 第三节标题就是 **「LPS is best effort and not complete. It describes part of Linux, and it makes some assumptions that it does not check. A proof is only as good as LPS.」** 这句话把「形式化验证」这件事最容易误导人的地方直接摆在了台面上——**证明的可信度上限由语义模型的完备性决定，而这个模型自己明说不完备**。

然后是 `What a proof does not say` 这一节，六条边界：

- **不证明库正确。** sanitizer 检测不到的错误（如错误结果、内存泄漏）不在排除范围内。
- **只覆盖一个入口点可达的代码**，不是整个库。
- **只针对这些二进制**：clang 20.1.8 + musl 构建的静态 riscv64 程序，**不是源码，也不是 OSS-Fuzz 的 x86-64 构建**。
- **在 LPS 中为真**；LPS 与 Linux 不同处，证明可能不适用。
- **agreement statement 不排除永不结束的运行**——只有 halts statement 能排除，**而本次发布没有任何一条 proof 证明 halts**。

**这最后一条值得单独强调。** 它意味着 138 条已证证明的主张是「在覆盖范围内 sanitizer 不报错且两构建行为一致」，**而不是「程序会终止」**。一个能被 fuzzing 之外的形式化方法证明「不会崩溃」却没证明「会终止」的库，在实践中仍然可能挂死。**作者把这个缺口写在最显眼处而不是藏起来。**

### 趋势 3：破坏性操作的不变量与「提前拒绝」（趋势分 89）

`xevrion/hatchzip`（2.5 天 888⭐ ⑂17，**fork/star 1.9% 为本批最低**，subs 1，Rust，Apache-2.0）的 star 数比同批的 oss-verify 高一个量级，但**它的内容密度是本日第二高的**。

**它解决的问题具体到能算。** 180 GB 的归档解出 200 GB，WinRAR / 7-Zip / `unzip` 需要 **380 GB** 磁盘，因为归档与产物必须同时存在于盘上。**HatchZip 只需略多于 200 GB。**

**技术路线是一条完整的理由链，而不是一个技巧：**

1. **只能从尾部截断。** 从前或从中删除需要打洞（Linux `fallocate`、Windows `FSCTL_SET_ZERO_DATA`、macOS `F_PUNCHHOLE`），**而 FAT32 与 exFAT 不支持打洞，且各系统行为不同**。所以 HatchZip 从尾部工作。
2. **每个格式把归档描述为 unit 列表**（ZIP 一个 entry = 本地头 + 数据；7z 一个 solid block 或非 solid 时的一个文件；tar 一个 entry 含其前的长名/pax 记录；`.tar.gz` 整个归档从前端解）。**unit 按位置倒序解压，每批之后把归档截断到该批最低 unit 的起点。**
3. **7z 的 solid block 只能从头解码**，所以它只能在其全部解出后才被释放——**最大 unit 就是就地解压的主要成本**（需要「输出 + 约等于最大 unit」的空间）。
4. **目录与空文件在 7z 里没有数据只有头条目**，构成一个额外 unit，起点在头所在处，所以先做，且截断它只释放已保存的头。

**它给出的唯一硬拒绝场景是可复算的**：7-Zip 默认设置会把整个归档放进一个 solid block，此时「一块在被完全解出前一点空间都释放不了」——**HatchZip 在碰任何东西之前就拒绝并说明原因**。README 对比表的最后一行结果就是 `Refused before touching anything`。

**README 的对比表全部带具体数值**（同一份 200 MB 游戏数据、21 个文件、220 MiB tmpfs 模拟整机磁盘、约 50 MB 空闲）：

| 归档 | `unzip` / 7-Zip | HatchZip |
|---|---|---|
| ZIP，180 MB | **unzip 在第 6/21 个文件耗尽空间** | 完成，每个文件逐字节一致 |
| 7z 25.01 `-ms=20m`（10 个 solid block） | 需 380 MB | **0.64 s 完成，逐字节一致** |
| 7z 分 5 卷各 40 MB | 需 380 MB | 完成，**卷被逐个删除，峰值占用 210 MB** |
| tar（GNU tar），200 MB | 需 400 MB | **0.12 s 完成，逐字节一致** |
| 7z 默认设置（1 个 solid block） | 需 380 MB | **在改动任何东西之前就拒绝** |

速度上 ZIP 解压 **0.25–0.35 s，对比 unzip 6.00 的 1.48–1.50 s**（**含一次 `unzip` 跳过的 fsync**）。测量环境写明：Fedora 43、Intel Core i7-14700HX、SK Hynix NVMe SSD、热页缓存；空间测试用 220 MiB tmpfs，速度测试用 ext4。**速度来自并行解压，所以只含一个巨型文件的归档按单核速度解出。** README 还说明额外空间需求约等于「能一次释放的最大单元」的大小，并指出在支持打洞的文件系统上，大文件每 256 MiB 就释放一次归档字节（**一个 600 MiB 存储文件在 950 MiB tmpfs + 367 MB 空闲下完成，而传统方式需要 629 MB**），`hatchzip check` 能为任意归档算出确切数字。

**AGENTS.md 把不变式写成绝对句，这是本批最值得抄的一段工程纪律：**

> **「The tool destroys its input. The invariant is absolute: the journal never claims a file before it is durable, and the archive is never truncated past an entry the journal doesn't claim.」**
> 「Anything that can be refused is refused before the archive is touched.」
> 「Every number in the README and docs is measured on real hardware, never estimated. Paste the measurement when you change one.」
> 「A behavior is not finished until it ran for real: a real archive extracted, the output compared byte for byte, the crash tests passing.」
> 「**Never run `extract` on an archive you can't recreate. It deletes it.**」

以及通信规范：「Be succinct. Prefer code over prose.」「**State what you did not verify. An honest gap costs less than a confident wrong claim.**」

**它还把踩过的坑写成具体条目**（`Traps already fallen into`），每一条都是真实事故而非泛泛的最佳实践：zip crate 反向扫描整个归档找 end record，**`storage::Reader` 必须对已截断区域返回零而不是报错，否则每次恢复都失败于 `No CDFH found`**；tar 依赖同样的零来停在截断点；Windows 上必须用字节区间锁，因为锁归档会阻塞自己的读取线程（`another process has locked a portion of the file`），`platform::open_exclusive` 在那里改用 share mode；**Linux 用一次 `syncfs` 刷新一批，所以每目录的 bug 只在 macOS 与 Windows 上暴露**；链接条目的文件夹直到最后才存在，不要按批处理；不要在测试里硬编码单元数（7z writer 给某些空文件单独一个 block，会让每个计数差一——改为断言不变式）；7-Zip 默认设置可能把整个归档放进一个 solid block，测试要同时用 `-ms=<size>` 与默认设置；**恢复时崩溃批次写过但未提交的文件仍占空间，必须先删除再做空间检查，否则检查会拒绝一个其实装得下的运行**。

**它还用本地计数解决了一个真实痛点**：`vesalius stats` 显示 Claude 到底问过什么（工具、调用数、token、每次答案的中位耗时、完整性检查是否通过），**从不记录你的问题、符号或代码**；`vesalius doctor` 按 Claude Code 的方式启动 server 并检查每一环连接、它服务哪个仓库、索引有多新。这直接针对 MCP 生态里最常见的抱怨——「agent 从来不调我的工具」——而 Vesalius 的答案是**先承认这曾经是真的（第一轮 2/24），然后把根因写下来，再改设计**。

**对比表也毫不含糊地写明它不是所有人的正确工具**：调用图只覆盖 4 种语言，**其余 13 种只有词法**；只在 macOS 15+ Apple silicon 上运行；**在仓库里不留任何东西**（对比 CodeGraph 留 `.codegraph/`、graphify 留 `graphify-out/`）；setup 只加一条 MCP 条目与一条权限规则；**无网络**（CodeGraph 默认开匿名遥测与更新检查）。

## 重点项目深度分析（top 3）

### Deep Dive 1：oosexgang/hackios-xnu-kernel（本日信息量最大的单项目）

**项目定位。** 在 Android 手机硬件与 QEMU 上启动 Apple 开源的 XNU 内核（xnu-8796.121.2 = iOS 16.5 的内核）并在其上运行**未修改的 iOS 16.5 用户态**，1.7 天 1,064⭐ ⑂183（**fork/star 17.2%，本批最高**），C，**APSL 2.0（LICENSE 文件）/ NOASSERTION（GitHub API）**，20677 KB，subs 4，oi 7，**全仓库仅 6 个 commit，contributors API 返回 2 人**。

**为什么它值得比它的 star 数更多的注意力。** 因为它是**48 小时内出现的第三个 Apple 内核移植项目，而它在最关键的那个决策上与前两个相反**——前两个都坚持「不改内核」，它直接编译 Apple 开源的 XNU 源码并打补丁。**三个项目、三种路线、同一周，这个事实本身就是本日最强的结构性信号：Apple 硬件逆向已经不再是一个人的黑客项目，而是一个有多种已验证技术路线的领域。**

**它的技术亮点：**

1. **自写 EFI loader**（`xnuloader/loader.c`，clang + lld-link，**不用 EDK2**），它常驻内存、提供 USB fastboot 协议链路、看门狗、接收内核日志。
2. **UEFI 移植**（`uefi/` 为 Project Silicium 移植 + `mkxnuimg.py` 打包），**每个 release 附带 `hackios-redwood-boot.img`——redwood UEFI 内嵌自写 loader，可直接 `fastboot boot`，且不含任何 Apple 文件**。
3. **Apple 闭源驱动的替代实现**（IOSurface / IOMobileFramebuffer / AppleKeyStore / 网络栈 / minicrypto 替 corecrypto / AMFI 与 Sandbox 替身）。
4. **Metal 驱动工作**（Mesa 25.0.7 + AIR→ir3 前端），**456 个系统 shader 中 293 个已在 Adreno 642L 上运行**（62.9%）。
5. **Linux Wi-Fi 驱动层**（WCN6750 via ath11k + LinuxKPI，`wifi/lx/`）。
6. **「用户态一个字节未改」的实现方式**：缺失部分由内核替代驱动或 `DYLD_INSERT_LIBRARIES` 注入库补齐（`kern.exec_inject`），注入进 backboardd / SpringBoard / mediaserverd，mediaserverd 获得自写 CoreAudio 输出设备。
7. **双运行目标**：真机（fastboot boot，不写闪存，重启即回 Android）与 QEMU（**无需真机，20 分钟会话，2–3 分钟出锁屏**）——**QEMU 路径让任何人都能复现，这是它 fork-star 17.2% 的机制解释**。

**风险。**

- **⚠️ 许可需特别核验（本批最严重的一处可核验元数据问题）。** 仓库 `LICENSE` 首行是 `APPLE PUBLIC SOURCE LICENSE Version 2.0 - August 6, 2003`——**APSL 2.0，与 GPL 不同的 copyleft，且含专利报复条款**；GitHub 侧 `license.spdx_id` 为 `NOASSERTION`；**README 与 NOTICE 均未说明该仓库自有代码的许可**。APSL 2.0 对「External Deployment」（分发给第三方，或作为 Larger Work 提供服务）有明确条件（须满足 Section 2.1 关于 Source Code 的全部条件）。**这直接影响「能不能把它的代码放进商业产品」这个判断——依赖 license 扫描器的工具会得到错误的默认答案。**
- **⚠️ 本日新增发现的元数据不一致，累计第四类四例**（10-22 的 php2shell-poc spdx_id=null / 10-23 的 UniXNU 与 Macintosh 两处 NOASSERTION / 本日 HackiOS 的 NOASSERTION + Vesalius 的无 LICENSE 文件）。
- **star 数与社区规模严重不匹配**：1,064⭐ 但 subs **4**、贡献者 **2 人**、主仓库 **6 个 commit**。
- **功能缺口明确**：蜂窝、蓝牙、本内核下充电、**App Store 内容与 Apple ID 登录（无 Secure Enclave，FairPlay daemon 退出）**、视频与实况照片；Metal **456 个 shader 中 163 个不可用**。
- **它自己声明的形态**：「It is a research bench, not a ROM: a session lasts a given number of seconds, then the kernel returns to the loader and hands over its log.」
- **未经第三方复现**：QEMU 20 分钟会话与真机截图均为作者自述。
- **用户态仓库 328⭐ ⑂116（fork/star 35.4%），但只有 4 个 commit 且 contributors API 返回空数组**——与内核仓库的形态一致，说明是同一团队的集中发布。

**是否值得跟踪。** **值得，且跟踪方式应是「它会不会扩到第二台设备」而非「star 数」。** 它是本日唯一一个把「可复现路径」（QEMU）与「真实硬件路径」（真机）同时提供的项目，也是唯一一个把「Apple 内核可以是补丁目标而不只是黑盒」的路线证明出来的项目。**观察重点：(1) `docs/checks.md` 是否继续更新（这是它最独特的资产）；(2) 163 个不可用 shader 是否继续下降；(3) 是否出现第二台设备 profile（决定它是可移植方案还是封闭作品）；(4) `redwood.patch` 的规模与是否随 XNU 版本更新；(5) 许可表述是否补齐自有代码条款。**

### Deep Dive 2：theorem-labs/oss-verify-proofs（把「我证明了什么」做成机器可读的形式）

**项目定位。** 针对 OSS-Fuzz 的 fuzz target 给出机器检验的 Rocq 证明，1.5 天 92⭐ ⑂6（fork/star 6.5%），Rocq Prover，MIT，**2142968 KB ≈ 2.1 GB（本批最大）**，**subs 0**，oi 1，topics 6，**全仓库仅 2 个 commit，contributors API 返回空数组**。

**为什么它值得比它的 star 数更多的注意力。** 因为它证明了一件本日报其他项目都在做但没做到的事：**把边界变成可执行的检查，而不只是可读的声明。** 对比本日其他三个项目——HatchiOS 讲「怎么验证你的验证」，Vesalius 讲「我的实验失败了」，hatchzip 讲「先拒绝」——**oss-verify 讲的是「让机器读出我的证明边界，并且让检查器真的会拒绝」**：`oft check` 在 `Print Assumptions` 阶段拒绝任何不在 `toolchain/allowed-axioms.txt` 里的假设。**一个只会通过的检查器和一个会拒绝的检查器，价值差一个数量级——而后者可被独立验证。**

**三个技术观察点：**

1. **证明的对象是二进制而非源码。** 这让证明可核验（build record 含每个二进制的 SHA-256），但也让它**与 OSS-Fuzz 实际的 x86-64 动态构建之间存在可核验的落差**——README 自己列了这一条。
2. **LPS 是形式化模型，因此它的不完备性被转移成了证明的适用性边界。** 作者的处理方式是把边界写成句子而不是脚注：「**A proof is only as good as LPS.**」并且 `docs/semantics.md` 专讲设计原则与其极限，`analyses/known-issues.md` 逐条给出每个未证 statement 的原因（**229 条被模型阻塞，多数正是因为模型不覆盖线程与 CPU affinity**）。
3. **许可分层是一份值得抄的文档实践。** NOTICE 区分「我们写的」与「由 Anthropic 授权的证明派生而来的」，`LICENSES/` 存两份许可文本 + NOTICE，且**每个此类证明的 build record 指名这三个文件**。**在一个 AI 辅助证明越来越多、而训练数据来源许可越来越敏感的时间点，这种处理方式值得被直接借鉴。**

**风险。**

- **⚠️ `subs 0` + **2 个 commit** + **contributors API 返回空数组** = **机构发布而非社区共建**。**没有任何外部贡献者痕迹**，也没有外部复现记录。
- **⚠️ 本次发布没有任何一条 proof 证明 halts**——138 条已证证明的主张只是「不触发 sanitizer 错误且两构建行为一致」，**不能排除永不终止的运行**。
- **证明只对静态 riscv64 有效**：clang 20.1.8 + musl。**与 OSS-Fuzz 实际的 x86-64 构建之间存在明确落差**，README 明确列出但落差的影响需读者自行判断。
- **2.1 GB 仓库体积对 clone 不友好**；CI 已改为 'one proof unit per check job'，说明体积确实构成工程约束。
- **验证成本高**：16 核上一次证明检查最多需 20 GiB 内存（每核编译一个文件）。
- **「LPS is best effort and not complete」是作者自陈**，因此其证明的强度受限于一个公开声明为不完备的模型——**这不是缺陷而是诚实，但读者必须知道上限在哪**。

### Deep Dive 3：xevrion/hatchzip（本日唯一「今天就能用」的项目，也是唯一带绝对不变式的）

**项目定位。** 就地解压超大归档，边解边把归档从尾部截断，2.5 天 888⭐ ⑂17（**fork/star 1.9%，本批最低**），Rust，Apache-2.0，1990 KB，subs 1，oi 8，**contributors API 返回 1 人**，3 个 release × 22 个 asset。

**为什么它值得比它的 star 数更多的注意力。** 因为它是本日唯一一个**「我现在就能下载、用它、并且能自己验证它」的**项目——而它同时是本日 fork-star 最低的项目。**这两件事同时成立，本身就是本日最强的一条读法。**

**它的技术亮点：**

1. **理由链而非技巧。** 只能从尾部截断（打洞在 FAT32/exFAT 上不支持且各系统行为不同）→ 每格式的 unit 划分 → 倒序解压 → 每批截断到最低 unit 起点。**每一步都有「为什么不能是别的」**。
2. **可复算的硬拒绝。** 7z 默认设置的单个 solid block 无法在解出前释放空间 → **在碰任何东西之前拒绝并解释原因**。
3. **journal 作为崩溃安全的真相源**，配 `<archive>.hatchzip-tail` 保存索引尾部（在截断移除它之前复制并记 CRC-32），**已截断区域读作零**让 zip crate 反扫与 tar 解析都正确停下。
4. **实测数字而非估计**：README 的每一个数字都来自真实硬件（AGENTS.md 明令「Every number in the README and docs is measured on real hardware, never estimated」），并附测量环境。
5. **平台差异被收进一个模块**：AGENTS.md 明令 `platform/` 之外禁止 `cfg(target_os)`/`cfg(windows)`，CI 三平台跑测试。

**风险。**

- **⚠️ 未代码签名**：Windows 需「更多信息 → 仍要运行」，macOS 15+ 需手动允许。**这在企业环境是实际部署障碍。**
- **⚠️ APFS 与 NTFS 上的打洞未验证**（README 明说 'NTFS and APFS not yet verified'）——**这意味着「每 256 MiB 释放一次」的那个优化在 macOS 与 Windows 上不生效**，那两个平台上的实际收益接近「输出 + 最大 unit」而非 README 里那个 950 MiB tmpfs 的极端例子。
- **单作者**：contributors API 返回 1 人，subs 1。
- **这是破坏性操作**（AGENTS.md 自己说「It deletes it」「Never run extract on an archive you can't recreate」）——**journal 的正确性是唯一的安全屏障，而 journal 的实现在本窗口未逐行核验**。
- **7z 支持不完整**：7-Zip 自己的格式特性（如某些加密、某些压缩方法）是否全覆盖，本窗口未核验。
- **单一文件系统的行为差异**（FAT32/exFAT 上打洞不支持，但截断支持）——README 说「任何能收缩文件的文件系统」都能用，但**收益差异未量化**。

**是否值得跟踪。** **值得，且优先级在本日「可立即采用」类别中最高。** **观察重点：(1) 签名与公证（这是企业落地的必要条件）；(2) APFS/NTFS 打洞验证；(3) 是否支持更多压缩方法与加密 7z；(4) journal 格式的稳定性（跨版本恢复的兼容性）；(5) 贡献者数量——单作者项目的连续性是真实风险。**

## 风险与机遇

### 机会

1. **⭐ 「我的检查会骗我」成为一份可复制的文档类型。** HackiOS 的 `docs/checks.md` 把十一让检查说谎的方式写成了带真实代价的条目，并给出对策「**每个例外都有自己的列、名字和数字**」与「**a denominator lies as quietly as a summand**」。**这个方法论可以移植到任何写测试、跑 benchmark、做验证的团队——包括本日报的读者自己的项目。**
2. **⭐ 「不会失败的检查器」与「会失败的检查器」应当被区别对待。** oss-verify 的 `oft check` 在 `Print Assumptions` 阶段拒绝越界公理，且允许公理被逐条列出。**这与上一条是同一件事的两面：如果你的检查只会通过，它就不构成证据。**
3. **⭐ 破坏性操作也可以有绝对不变式。** hatchzip 的「journal 在文件持久化之前不认领它；归档绝不截断到 journal 未认领的条目之后」是可以直接照抄的形式。**更重要的是它配了一条组织纪律：「State what you did not verify. An honest gap costs less than a confident wrong claim.」**
4. **⭐ 失败的实验轮次值得写进 README。** Vesalius 的第一轮 24 次里 agent 只调用了 2 次，作者把它写成 benchmark 的第一段而非附录——**这让读者知道「20/20」这个数字是怎么来的，也让人能判断该改动是否真的有效。**
5. **⭐ 许可分层的处理方式（oss-verify 的 NOTICE + LICENSES/ + build record 指名）值得被抄进任何混合来源的项目。** **本周已记录四类 license 元数据问题（NOASSERTION / null / 无 LICENSE 文件 / APSL 未标注），这说明「许可证表述」已经是开源发布的一个真实故障点。**
6. **Apple 内核移植在一周内出现三条独立技术路线（UEFI 伪平台契约 / EL2 hypervisor / 编译开源 XNU 打补丁），且本批四条路线都把「Apple 私有输入不得入库」写成了仓库级制度。** **这既是领域成熟度的信号，也是一份现成的合规清单模板。**
7. **本日出现的可复现路径值得利用**：HackiOS 的 QEMU 路径（无需真机、20 分钟会话、2–3 分钟出锁屏）与 oss-verify 的 `oft check`（可在自己环境独立复现检查流程）——**这两个是本日报中唯二能由第三方独立执行完整验证的项目。**

### 趋势 1：Apple 内核移植的两条独立路径，撞上同一组难点（趋势分 90）

这是本日最值得记的结构性观察。**两个互不相识、作者不同、路径不同的项目，在同一天各自解决同一个问题，并各自独立地把「Apple 私有输入不得入库」写成了仓库级制度。**

先固定事实基线（全部来自 GitHub 官方接口与 README/AGENTS.md 原文）：

| 事实 | UniXNU/UniXNU | Acelogic/Snapintosh |
|---|---|---|
| 目标 | iOS + macOS 跑在非 Apple ARM64 硬件 | macOS 27（build 26A428）跑在 Snapdragon X2 Elite 笔记本 |
| 路径 | **UEFI** + 伪平台契约 | **EL2 hypervisor**（monitor）+ 工具链 |
| 内核 | 官方 XNU，**不 patch**（README 明写补齐平台契约） | 官方 kernelcache（J700/T8140），**默认未修改** |
| 设备覆盖 | **35 份设备文档**，多机型移植 | **只支持一台**（ASUS Zenbook A16 UX3607OA，X2E-96-100，README 原文「Nothing else is supported」） |
| 页表难点 | `docs/xnu/four-k-page-tables` 单列一章 | `shadow/` 目录（16 KiB → 4 KiB 影子页表） |
| GPU | 原生 Adreno 740 Metal 驱动（10-22 news） | 自写 AdrenoMetal.bundle + AdrenoX2 + air2ir3 shader 编译器 |

| 额外依赖 | — | **必须有一台 macOS 27 Mac 主机**（USB-C NCM） |
| 规模信号 | 35 设备 · 16 驱动 submodule · subs 3 · 贡献者 6 人 · 30 commits | **11 commits**（5 小时内完成）· subs 4 |
| 许可 | BSD-2-Clause-Patent（文件）/ NOASSERTION（API） | MIT（文件）/ NOASSERTION（API） |

**共同的三个技术难点：**

1. **16 KiB → 4 KiB 页表翻译**。Apple 的 XNU 用 16 KiB 页，而绝大多数 ARM64 SoC 的 MMU 只支持 4 KiB。两个项目都把它单列为核心章节/核心目录——**这说明它是这类移植绕不过去的第一个真问题**，而不是某个项目的个性选择。

2. **Apple 平台契约的构造**。UniXNU 的做法是提供内核"认识的"设备与寄存器（16 个 `Native*` submodule + `Arm*` 平台层）；Macintosh 的做法是在 EL2 提供 SPTM/TXM 调用、内核 16 KiB 页表翻译、以及 AIC / ANS2 NVMe / DART 等 Apple 设备模型。**两者都不 patch 内核**——这是一个共同的、且反直觉的取舍：继承内核的全部不兼容，换来内核升级时零 rebase。

3. **私有输入的合规处理**。UniXNU README：「Do not add Apple IPSW files, kernelcaches, disk images, trust caches, Data seeds or vendor firmware to this repository.」Macintosh AGENTS.md 第 1 条列举了九类不得提交的内容（kernelcache、固件、restore-image 部件、KDK、kext、dyld cache、ACPI dump、反汇编/vtable/ABI dump、重建的 `*26A428.h` 头文件），**并加了一句「Do not paste protected source material into PRs, tickets, build logs or test fixtures」——把禁止范围从代码扩展到了 issue、构建日志与测试夹具**。

### 趋势 3：codegen 的派生物从磁盘上消失（趋势分 87）

- **「No codegen — the type checker asks Reylo directly: no generated files, no watcher.」** 这不是"生成得更好"，是**不生成**。
- **「Checked against your database — a misspelled column, a wrong parameter or a dropped table is a type error, in `tsc` and in your editor.」** 校验发生在**类型检查期**而非运行期，且要求一个正在运行的开发库。

还有一条论证方式的转变值得记：「**Agent-friendly** — each fact lives in one place, so an agent cannot leave a stale type behind, and the type check finds every caller it missed.」**这把"单一事实源"从面向人的 DRY 论点改写成面向 agent 的失效模式论证**——不再是"这样更整洁"，而是"这样 agent 就无法制造过期状态"。2026 年工具设计开始用「agent 会怎么弄坏它」而不是「人会不会弄错它」来论证，这是一个值得注意的转变。

**架构师速览（reylo）：**

| 决策问题 | 研究判断 | 证据边界 |
|---|---|---|
| 系统边界 | TS 语言插件层（content mapper）· Rust 引擎（`engine/`）· **对真实数据库的 schema 读取通道** · 类型检查期（`tsc` 与编辑器）· 运行期（`.run(db, params)`）。数据面是类型检查时的 SQL 解析 + schema 查询；控制面是 TS 编译器调用 mapper | README Setup 段（需 TS 7.1 beta、Node 24+、**一个正在运行的开发数据库**）+ 六卖点 + `Cargo.toml`/`engine/`/`oracle/` 目录；**`oracle/`、`skills/`、`lab/`、`wiki/` 的内容未取，待核验** |
| 主路径 | 编辑器或 `tsc` 遇到 `.sql` import → 调 content mapper 请求类型 → mapper 交给 Rust 引擎 → 引擎解析 SQL **并连开发库读取当前 schema** → 推导该条查询的行类型（受方言与 cast 影响）→ 返回给 type checker → hover 得到类型，错列名/参数在检查期报错 → 运行期 `.run(db, params)` 执行同一条 SQL | 由 README 的 Setup 依赖 + 六卖点 + 示例代码倒排；**「schema 读取是否每次检查都发生、是否缓存、缓存如何失效」README 未说明，这是本项目最关键的未决问题** |
| 关键权衡 | **零 codegen（检查时实时查询）vs 生成文件（离线、快、可 review）**——实时查询把成本转移到 type check 延迟与对开发库的依赖上 · **对着真实数据库校验 vs 纯静态解析** · **零手写类型 vs 显式类型（可读性）** · **依赖 TS 7.1 beta vs 现在就能用（ORM 或 codegen）** · **方言原生 SQL 全文力 vs 可移植性**（README 强调 "any statement, function, operator or syntax your database supports, in its own dialect"） | README 三项依赖 + 六卖点逐条 + **cast 直接影响推导结果这一事实**（`::int` → `number`）；**未明示：type check 性能开销、schema 缓存策略、错误信息质量、非 TS 后端的可用性** |
| 最小 PoC | 1. **先确认 TS 7.1 可安装**（`npm install -D typescript@beta`）——**这一步不成立则整个 PoC 不成立，先不要往下走**→ 2. 准备 Node 24+ 与运行中的开发库 → 3. 安装三件 → 4. 在 `tsconfig.json` 为 `.sql` 与 `.reylo.yaml` 注册 → 5. 用 README 的 `get_author.sql` 原样建表并 import，hover 确认类型为 `{ id: number; name: string; post_count: number } | null` → 6. **故意把 `post_count` 改成不存在的列，确认编辑器立刻标红且 `tsc` 报错**——**这一步是整个 PoC 的意义所在**：验证"对着数据库校验"是真的而非只做了静态解析 → 7. 改 SQL 的 cast，确认类型随之变化 → 8. 运行 `.run()` 确认一致 → 9. **测量 type check 延迟**（`tsc --diagnostics`，小项目与大项目各一次）——**这是唯一能回答"零 codegen 是否真的划算"的方法** | **第 5–7 步是最关键的自检**：若第 6 步不报错，说明它根本没连库校验，"Checked against your database" 就是空话；**第 9 步是 README 完全没提但决定该方案成败的问题** |

## 最值得关注的方向

今天四个项目分属四个领域（硬件移植 / 推理框架 / 工具链 / 语言工具），没有一个共同的技术主题。**但有一条判断标准可以跨领域复用，而且它在前三天已经连续出现：把边界、缺口与失败模式写成可核验的文档，比 star 数更能预测项目会不会被用起来。**

按项目逐个说：

- **UniXNU**：35 份设备文档让"这件事能不能做"从玄学变成查表；README 的 Private blobs 段把合规要求放在最显眼处。
- **Snapintosh**：Status 表把"已可用 / 进行中 / 不支持"三档措辞放在同一张表里，且给"进行中"标了量化目标（60 Hz）。**读者不需要读完全文就知道这台机器现在能干什么。**
- **DeepInfer**：README 有一整段专门写"本次发布不含什么"。对生产引入者来说，这段话的价值高于任何一项特性列表。
- **reylo**：六卖点里把"No codegen"和"Checked against your database"并列——**一个减少派生物，一个把校验提前，两者都在缩小"人可能弄错"的窗口。**

**跨项目的第二个观察（本日最实用的一条）：fork-star 在本日四个项目之间完全不可比，但有一个可解释的规律。**

| 项目 | ⭐ | ⑂ | fork-star | 归类 | 机制解释 |
|---|---:|---:|---:|---|---|
| UniXNU/UniXNU | 750 | 118 | **15.7%** | 可改造型 | fork 去移植自己的机型——README 专设 `docs/porting/`，35 份设备文档就是证据 |
| deepseek-ai/DeepInfer | 19,806 | 2,106 | 10.6% | 可读型 | fork 去读它的调度逻辑；kernel 栈本身已拆成 5 个独立仓库 |
| Acelogic/Snapintosh | 530 | 29 | 5.5% | 不可改造型 | **只支持一台机器，没有第二台可移植**（README「Nothing else is supported」） |
| colinhacks/reylo | 616 | 3 | **0.5%** | 不可改造型 | **需要的是等 TS 7.1 stable 并升级，而不是 fork 它** |

**推断（不构成事实）**：本批四个数据点显示，fork 比例与「项目是否允许/需要用户改造」相关，而与项目质量、热度或价值无关。**这是连续第三天观察到同一条分界线**（10-21 记录 1.1%–18.6%，10-22 记录 5.5%–35.9%，本日记录 0.5%–15.7%）。**但这仍是四个数据点，不足以支撑任何普遍结论。**

**必须同时说清的第三点：本日没有事件驱动的热度洪峰，但"没有一个可直接采用"这件事比"排名"更重要。**

| 项目 | 现在能不能用 | 卡在哪 |
|---|---|---|
| UniXNU | 不能（除非你的机型已在 35 份设备文档里） | 单机型移植成本；无 release |
| DeepInfer | 不能用于生产 | **缺 KV cache / PD 分离 / 跨副本负载均衡**——即缺它的核心设计目标 |
| Macintosh | 不能（除非你有那台 A16 和一台 Mac） | 11 commits、单机型、需第二台设备、音频摄像头蓝牙全缺 |
| reylo | 不能（除非 TS 7.1 stable） | **单一语言特性依赖** |

**这四个项目没有一个可以直接投入生产——这一点比它们的排名更能说明今天这个窗口的性质：这是研究快照与设计样本的窗口，不是工具发布的窗口。**

## 重点项目深度分析（top 3）

### Deep Dive 1：UniXNU/UniXNU（把移植难度写成可查询索引）

**项目定位。** 独立项目，通过 UEFI 在非 Apple ARM64 硬件上启动 iOS 与 macOS，3.5 天 750⭐ ⑂118（fork/star 15.7%，本批最高），Python，BSD-2-Clause-Patent，1947 KB，subs 3，oi 6。

**为什么它值得比它的 star 数更多的注意力。** 因为它的**规模信号来自三处可核验的结构事实，而不是来自热度**：

1. **35 份设备文档**（`docs/devices/`）。README 明确说明设备仓库用与主仓库相同的布局，其 modules 覆盖同名 modules，其 `package/` 成为构建树里的一个 kit——**这是一套已经被复用到至少 35 款设备的架构，不是单机型 hack。**
2. **16 个独立公开驱动的 submodule**。驱动不在主仓库里，各自独立、按需克隆。这既是可复用性设计，也是一种责任边界划分。
3. **文档站 unixnu.com 是一等公民**：`docs/concepts/{boot-chain,payload,prelink,security,userdata}.md`、`docs/drivers/{device-tree-matching,kexts,native-adreno}.md`、`docs/xnu/four-k-page-tables`，配 `docs.yml` 与 `macos.yml` 两条工作流。

**风险。**
- **⚠️ `license.spdx_id` 为 `NOASSERTION`，而 LICENSE 首行明写 `SPDX-License-Identifier: BSD-2-Clause-Patent`**——可核验的元数据不一致（严重程度低，因文件本身无歧义）
- **star 数与社区规模严重不匹配**：750⭐ 但 subs **3**、贡献者 **6 人**、主仓库 **30 个 commit**
- **没有任何 release**：分发路径是 clone + submodule + 自建
- **原生 GPU 驱动的声明无法在本日报核验**：news 段落称 Adreno 740 驱动在小米平板 6S Pro 上完全工作，但仓库按其自身规则不含可运行产物
- **设备覆盖是查表式的**：README 未给"最低可移植门槛"（内存、存储、特定 SoC 特性）
- **35 份设备文档中的机型代号大量为国产 SoC**（sheng / fajita / nuwa / pipa / piano / q2q / gta4l），意味着实际使用者集中在特定法域

**是否值得跟踪。** **值得，但跟踪方式应是"设备覆盖表"而非"star 数"。** 它是本日唯一一个把难度直接写成可查询索引的项目。**观察重点：`docs/devices/` 是否从 35 增长到 40+（说明有外部贡献者）；是否出现第二个由外部贡献者提交的设备文档；macOS/iOS 内核变更如何被跟进（保持官方内核意味着每次系统更新都要重做契约层）。**

### Deep Dive 2：deepseek-ai/DeepInfer（本日最有信息量的一份"不做什么"清单）

**项目定位。** DeepSeek 生产推理框架的开源版本，7 天 19,806⭐ ⑂2,106（fork/star 10.6%），Apache-2.0，2965 KB，**subs 43 为本批最高**，oi 193。

**为什么它值得比它的 star 数更多的注意力。** 因为它是本日唯一**同时具备两个特征**的项目：**由头部模型厂商官方开源**，且**明确描述了自己的生产环境规模**。QA 文档里的三条目标（多厂商加速器 / prefill 用 8 卡机而 decode 用 64–128 卡超节点 / KV cache 保留 >72h）解释了所有架构选择——尤其第二条，**prefill 与 decode 差一个数量级的硬件配置不是为了省钱，而是为了让缓存有一个能待得住的家**。

**它的三条技术观察点：**

1. **DSpark 的 confidence-scheduled verification** 用置信度决定验证多少个 draft token，而不是固定值——这正是 2026 年投机解码的核心争论点，README 直接把开关暴露为环境变量。
2. **SWA bounded replay 的正确性约束被写进文档**：保留的后缀"必须覆盖 SWA 窗口加上最大回退长度"。**一条可写死的正确性要求，比一个漂亮的 benchmark 更有价值。**
3. **batch-invariant 与确定性采样** 把可复现性做进引擎而非依赖外部固定种子，且两者都标注 **NVIDIA only**——说明昇腾路径并非功能对等。

**风险。**
- **⚠️ 最关键的限制是框架不完整**：不含 KV cache、PD 分离、跨副本负载均衡。**即使全部编译成功，也无法复现 72h 缓存复用——而那是它最核心的设计目标之一。**
- **7 天 193 个 open issue**：对新框架属正常，但配合 subs 43 说明确有大量真实用户。**是早期信号而非质量缺陷**，需观察关闭率。
- **「155T tokens/日、38 USD/GPU-hour」是作者声明**，本日报无法核验（私有集群数据）；README 的两张 Pareto 图（prefill 4×SM100、decode 64×SM100）是当前唯一可复核的量化证据
- **昇腾路径成熟度未知**：列为受支持硬件，但本窗口未取到任何昇腾特定的性能数据或限制
- **无 release**

**是否值得跟踪。** **值得，优先级在本日四个项目中最高。** 理由：它是本日唯一一个有公开声明的生产规模、且把不在范围内的东西写进 README 的项目。**观察重点（三项缺失是否开源，是这个项目未来的分水岭）、`deep_cluster/` 的实际内容（PD 分离代码是否已在树内未接线）、昇腾与 NVIDIA 的功能差距、`subscribers_count` 与 issue 关闭率的变化。**

### Deep Dive 3：Acelogic/Snapintosh（Status 表是本日最值得学的一个形式）

**项目定位。** 在 ASUS Zenbook A16（Snapdragon X2 Elite）上运行 Apple 官方 macOS 27 的 EL2 hypervisor，20 小时 530⭐ ⑂29，Python，MIT（文件），9641 KB，subs 4，oi 4，**全仓库仅 11 个 commit**。

**为什么它值得比它的 star 数更多的注意力。** **因为它的 Status 表。** 这一张表把以下内容放在同一套"已可用 / 进行中 / 不支持"的三档措辞里：

- 桌面：启动到桌面且 GPU 加速，**桌面测试场景的像素检查通过**
- 流畅度：**进行中，「interaction is usable but not yet smooth」**，目标稳定约 60 Hz，屏幕的 120 Hz 排后
- Wi-Fi：扫描、WPA2、DHCP、ping 在 host-proxy 测试架上可用，**从 macOS Wi-Fi 菜单发起连接尚不可用**
- 其他硬件：**音频、摄像头、蓝牙、休眠与外接显示器均不支持**

**这张表的价值在于它同时给出了"已验证"和"未达标"的边界，且给了未达标项一个量化目标。** 对比同规模项目通常只写一句 "coming soon"，信息密度高一个量级。

**第二条值得记的是 `gpu/agx*` 目录的存在本身就是一份诚实的路线记录。** README 说这是"an earlier virtual-AGX model, kept for reference"。**保留一条放弃的路径并标注为参考，比删掉它更能让读者理解为什么现在选原生驱动。**

**风险。**
- **⚠️ `license.spdx_id` 为 `NOASSERTION`，而 LICENSE 首行明写 `MIT License`**——同类元数据不一致
- **只支持一台笔记本**：README「Nothing else is supported. The monitor, device tables, clocks and register addresses are specific to this machine.」
- **必须有一台 macOS 27 的 Mac 主机**，且 AGENTS.md 把独立运行列为「a direction, not an already implemented or authorized replacement」
- **⭐ 11 个 commit、单机型、单次公开**：历史集中在 2026-10-22 的 5 小时内，**这不是成熟项目，是一个刚公开的快照**
- **未经第三方复现**：「pixel checks across the desktop test scenes pass」是作者自述
- **GPL-2.0 成分**：主体 MIT，但 `LICENSES/` 含 GPL-2.0-only 与 GPL-2.0-or-later，**具体哪些文件是 GPL-2.0 本窗口未逐项核验**

**是否值得跟踪。** **值得，但应作为"分层与状态记录的样本"而非"可用工具"。** 它的 EL2/EL1/EL0 分层表、Status 三档措辞、AGENTS.md 的九条禁止提交清单、THIRD_PARTY_NOTICES 的成分声明——**这四样加起来是一份关于"如何在硬件逆向项目里表达边界"的完整示范**，而这些都不需要它继续可用。**观察重点：60 Hz 目标是否有进展；是否出现第二台机型（决定它是封闭作品还是可移植方案）。**

## 风险与机遇

### 机会

1. **"缺什么"比"有什么"更值得读。** DeepInfer 用整段 README 写"本次发布不含 KV cache、PD 分离、跨副本负载均衡"，Macintosh 用 Status 表逐项写"音频、摄像头、蓝牙、休眠、外接显示器均不支持"。**对准备引入的人，这两张清单的信息价值高于任何特性列表**——它们直接决定"我能不能用"和"我要自己补多少"。
2. **两个独立项目同时把"Apple 私有输入不得入库"写成仓库级制度，且 Macintosh 进一步扩展到 issue 与构建日志。** UniXNU 的 README Private blobs 段与 Macintosh 的 AGENTS.md 第 1 条是两个互不相识项目的独立表述。**这类合规纪律在硬件逆向领域正在标准化，值得被抄进任何相关项目。**
3. **codegen 的替代路径出现了，而且论证方式变了。** reylo 让派生物不再存在于磁盘上（type checker 直接问引擎），并把"单一事实源"从 DRY 论点改写成 agent 失效模式论证。**凡是"事实源 A 变了，派生物 B 需重新生成"的场景，content mappers 都适用**——这个思路的可迁移性比项目本身大。
4. **16 KiB→4 KiB 页表翻译这个难点被两个独立项目同时确认为核心。** Macintosh 的 `shadow/` 与 UniXNU 的 `docs/xnu/four-k-page-tables` 都在同一位置把它单列。**一个技术难点被两条独立路径同时撞上，是这个难点真实存在成本的最好证据。**
5. **本日是自 php2shell 事件以来第一次没有事件驱动的热度洪峰。** 这意味着连续三天观察到的"fork-star 低区间"现象在本日**不是事件驱动的结果**——它更像是常态。**这为后续几天的观察清掉了一个混淆变量。**

### 风险

1. **四个项目没有一个可直接采用。** 今日的性质是研究快照与设计样本窗口，不是工具发布窗口。做选型时**"有没有被关注"与"能不能用"在今天是完全脱钩的两件事**——19,806⭐ 的 DeepInfer 不能用于生产，616⭐ ⑂3 的 reylo 反而把技术路线说得最清楚。
2. **reylo 的存续完全由一个尚未 stable 的语言特性决定。** README 要求 `typescript@beta`。若 content mappers 在 stable 前变更 API，项目需重写；若 TS 7.1 跳票，项目为零。**这是本日四个项目中最大的单点风险，且风险不在项目内部。**
3. **两处 `license.spdx_id = NOASSERTION`**（UniXNU 与 Macintosh），尽管两处 LICENSE 文件内容清晰。**依赖 license 扫描器的工具（合规流水线、企业采购清单）会把这当成非标准协议处理**——这是本日新增的可核验元数据问题。

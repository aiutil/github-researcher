The components in `native/upstream` and the files derived from them keep their own licenses (**GPL, LGPL, BSD, libpng, Unicode and Skia**), and a build that includes them follows those terms too.」而 `native/upstream/` 实际含 **18 个上游组件**，其中 **8 个是 ReactOS 的**（`reactos-controls` / `reactos-delayimp` / `reactos-installer` / `reactos-nls` / `reactos-nonclient` / `reactos-rtl` / `reactos-text` / `reactos-user32` / `reactos-utf8`），外加 libpng、Skia、Unicode。**GitHub 侧的 `license.spdx_id` 只显示 MIT。** **即：主许可正确，但上游 GPL/LGPL 组件的义务只在散文里提及、未结构化到仓库中，扫描器会给出「纯 MIT」的错误默认答案。** 这与前四类（NOASSERTION / null / 无 LICENSE 文件 / APSL 未标注）性质不同——**它是「主许可正确但组合许可被折叠」的第五类**。

### 趋势 3：「可逆」被写成机制而不是承诺——两个 Android 设备项目的同构设计（趋势分 88）

本日有两个 Android 相关项目同时冒头，且**它们解决的是同一个问题的两端**：一个管电视，一个管手机；一个用设备身份锁，一个用 10 条 agent 硬规则。**⭐ 它们的共同结构是：把「不可逆的操作」从 agent 与脚本的可达范围里拿走，而不是靠提示词请求执行方克制。**

**⭐ `xMazaki/unbloat-android-tv`（4.5 小时 174⭐ ⑂14，fork/star 8.0%，subs 1 oi 0，Java，10660 KB，14 commits，contributors 2 人）**

它是一个法语/英语双语的 Android TV 精简套件 + 自制极简桌面「Zen Home」（Apple TV 风格），含 `ecran-accueil/ZenHome.apk`（9.7 MB）、可编辑的 AndroidManifest 与 19 张壁纸素材。

**⭐ 它的「可逆」是一张带「是否改动电视」列的菜单表：**

| 菜单项 | 做什么 | 是否改动电视 |
|---|---|---|
| **1. 诊断 + 备份** | 读 Android 版本、内存、CPU、Wi-Fi；备份应用与设置列表，带截图 | **No** |
| **2. 精简** | 关闭已知广告、遥测与无用服务（Google、TCL、Sony、Xiaomi…）；**对你可能用到的功能（Chromecast、Assistant…）先问你** | **Yes, reversible** |
| **3. Zen Home** | 装极简桌面：你的标题、4/6/8 应用布局、常用应用；**也可选禁用原桌面**（原桌面通常很吃资源） | **Yes, reversible** |
| **4. 我的照片** | 换成你自己的照片 | **Yes, reversible** |
| **5. 截图** | 截当前画面 | **No** |
| **6. 全部还原** | 重新启用所有被关的东西、放回原桌面与动画、卸载 Zen Home | **Back to original** |
| **7. 换一台电视** | 改目标电视 | **No** |

**并且明写：「Nothing is ever uninstalled, except Zen Home if you ask. Apps are only *disabled* and can be turned back on in one click.」**

**⭐⭐ 三条真正的工程设计（而不是免责声明）：**

**① Identity lock（设备身份锁）：**

> The kit records your TV's serial number. Before every action, it checks that the device at that address is the same one. **Another TV, a box or a Fire Stick that gets that IP will never be modified.**

**这是对「adb 默认连第一台设备」这一真实误操作风险的具体防御**——**不是靠用户记得自己在改哪台电视，而是靠每次动作前重新核对。**

**② Protected apps（受保护应用）：**

> Play Store, Google services, settings, keyboard, WebView… **are never disabled, even if added to a list.**

**③ 单一桌面禁用边界：**

> **Option 2 never turns off the current home screen.** Only option 3 can disable it, once Zen Home is installed.

**⭐ 而且它把「可逆」的失效条件也写出来了**——这在本批里是罕见的：

> Undo: option 6. If the PC isn't available anymore, on the TV: Settings → Apps → See all apps → Show system apps → pick the app → Enable.
> **TV system updates stay enabled. After a big update, some apps may be re-enabled: just run option 2 again. This happens often on Fire TV.**

**实测数据只有一台 2019 年的 TCL（Android 9、2 GB RAM）**：空闲 CPU **61% → 12%**、可用内存 **451 MB → 720 MB**，附前后截图。

**⭐ 它的素材许可处理是本批最细致的一份**：19 张照片全部来自 Wikimedia Commons「Featured pictures」，被裁剪为 16:9 并缩放到 1920×1080；`CREDITS.md` **逐张列出**文件名、地点、作者、许可（CC BY-SA 3.0 / 4.0）与 Commons 源链接；字体 Poppins 用 SIL OFL 1.1。而 `LICENSE` 文件的尾部主动声明：

> **Note: bundled photos (ecran-accueil, assets/walls) are NOT under MIT; each keeps its own Creative Commons license, see CREDITS.md. Poppins font: SIL OFL 1.1.**

**⭐ 这与 10-24 记录的 HackiOS（NOASSERTION + APSL 2.0 且未说明自有代码条款）性质不同：这里的根 LICENSE 文件是 MIT 且明确排除了素材，缺的只是 GitHub 侧的自动识别（`spdx_id` 为 NOASSERTION）——属可机读性缺陷而非法律实质问题。**

**⭐ `rddmwmddr/android-ad-cleaner`（4.5 小时 140⭐ ⑂12，fork/star 8.6%，subs 1 oi 6，Python，MIT，4043 KB，25 commits，contributors 1 人，2 个 release）**

关掉国产安卓手机里的广告、热搜、资讯推荐与营销推送，**不 root、不解锁、不刷机，系统更新不受影响**。

**⭐⭐ 而它最有价值的资产是 `AGENTS.md`——一份写给「能在用户电脑上执行命令的 AI 智能体（WorkBuddy、Claude Code、Codex、Trae、Cursor 等）」的 10 条硬规则。** 每一条都对应一类具体的 agent 失效模式：

| # | 规则 | 对应的失效模式 |
|---|---|---|
| 1 | **每条 adb 命令都带 `-s <序列号>`**（「电脑上可能连着多台设备（电视、模拟器）」） | **设备选错**——与 unbloat 的 Identity lock 同构 |
| 2 | **正常功能不能坏**（下拉搜索、负一屏卡片、应用商店的安装和更新、浏览器、天气预警、快递和更新通知要保留） | **过度执行** |

| 4 | **不碰系统更新；不 root，不解 BL，不刷模块，不改 system 分区** | **越过授权边界** |
| 5 | **改之前说清楚，改完能还原** | **静默变更** |
| 6 | ⭐ **不替用户同意协议**——遇到用户协议、隐私政策、权限申请，点「取消」「以后再说」「不允许」「禁止」，**不点「同意」「允许」** | **代替用户做决定** |
| 7 | **不绕过锁屏**（`run.py check` 显示锁屏时请用户解锁） | **绕过用户在场的前提** |

| 10 | ⭐ **不挂这些包**（`com.heytap.quicksearchbox` 下拉搜索、`com.coloros.assistantscreen` 负一屏、各品牌应用商店）——**「挂了功能会坏，`run.py` 会拒绝」** | **破坏系统功能** |

**⭐⭐ 规则 10 是本批最值得学的一句：因为它不是靠提示词约束 agent 不做坏事，而是让工具本身在代码层拒绝做坏事。** 这与 10-24 记录的 hatchzip「Anything that can be refused is refused before the archive is touched」是同一条原则在设备操作领域的再现——**本日报连续第二天观察到「拒绝优于补救」这条工程原则。**

**风险。**

- **⚠️ `subs 0` + contributors 1 人 + 仅 8 个 commit = 一个个人项目在赛事截止日当天的一次集中发布。** 没有任何外部贡献者痕迹，也没有外部复现记录。
- **⚠️ 它的能力矩阵**基于未验证的官方文档描述与第三方捕获**，「33 个工具」的必填参数没有一条来自官方 schema。** 它自己写了这一点（`S:` 标记 + 「not an output JSON schema」），但读者容易在摘要层丢掉这个标记。
- **⚠️ 平台限制**：Python 3.11+、**Linux 或 macOS（无 Windows）**；只实现了 3 个工具中的契约回归。
- **⚠️ 它依赖官方服务的限流额度**（600 次/分钟），而官方服务规则第 3、6 条限制自动化访问——**这正是它选择离线优先的根因，也是它验证路径的天然边界。**
- **⚠️ `license.spdx_id` 为 NOASSERTION**（尽管 LICENSE 文件是 MIT 且有额外条款）——**依赖 license 扫描器的工具会给出错误的默认答案**。
- **⚠️ 官方 MCP 的许可条款禁止未经书面授权的商业使用**——**mcreplay 的 LICENSE 尾部自己也写了这句**（「This license grants no permission to use the official service commercially or outside its rules」），**但这意味着依赖该服务的任何商业产品都需要单独审视许可边界。**

**是否值得跟踪。** **值得，且跟踪方式应是「它是否被赛事之外的人采用」，而不是「它能不能获奖」。** 观察重点：**(1)** 是否出现第一个外部 fork（fork/star 4.9% 说明还没到）；**(2)** 它的工具覆盖是否从 3 个扩展（这是它能力边界最直接的指标）；**(3)** 是否有人把它的退出码接进 CI 并公开（这会验证「契约回归」这个模式是否真的有用）；**(4)** 赛事结束后（10-25 23:59 截止）的存续情况——**特别是那 122 个仓库里有多少会因为许可或无差异而消失**；**(5)** 官方是否发布正式的 schema（那会改变它的核心价值）。

### Deep Dive 2：mirkobrombin/raven（本日最值得警惕的元数据陷阱，也是最扎实的一个工程样本）

**项目定位。** 在 Linux 上跑 Windows 应用，**不用虚拟机、不用 winetricks、不用 DLL 覆盖**；**但它的 `created_at` 是 2026-10-24T17:13:42Z——这是一个改名仓库的时间戳，而它实际有 653 个 commit、最早可追到 2025-09-05。**

**为什么它值得比它的 star 数更多的注意力。**

**因为它同时提供了两样东西：一份工程上相当扎实的兼容层样本，和一个「`created_at` 会骗人」的活教材。**

**它的技术亮点：**

1. **⭐ 直接执行 + 沙箱隔离 + API 全量自实现。** 「The program's code runs directly on your CPU, inside a sandbox where it cannot reach Linux. Every call it makes to the system is answered by Raven, which plays the part of the Windows kernel and its services.」
2. **⭐⭐ 四段 25% 的兼容评分**——把「装得上 / 起得来 / 有主窗口 / 能完成真实工作流」拆成可累加的阶段，让「VLC 25%」和「Notepad++ 100%」成为可比较的事实而非印象。
3. **⭐⭐ 交替运行的 benchmark 设计。** 四轮交替 Raven / Wine / Soda，**理由写明：「so a change in machine load weighs on both」**——这是本日报见过的最基本也最常被省略的 benchmark 纪律。
4. **⭐⭐ 主动作废自己的一组数据并说明原因**（「its scene configuration was not verified against the retained samples」），同时保留旧数据供对照。
5. **⭐⭐ 公开测试跳过条件**（「or those tests are skipped」+ 五个环境变量名），而不是把跳过算进通过率。
6. **⭐ 为可复现性牺牲性能**：选软件 Vulkan，并明说「a hardware GPU raises them for every runtime」。
7. **⭐ 前缀快照与回退**（每个应用一个 `RAVEN_PREFIX`，每次安装器前快照，`--restore-prefix` 回退）。
8. **⭐ 混合上游来源的诚实声明**（自建 MIT + ReactOS/Skia/libpng/Unicode 各自许可）。

**风险。**

- **⚠️⚠️ 最大的风险是元数据层面的：`created_at` 不可信。** 任何自动化流程——包括本日报自己的「今日新项目」筛选——若只用 `created_at`，会把这个 14 个月的项目当成 4 小时前的新项目。**修正后的原则：必须用 `commits` API 交叉验证。**
- **⚠️ 单作者**（contributors API 返回 1 人）、**subs 1**、**无 release**（分发路径是从源码构建）。
- **⚠️ GPL 义务只在散文里**：根 `LICENSE` 是 MIT，`license.spdx_id` 也是 MIT，但 `native/upstream/` 静态引入了 9 个 ReactOS 组件（GPL/LGPL）——**这是本日新增的第五类许可元数据问题：「主许可正确但组合许可被折叠」**，扫描器会给出「纯 MIT」的错误默认答案。
- **⚠️ 它自己列出的限制**：只支持 Windows 应用（不是游戏生态）；`native/upstream/reactos-user32/` 下只有 `bridge.c`/`register.c`/`scrollbar_control.c`/`shim` 四个文件，**说明 ReactOS 组件是按需挑选的移植而非全量引入**（这既是好消息也是限制——未移植的部分如何处理，本窗口未核验）。
- **⚠️ 性能优势的边界**：软件 Vulkan 下 71.5 vs 63.0 FPS 的差距在真实商业应用上未必线性；**且这 8 个逻辑 CPU 的环境不具代表性。**
- **⚠️ 未经第三方复现**：全部 benchmark 为作者自述。

**是否值得跟踪。** **值得，且这是本日唯一一个「应当被当作方法论样本而非产品候选」的项目。** 观察重点：**(1)** 兼容矩阵的实际规模（`cmd/compat-matrix` 与 `internal/compat/matrix.go` 的数据来源本窗口未核验，这是它最核心也最未知的部分）；**(2)** 是否发布 release（当前只能从源码构建，对采用是硬门槛）；**(3)** ReactOS 上游组件清单是否被结构化到仓库里（对应第五类许可问题）；**(4)** 是否支持 ARM64 宿主；**(5)** 它是否继续在自己的仓库里维护 `docs/benchmarks.json` 里被作废的数据——**这是「作废数据是否留痕」的一个长期观察点。**

### Deep Dive 3：songjianyang/xss-audit（本批最高 fork 比例，而它只有 15 KB）

**项目定位。** 一份 26 KB 的静态 XSS 审计规程（agent skill），4.6 小时 194⭐ ⑂50（**fork/star 25.8%，本批最高**），MIT，**仓库仅 15 KB、仅 1 个 commit、contributors 1 人、无 release、subs 0**。

**为什么它值得比它的 star 数更多的注意力。**

**因为它是本日唯一一个「产物是文字」的热门项目，而它的质量控制方式恰好是它自己文档结构的一部分。**

**它的技术亮点（准确地说，是它的规程设计）：**

1. **⭐⭐ 14 层覆盖的是真实的 sink 分类**，包含 mXSS、SVG/MathML 命名空间混淆、JSON-in-script 的 `</script>` 逃逸、原型污染链、CSS-in-JS 插值、框架信任钩子、模板注入——**不是「搜索 innerHTML」的简化清单**。
2. **⭐⭐ 开篇的 Reality check 把清单本身的局限说在前面**：「none of these measures guarantees complete protection on its own」。
3. **⭐⭐ 执行规则把失效模式显式化**：不得跳过任何搜索类别、不得因文件名判断安全、必须逐个追数据流、必须按**正确上下文**（HTML/attribute/URL/JS/CSS）检查消毒。
4. **⭐⭐⭐ 点名了具体的 URL 校验反例**：`new URL('javascript://trusted.com/%0aalert(1)').hostname` 是 `trusted.com`——**只校验 hostname 是不够的**。
5. **⭐⭐⭐ 要求把「排除项与未读文件」记进报告**，并单列 manual-review 区——**一份「我检查了哪里、没检查哪里」的账本**。
6. **⭐⭐⭐ 示例报告第一行就写「Fictional example… no reproduction steps were executed」**——**在一个「输出格式即卖点」的品类里，唯一示例被明确标注为虚构且未经执行**。
7. **⭐ `SECURITY.md` 把工具的输出流向也管起来**：在别的项目里发现的漏洞报给那个项目，不是这个仓库；公开 issue 不含凭据与未脱敏利用报告。

**风险。**

- **⚠️ subs 0 + 1 个 commit + 15 KB + contributors 1 人 = 一份被当作 skill 分发的静态文档，尚无社区共建。**
- **⚠️ 它声称的漏洞发现数与 MSRC 排行榜排名本日报无法核验**（附了 leaderboard 与 X 主页链接，但排行榜是外部页面）。
- **⚠️ 静态分析必然有假阳与假阴**——README 自己写了（「Static analysis can produce false positives and false negatives, especially for dynamic runtime behavior, build-time transforms, excluded code, and framework-specific execution timing. Review exclusions and verify findings before relying on them. No coverage is guaranteed.」）。
- **⚠️ 报告可能包含敏感信息**——README 自己警告：「Generated reports may contain sensitive paths, source code, internal domains, or credentials. Review and sanitize them before sharing.」
- **⚠️ 25.8% 的 fork 比例不可读作「质量更高」**——它对应的是「改一份 26 KB 的 Markdown 几乎零成本」。

**是否值得跟踪。** **值得，但作为「规程设计的样本」而非「安全工具」。** 观察重点：**(1)** 是否出现第二个 commit（即是否有人补上更新机制——**静态清单会随浏览器 API 演进而腐化，这一点它自己也承认**）；**(2)** 是否有外部使用者发布用它做的真实审计报告（**这是判断它是否真的被用的唯一信号**）；**(3)** 14 层是否扩展到它点名但未覆盖的 API（如 Trusted Types 的实际落地路径）；**(4)** 是否有 fork 改造成支持其他框架/语言的版本——**这正是 25.8% fork 比例最可能的去向**。

## 风险与机遇

### 机会

1. **⭐⭐⭐ 「未验证」可以是产品的一部分，而不是免责声明。** mcreplay 的 `capability-matrix.md` 首行写「No authenticated calls were possible… All reliability judgments below are provisional」**并仍被发布**，同时另一份文档记录了实测。**并行保留两份互相矛盾的证据，是本日报见过最难的诚实形式，也是最值得抄的形式**——它比「只写一份并标注可信度」更有信息量，因为读者能看见认知的推进过程。
2. **⭐⭐⭐ 让「破坏性变化」成为 CI 的退出码，而不是一句警告。** mcreplay 的 0/1/2/3 四档退出码 + `breaking`/`review`/`info` 三级分类，是一个可以原样搬进任何「上游 API 会漂移」场景的设计。**它与 10-24 记录的 oss-verify `oft check`（在 `Print Assumptions` 阶段拒绝越界公理）属于同一族：让检查器真的会拒绝。**
3. **⭐⭐⭐ 把「不可逆的操作」从执行方的可达范围里拿走。** android-ad-cleaner 的 `run.py` **会拒绝**挂载受保护包（不是提示 agent 别挂）；unbloat 的 Identity lock **每次动作前核对序列号**（不是提醒用户记着自己在改哪台电视）。**⭐ 这与 10-24 记录的 hatchzip「Anything that can be refused is refused before the archive is touched」是同一条原则——而本日它在设备操作领域再现，说明这条原则正在从单项目走向品类惯例。**
4. **⭐⭐ 把「我不会做什么」写成给 agent 的硬规则，并且逐条对应一种失效模式。** android-ad-cleaner 的 `AGENTS.md` 10 条，其中「不替用户同意协议」「不截账号页」「不用 `pm uninstall` / `pm disable-user`」三条是本批唯一直接处理「agent 代替用户做决定」与「agent 泄露隐私」的项目。**在 agent 正在获得设备操作权的 2026 年，这份文件值得被直接抄。**
5. **⭐⭐ benchmark 的两个基本动作：交替运行 + 主动作废并留痕。** raven 的「四轮交替以抵消机器负载」与「These replace the earlier ClassiCube series; its scene configuration was not verified」+ 旧数据留在 `docs/benchmarks.json`，是任何做对比测量的团队都该抄的两步。**本日报已连续记录多日「实测 vs 估计」的区分，而这是它最完整的两个样本。**
6. **⭐⭐ 跳过条件要写进 README，而不是算进通过率。** raven 明写五个环境变量与「or those tests are skipped」。**这比「ctest 全绿」诚实一个量级**，且几乎零成本。
7. **⭐⭐⭐ 参赛者自己写的竞品分析，是判断生态质量最可靠的样本。** mcreplay 逐个检视 10 个对手后写下「It would be inaccurate to label every competitor a 'thin AI wrapper.'… several contain deterministic engines and defensive transport.」**⭐ 这构成本日报连续第二天记录的「热度不等于价值」的第一个反例——**而且它来自一个正在比赛中的参赛者之手，比任何外部评论都更有说服力。** **任何做生态扫描的团队都该把这种「读可执行代码并记录 SHA」的方法抄过去。**
8. **⭐⭐ 素材许可逐张署名 + 根 LICENSE 主动声明排除，是混合许可项目的正确做法。** unbloat 的 `CREDITS.md` 逐张列出 19 张 CC 照片的作者、许可与源链接，`LICENSE` 尾部明写照片不在 MIT 之下、字体为 SIL OFL 1.1。**⭐ 这比 10-24 记录的 HackiOS（APSL 2.0 且未说明自有代码条款）高出整整一个层级。**
9. **⭐⭐⭐ 「可逆」必须连失效条件一起写出来。** unbloat 明写「系统更新后部分应用可能被重新启用，需再跑一次选项 2」并给出电视侧的兜底还原路径。**只写「可还原」而不写「什么情况下会失效」的文档，在用户真正需要还原时是无效的。**
10. **⭐⭐ 本日报自身的教训可迁移：任何自动生成的索引字段，都必须能被一条命令验证。** 今日修正的 `Macintosh/Snapintosh` → `Snapintosh/Snapintosh` 是一个 4 天、三处落盘、无人发现的错误——**而验证它只需要 `gh api repos/Snapintosh/Snapintosh` 两秒。** **在有 749 个项目档案的仓库里，这条原则的杠杆最大。**

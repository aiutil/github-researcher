⭐⭐⭐⭐⭐ **方向二：同一账号矩阵可以同时承载多个家族，这是比「命名词根」更硬的判据。**

## 风险与机遇

**⭐⭐⭐⭐⭐ 风险一：投放体开始「认领」上游，镜像的授权状态成为新的攻击面。**
本日 21 个镜像在 README 里逐字保留上游的 credits 表，却把 `LICENSE` 从 MIT 换成 Apache-2.0，并把唯一的下载入口换成一条 Dropbox 链接。⭐⭐⭐⭐⭐ **后果是：上游作者的名誉与 star 被搬运，而用户的下载行为被导向投放者控制的地址。**⭐⭐⭐⭐⭐ **这类形态用「仓库是否为空壳」完全查不出来 —— 镜像仓有 53 个真实 Go 文件、53 个 commit、Apache-2.0 许可。**

**⭐⭐⭐⭐⭐ 风险二：账号矩阵提示投放基础设施已是「多家族并行」。**
本日实测同一个账号在 3 个家族里各持 9–10 个副本 + 主仓库 + 占位仓库，⭐⭐⭐⭐⭐ **即投放方同时运营多条产品线，每条线用不同的名字和不同的诱饵。**⭐⭐⭐⭐⭐ 这意味着**逐日单窗口的观察会系统性低估投放规模**，⭐⭐⭐⭐⭐ 而「把 owner 账号作为追踪主键」能一次性看到全部家族。

**⭐⭐⭐⭐⭐ 风险三：`steam-library-bridge` 的 release 结构是「用版本号伪造历史」的新样本。**
4 个 release、8 个 asset、版本号从 1.2.8 一路到 4.4.2，⭐⭐⭐⭐⭐ 但只有 1 个 commit。⭐⭐⭐⭐⭐ **用户看到「更新到 v4.4.2」会默认认为经历了 4 次迭代。**⭐⭐⭐⭐⭐ 同时注意它的 `subs 19` 相对 176⭐ 是**本日真项目里最高的 subs/star 比之一**，⭐⭐⭐⭐⭐ 而它的账号只有 12 天、0 followers —— ⭐⭐⭐⭐⭐ **这说明「subs 高」在本日再次不是「关注真实」的证据（与 11-15 记录的一致）。**

**⭐⭐⭐⭐⭐ 风险四：许可判据本身需要修正。**
`interspace` 的 `license.spdx_id` 是 `NOASSERTION`，但 LICENSE 文件明确写着 MIT；⭐⭐⭐⭐⭐ **若只按 `spdx_id` 判「无许可」，会误判。**⭐⭐⭐⭐⭐ 反过来，`Gemini-Config-Checker-` 的 `spdx_id` 是 Apache-2.0，⭐⭐⭐⭐⭐ **但它是从 MIT 上游复制后改写的 —— 若只按字段判「有许可」，也会误判。**⭐⭐⭐⭐⭐ **结论：许可必须读文件，且要读仓库内的第三方声明文件（mixbar 的 `THIRD_PARTY_NOTICES.md` 是范例）。**

**⭐⭐⭐⭐⭐ 机遇一：「blob sha 比对」把镜像检测的成本降到了接近零。**
不需要下载任何内容，不需要比较 README 文本，⭐⭐⭐⭐⭐ 只要 `git/trees` 的 blob sha 一比就知道字节是否相同。⭐⭐⭐⭐⭐ **这可以做成一个零成本的每日巡检项。**

**⭐⭐⭐⭐⭐ 机遇二：`pydtcpip` 的「能力矩阵 + 三档验证状态」是可迁移的模板。**
`Verified` / `Unverified (profile implemented)` / `Not applicable` 三档，⭐⭐⭐⭐⭐ 把「支持什么」和「验证过什么」分成两个正交维度，⭐⭐⭐⭐⭐ **任何「支持 N 种设备/模型/平台」的项目都可以直接抄。**

**⭐⭐⭐⭐⭐ 机遇三：三种「诚实边界」的落点已经成型，可直接抄。**
`AGENTS.md` 的否定式清单（pydtcpip）/ `pre-commit` 可读的预算清单（coordinator）/ README 的签名校验条款（interspace），⭐⭐⭐⭐⭐ **共同点是：边界写在机器会读到的地方，而不是散文里。**

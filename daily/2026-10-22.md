### 趋势 2：把「等补丁」这段空窗期做成可安装软件（趋势分 89）

`HOSTED-POWER/php_uploadprogress_guard`（53⭐ ⑂4，C，MIT，12 小时）是今日四个项目里唯一**不是 PoC 也不是 PoC 检测**的项目，也是唯一一个把缓解措施本身当作产品来交付的。它的核心动作是把官方补丁**逐组件镜像**进一个可加载的 PHP 扩展，从而「在未打补丁的 PHP 上移除已公布攻击链的每一环」。

它的 README 从一个反直觉的建议开始：**「Install the official PHP release… we recommend it without reservation. This module protects an unpatched PHP for real.」** 并给出理由——包管理器可能明天就供上补丁，也可能永远不供（发行版停更的 LTS、嵌入式设备、被厂商锁死的 appliance）。这个表述把项目的定位卡得很准：**它不是补丁的替代品，是补丁的候补**。

技术上三个机制（README 明示）：v3.0.0 **移除 session upload-progress handler** + **携带修复版 parser** + **让 parser 本身不可能 OOM**（headroom guard 保留 `memory_limit` 的八分之一）；`mode=native` 改为在 OOM 时直接结束进程（exit 137）而非继续服务下一个请求；`mbstring.encoding_translation=On` 的宿主交还给 PHP 自带 parser，因为 mbstring 的多字节 hook 是 file-static、无法镜像（但 callback detach 仍然生效）。

**最见工程功力的是「自检让位」机制**：用 `nm -D` 探测引擎是否导出了修复符号，已带官方补丁就报告 `carries the official fix => yes (fix symbol exported by the engine; parser replacement skipped)`。README 给出了逐版本的结果：Sury 的 5.6.40-104 / 7.0.33-92 / 7.3.33-35 / 7.4.33-31 / 8.1.34-9 / 8.3.36-1 全部报 yes，官方 docker 的 8.4.11 / 8.1.20 / 7.4.33 / 5.6.40 全部报 no 且全部机制 active；并说明「Neither fix symbol exists on any unpatched engine (`nm -D`)」。这意味着**装了它的机器在升级 PHP 后会自己退场，不需要任何人工卸载动作**——这是临时缓解方案最重要的工程属性。

### 趋势 3：大厂把研究原型当研究原型发布（趋势分 86）

`NVIDIA/flare-local-inference`（485⭐ ⑂47，fork-star 9.7%，Apache-2.0，NVIDIA 官方组织，2 天）的 README 有一个细节值得单独记：**第一句是对 agent 说的**——「**Coding agents: skip this README and read AGENTS.md directly.**」

架构上，它把「构建期」与「运行期」切成一条硬边界并写进代码库结构：

- `ignition/`（Python 包）用 PyTorch、Transformers、FlashInfer/b12x 加载模型、调 kernel、编译 forward、把 CUDA graph 捕获成运行时包

四条设计原则里最有信息量的是第三条：**「Make memory and state explicit. Plan buffers and execution capacities ahead of time. Treat conversation state—including recurrent state alongside KV caches—as a whole, so reuse, branching, and resuming preserve it correctly.」**——把循环状态（recurrent state）与 KV cache 当作一个整体来规划，正是 2026 年 serving 设计的核心争论点，而 README 把它列为原则而非实现细节。

**它同时划了两条非常少见的边界**。第一条在 README：「Flare is not, and will never, be a replacement for production inference engines like vLLM.」第二条在 `AGENTS.md`，而且是**面向所有贡献者（含 agent）的三类驳回标准**：

- **拒绝未批准的范围扩张**：CPU 或非 NVIDIA 执行、可互换执行后端、训练或微调、多模型托管与路由、无关服务 API、通用集群编排——「均需维护者明确决定后才能实现；已支持的跨节点准备与服务**不授权**这些新增」
- **拒绝架构违规**：生产 Python 回调、eager serving、运行期编译或重捕获、稳态 GPU 分配、模型特定原生策略或状态更新算法、准备元数据中的可执行扩展机制——并补一句「**Flags, enums, callbacks, optional paths, and temporary implementations cannot be used to bypass them**」
- **拒绝削弱保证**：完整缓存与投机状态、非活跃行行为、异步资源生命周期、checkpoint 精度、模型语义、模型包兼容性；「**不得删除校验、压制错误、静默替换执行路径，或放宽参考值、工作负载与数值边界来换取通过的检查或好看的指标**」

还有一句直接针对 agent 生成的贡献：**「Hypothetical future consumers, agent-generated suggestions, and lint findings alone do not establish a need for a change.」** 并且把发版纪律写成流程：进入 clone 后与 pull 后必须重读 `AGENTS.md` 与 `docs/design-review.md`，提交前启用 `.githooks/commit-msg` 钩子并按该文档做 **staged-diff 复核**；「A rejected acknowledgment requires reading that document and reviewing the staged change before retrying; **do not treat the rejection as a formatting repair**」——最后这半句是针对「agent 收到拒绝后当成格式问题去改」的防御性设计。

### 趋势 4：多 agent 终端从「多标签」到「多 agent 状态机」（趋势分 84）

`dominikmartn/harp`（527⭐ ⑂29，Rust，AGPL-3.0 但 `warpui` 与 `warpui_core` 两个 crate 为 MIT，217 MB，个人项目，**2 天 4 个 release**：v0.1.0 10-20 11:13Z → v0.1.1 13:43Z → v0.1.2 18:09Z → v0.1.3 10-21 10:29Z）是 Warp 的非官方 fork，核心动作一句话说清：**把 tab bar 换成专门为长跑型 coding agent 设计的侧边栏，其余保持 Warp 原样**。

侧边栏每行显示的状态是：**working / waiting for you / done / inactive**，配一个「未读标记，直到你真的看过才消失」；一个**小圆点**表示后台任务仍在跑；一个**月亮**表示你把这个 tab 置入了暂存；`Cmd+R` 重命名 tab。

**限额环（limit rings）是本项目最可借鉴的设计**。每个 provider 两个环——**5 小时窗口**与**周限额**，悬停显示数字与重置时间。数据来源分两种，README 说得很清楚：

- **Codex**：从 `~/.codex/sessions`（或 `$CODEX_HOME`）里的 `rate_limits` 日志读；Codex 至少回答过一次后环才出现
- **Claude Code**：Claude Code 只把计划限额交给 status line。**Harp 首次启动时若 `~/.claude/settings.json` 里还没有 `statusLine`，Harp 会自己加一个**——把 status line 的输入存到 `~/.harp/claude-statusline.json` 且不打印任何内容；**已有的 status line 保持不动**（想两者兼得，需要自己先把输入落盘，例如 `"command": "tee ~/.harp/claude-statusline.json | your-command"`）；环在 Claude Code 下一次回答后出现；**只对 Claude.ai 计划有效，API key 无效**

并且它把信任边界写成了三句否定：**「Harp fetches nothing and reads no credentials.」**「Everything else is upstream Warp… They talk to Warp's servers exactly as upstream does; **Harp adds no servers of its own**.」「**Logging in through Harp is untested.**」

**tmux 集成的思路同样值得记**：打开后，分组名与顺序存在 **tmux session 本身**上，因此**跨重启存活，且其他 tmux 客户端看到同一布局**；从手机 ssh 起的 session 可以用 `tmux set-option @warp_adopt 1` 认领一个 tab。默认关闭，开启后每 10 秒轮询。

**它还明确列出「故意移除」的东西**：tab bar 的搜索框、视图选项、tab 配置按钮、侧边栏分隔线选项、标题条面板开关。以及调试开关的用途——`WARPOSS_STATUS_TRACE=1` 把每一行状态的每次变化写成 `~/Library/Logs/harp.log` 的 `[status-check]` 行，「以对照某个 agent 的 transcript 做回归检查」；`WARPOSS_SKIP_LOGIN=1` 用测试用户启动并让所有认证请求失败以便自动化。

## 最值得关注的方向

今天四个项目分属三个领域，但共享一个更值得记的判断标准：**README 里的「我不做什么」，比「我能做什么」更能预测项目会不会活下来。**

- **php_uploadprogress_guard** 的 README 第一句是「先装官方发行版，我们无条件推荐」，第二句才是「本模块真实保护未打补丁的 PHP」。**主动劝退自己的项目，通常比夸大能力的项目更可信**。加上它把两次自身回归（v3.0.0 在 PHP 7.x 上拒绝所有 multipart、v3.0.1 的二进制在 Debian 12 上加载失败导致**PHP 继续运行但没有 guard**）直接写进 README——第二个回归尤其值得注意，因为它意味着**用户可能在毫无察觉的情况下处于「以为装了、其实没生效」的状态**。
- **Flare** 把同样的态度制度化成了 `AGENTS.md` 的三类驳回标准，并显式声明「agent 生成的建议本身不构成变更理由」。在一个越来越多项目开始接受 agent PR 的时期，这条规则的价值会随时间上升。
- **Harp** 的反向声明同样是硬边界：「Harp 不自建任何服务器」「通过 Harp 登录未测试」「Harp 不读取任何凭据」「有意移除了 tab bar 的搜索框、视图选项、tab 配置按钮」。
- **openai/php2shell-checker** 在一个所有人都在抢发「一键检测」的窗口里写「UNKNOWN 不等于已打补丁」「我不独立验证安全修复」——**在一个事件驱动的热度洪峰里，主动写出自己结论的不可用边界，是本日最反常也最值得学的动作。**

## 重点项目深度分析（top 3）

### Deep Dive 1：HOSTED-POWER/php_uploadprogress_guard（把「等补丁」做成可安装、可自检、会自己退场的软件）

**项目定位。** 宿主托管商 Hosted Power 为自家机队构建的 PHP 扩展，公开给所有人。12 小时 53⭐ ⑂4（fork-star 7.5%），C，MIT，5750 KB，`subscribers_count = 4`，`open_issues_count = 2`，覆盖 PHP 5.6–8.5 与 Sury / Remi / cPanel EA4 / DirectAdmin CustomBuild / 官方 Docker 镜像。

**为什么它值得比它的 star 数更多的注意力。** 因为它回答的是一个具体到可以立即执行的问题：**你的机器今天就要被攻击，但你的发行版要三个月后才供上补丁，或者永远不会（嵌入式 appliance、被厂商锁死的管理界面、LTS 已停更）——那这三个月怎么办？** NCSC-NL 的公告恰好点名了这一类机器（「PHP is also embedded in appliances, network devices, management interfaces and other vendor products where administrators may not be able to update PHP directly」）。这个缺口此前只能靠手改 `php.ini` 或加 WAF 规则顶，而这两者都不改引擎内部。

**技术亮点（全部可核验于 README）：**
- **逐组件镜像官方补丁**，覆盖 PHP 5.6–8.5 十二个 minor，每分支每 SAPI 单独测试
- **三个机制**：移除 session upload-progress handler（对 109619）· 携带修复版 parser 并让 parser 本身不可能 OOM（对 109618，headroom guard 保留 `memory_limit` 的八分之一）· `mode=native` 在 OOM 时直接结束进程（exit 137）而非让半初始化状态继续服务下一个请求
- **自检让位**：用 `nm -D` 探测引擎导出的修复符号，已打补丁则报告 `carries the official fix => yes` 并跳过 parser 替换——**升级后自动退场，无需人工卸载**
- **两处诚实降级**：mbstring 的多字节 hook 是 file-static 无法镜像 → `mbstring.encoding_translation=On` 的宿主交还给 PHP 自带 parser（callback detach 仍生效）；8.0–8.3 的副本不再依赖中途才加入的 `max_multipart_body_parts`
- **孤儿临时文件这一条最容易被忽略**：`mode=native` 下 worker 因 `child exited with code 137` 被回收且 0 孤儿上传临时文件，而**原生 PHP 启动失败会留下 1 个（`code 70`）**——在共享主机上这是磁盘耗尽的一个真实来源
- **12 个二进制全部 `GLIBC_2.14` 以下**，零编译警告，修复探针以 versionless weak reference 形式存在（`objdump -T` 可查）
- **两次自身回归写在 README**：v3.0.0 修了 v2.2.0 在 PHP 7.0–7.4 上拒绝所有 multipart 请求的 bug（原因：读取了 8.0.28 才存在的 ini）；v3.0.1 修了 v3.0.0 二进制在 Debian 12 及更早上因 `GLIBC_2.38` 无法加载、**导致 PHP 继续运行但 guard 未生效**的 bug

**风险。**
- **`dist/` 里是二进制 .so**：即使有 SHA256SUMS，宿主仍需信任发布者。这是所有「预编译缓解方案」的共同性质，也是本项目最大的信任假设
- **维护是单人 + 一个托管商**：上游 PHP 若在 Zend 引擎结构上做新改动，镜像可能失效；README 未说明跟进机制
- **与 WAF 的关系未讨论**：把 `session.upload_progress.enabled=Off` 这类官方缓解（NCSC-NL 列出的第一条）与本扩展叠加是否会冲突，README 未涉及
- **`subscribers_count = 4`**：这不是被广泛验证的工具
- **「PHP 继续运行但没有 guard」这个失败模式值得用户自查**——README 自己写下了这个回归，说明它真实发生过

**是否值得跟踪。** **值得，且优先级高于它的 star 数。** 理由与热度无关：**它是本日唯一一个把「临时缓解方案」当作长期工程对象来做、并把「自己会退场」写进机制设计的项目**。这两条（可复现的验证记录 + 自动让位）正是所有临时缓解方案通常缺失的部分。**观察重点：`dist/` 二进制的信任模型是否被独立验证（README 给了 SHA256SUMS 但发布者即构建者）、12 分支持续矩阵如何维护、以及是否会有第二个维护者出现。**

### Deep Dive 2：NVIDIA/flare-local-inference（研究原型的发布方式本身就是技术信号）

**项目定位。** NVIDIA 官方组织的本地推理服务器，面向 SM120/SM121 GPU，定位「long conversations, coding agents, and repeated tool use」，2 天 485⭐ ⑂47（fork-star 9.7%，本批最高），Apache-2.0，22386 KB，`subscribers_count = 5`，`open_issues_count = 8`。README 明写：**「This is a research prototype, and is made available via open-source to enable technical collaboration and collect early feedback.」**

**最值得记的技术判断（README 四条原则）：**
- **构建期拥抱标准 PyTorch 生态，运行期用 Rust**——`ignition/`（Python）负责加载/调 kernel/编译 forward/捕获 CUDA graph 并打包，`flare/`（Rust CLI）链接 `helios/`（Rust 运行库）在无 Python 的情况下服务该包。AGENTS.md 明确了依赖方向：**Helios 被 Flare 与 Heliopause 依赖，而 Helios 没有任何 Python 或准备工具的依赖**
- **复用规范模型实现，只为布局或执行确实不同的部分做特化**——这是对「什么都自己重写」的直接否定
- **把内存与状态显式化**：提前规划 buffer 与执行容量；**把会话状态连同循环状态与 KV cache 当作整体**，使复用、分支与恢复都能正确保持
- **运行时保持小而专**：模型配方负责模型计算，运行时负责调度、缓存存储与请求处理
- **编译与图捕获在服务之前完成**——运行期不编译

**最值得记的非技术判断（AGENTS.md）：** 这是本日唯一把「拒绝什么」写成制度文件的项目。三类驳回标准之外，还有两条常被忽略的补充：其一，「**Hypothetical future consumers, agent-generated suggestions, and lint findings alone do not establish a need for a change**」——直接拒绝以「未来可能有人用」或「agent 建议」为理由的贡献；其二，发版纪律要求提交前启用 `.githooks/commit-msg` 钩子并按 `docs/design-review.md` 做 staged-diff 复核，且「**被拒绝的确认不得当作格式修复处理**」——这是针对「agent 把架构评审的拒绝当成 lint 报错去改」的防御性设计。

**风险。**
- **研究原型，无 release**：`releases` API 返回空数组，启动路径需自行按 `docs/` 构建
- **硬件门槛硬**：仅 SM120/SM121，`vLLM 覆盖更广的模型、硬件与部署形态`——覆盖面确实窄
- **`subscribers_count = 5`，8 个 open issues 在 2 天内**——早期项目的正常状态，不能读作质量信号
- **README 几乎不给出性能数字**：30+ 份设计文档（`scheduling-theory` / `prefix-cache-offload` / `mtp-design` / `roce-ring` 等）存在，但 README 首页没有任何 benchmark 表格——**架构主张与实测证据之间目前有可见的落差**
- **贡献闸门严格可能拖慢采纳**：对外部贡献者而言，被 AGENTS.md 明确拒绝的范围（训练/微调、多模型托管、CPU 执行）恰好覆盖了不少人最想做的事

**是否值得跟踪。** **值得，理由是它提供了一份「研究原型该如何被公开」的完整样本**——尤其是 `AGENTS.md` 的驳回标准与 staged-diff 复核流程，可以直接被抄进任何有 agent PR 的开源项目。**观察重点：是否开始发布带 benchmark 的 release、SM120/SM121 之外是否扩展、以及贡献闸门在实际协作中是否真的挡住了架构违规（看 issue 里被拒绝的 PR 类型）。**

### Deep Dive 3：ikow/php2shell-poc（五条链 + 一键靶场 + 四类规则，但 star 数度量的是事件而非采用）

**项目定位。** 个人研究者 Qi Deng 的 CVE 研究与利用工具包，13 小时 859⭐ ⑂308，Python，2706 KB，`subscribers_count = 4`，`open_issues_count = 2`。

**必须先讲的一件事：它的热度不是技术指标。** 859⭐ 出现在创建后约 13 小时，而**最关键的 Chain D 与 Chain E 的利用代码放在付费 Substack 订阅之后**（README Disclaimer 明写），公开的 `exploit/` 只有 A/B/C 三条链。也就是说：**star 数最高的那部分价值，恰好是免费拿不到的**——这与「star = 工具被采用」的常规读法完全不同。同时它引用的「影响 78% 网站、WordPress 43%」是**作者主张，本日报未独立核验**；相比之下 `NCSC-NL/php2shell` 给出的是 `software/` 目录里的具体产品清单，这种形式更可核验。

**技术亮点（可核验于 README 与仓库树）：**
- **五条链各自标注「是否预认证 / 需要什么条件 / 适用哪个 SAPI」**，Chain D 明确标为「**Conditions: None — any endpoint**」「mod_php」，并被作者自己判为最关键
- **`lab/` 一键靶场**：`docker-compose.yml` 同时起 PHP-FPM + nginx + Apache mod_php，另有 `php-apache.ini` 与 `setup.sh`
- **`poc/` 五个验证脚本**逐链对应，含 ASAN 版 `verify_uaf_asan.php`（对 UAF 类问题用 ASAN 是标准做法）
- **`detection/` 四类规则**：Suricata/Snort IDS、Sigma SIEM、ModSecurity WAF、OpenResty/Nginx Lua 模块——**同一仓库同时覆盖网络层、SIEM 层、WAF 层与应用层**
- **缓解建议附边界声明**：`session.upload_progress.enabled = Off` + `session.use_only_cookies = On`，并明写「**The only complete fix is patching PHP… The OOM corruption (Chain D) is in the Zend engine core — no INI setting fixes it.**」——**明确否定了「改 ini 就行」的流行说法**
- **下游影响表**逐框架标注条件（WordPress 核心不用 PHP session 但 WooCommerce 与多数插件用；Magento 在维护模式下仍受影响；Laravel 的 `PendingBroadcast` 是已知 `__destruct` gadget）

**风险。**
- **⚠️ 许可证不一致（可核验）**：GitHub API 的 `license.spdx_id` 为 **null**（NOLICENSE），而 README 末尾写 **MIT**。以 GitHub 侧为准则**无授权**。对要复用其检测规则或靶场配置的人，这是必须先澄清的问题
- **最关键的利用代码不公开**：D/E 链在付费墙后
- **`subscribers_count = 4` / `oi = 2`**：这是事件驱动的注意力，不是深度关注
- **NOLICENSE 的连带影响**：`detection/` 里的规则能否被安全地内嵌进商业产品，取决于许可证澄清的结果
- **同时存在的多个竞争 PoC**：`eness/php2shell-...-PoC`（530⭐ ⑂94）、`9bie/php2shell-bypass-aslr-exp`（356⭐ ⑂130）、`Zer061/CVE-2026-109618`（52⭐ ⑂39）、`junaire/CVE-2026-109618-exploit`（74⭐ ⑂49）等，多数**无 license 或无 description**——生态碎片化明显，也说明本仓库的优势不在唯一性而在完整性（链 + 靶场 + 检测三者齐备）

**是否值得跟踪。** **作为研究材料跟踪，作为依赖不推荐。** 理由：它的**检测规则**（四类）与**靶场配置**是可直接复用的资产，值得抽取；它的**利用代码**部分在付费墙后，价值不可核验；而 NOLICENSE 与 MIT 的不一致必须在复用前解决。**观察重点：仓库是否补上 LICENSE 文件、四个检测规则是否被主流 WAF/IDS 项目（如 Corelight README 中提到的社区规则）合并、以及 Chain D/E 的公开程度。**

## 风险与机遇

### 机会

1. **「临时缓解方案」是一个被低估的产品形态。** php_uploadprogress_guard 证明了一件事：**在官方补丁到达之前的那段窗口里，有真实且迫切的需求，且这个需求可以做成有版本、有测试、有退场机制的正经软件**。这对任何做基础库、运行时、协议的项目都适用——不只是安全事件。
2. **在事件洪峰里主动写「我不做什么」，是本日最稀缺的动作。** openai/php2shell-checker 写「UNKNOWN 不等于已打补丁」「我不独立验证安全修复」；guard 写「我们无条件推荐官方发行版」；flare 写「不是也不会是 vLLM 的替代」。**热度越高，这类声明的价值越大**，因为它替代了本该由用户承担的验证成本。
3. **把贡献边界写成机器可读的文件，而不是散落在 CONTRIBUTING 里。** flare 的 `AGENTS.md` 把「拒绝什么」列成三类可执行标准，并明确「agent 生成的建议本身不构成变更理由」。在 agent 参与开源贡献越来越多的当下，这类文件本身就是一种防御机制。
4. **agent 状态管理正在成为独立的一层。** harp 证明「多开几个 agent」带来的真问题不是终端多标签，而是**「哪一个在等我」**。五种状态 + 未读标记 + 后台圆点 + 置入暂存 + 双 provider 限额环，是一套不需要模型就能做的信息设计；其中「限额从本地日志与 status line 读、不读任何凭据」的信任边界尤其值得借鉴。
5. **国家 CERT 仓库是 CVE 响应的高质量参考物。** `NCSC-NL/php2shell` 以 EUPL-1.2 + TLP:CLEAR 发布，`software/` 目录放受影响产品清单而非「78% 网站」这类统计，并引用 CERT-EU 编号 2026-018 与其他成员国 CSIRT 公告——**「给具体产品名」比「给一个百分比」有用得多**。

### 风险

1. **CVE 事件的 star 数与技术价值脱钩，且这种脱钩有明确机制。** 本日排名第一的趋势是事件驱动：13 小时 859⭐，而最关键的利用代码在付费墙后，最常用的资产（检测规则）反而不需要 star 数来评价。**今天的热度排序对技术选型没有参考价值**——这与昨日「fork-star 普遍偏低说明热度更像曝光」的观察是同一个问题的两面。
2. **预编译二进制的分发仍是信任问题。** guard 的 `dist/` 提供了 SHA256SUMS，但发布者即构建者，没有独立签名或第三方构建。这类方案在安全事件中的可信度高度依赖读者是否验证——而 README 明确鼓励「install the official release」，恰恰说明作者自己也把它定位为候补而非首选。
3. **NOLICENSE 与 MIT 自述不一致。** php2shell-poc 的 GitHub 侧 `license.spdx_id` 为 null。这是**可核验的事实**，也是本日报中唯一一处元数据与自述直接冲突的记录——在安全事件这种「大家都在复制粘贴」的场合，许可证不明意味着检测规则无法安全内嵌进商业产品。
4. **研究原型的架构主张与实测证据之间有落差。** flare 有 30+ 份设计文档，但 README 首页没有任何 benchmark。**「我们把内存与状态显式化」是一句主张，不是一个测量结果**；在本日报采信的所有材料中，guard 的 7 组实测表是唯一带具体输入与输出数值的一组。
5. **非官方 fork 的路线债是结构性的。** harp 明写「does not produce usable updates」——这意味着上游 Warp 的每次改动都不会自动到达，用户要么自己解冲突要么放弃某部分功能。2 天 4 个 release 表明当前跟随强度尚可，但**这不是一个能长期成立的模型**，README 自己也知道。
6. **Android TV 桌面赛道已连续第 5 天有新项目，但今日仍不重复建档。** `lesnolie/Tigris`（222⭐，声称已在索尼 BRAVIA XR-55A80J 验证）、`op7418/guizang-tv`（137⭐）、`Jimu888/home-tv-cn`（41⭐，**README 明写「基于 Aerial 定制」**）——赛道真实存在竞争，但也开始出现直接派生。**赛道已验证不等于每个项目都有价值**；差异化正在从「UI 像不像 tvOS」转向「在什么机型上能活下来」。

## 今日重点趋势（按排名）

### 趋势 1：vercel-labs/fx0 严肃工程化 durable design agent 公开参考实现（趋势分 90）

`vercel-labs/fx0` 2 天 296⭐ ⑂55 fork（fork-star 18.6%，本批最高）把「durable agent」从「各家 SDK 文档里的抽象名词」推到「**一个 `createFxAgent()` 调用即获得 agent loop / streaming / tool calls / retries / durable sessions**」的**可读参考实现**。README 明示的分层是本日最值得记的架构信息：

- **fx0 拥有**用户可见的一切：chat 与实时预览、登录、agent 调用的设计工具、Redis 与 Neon 里的 chat 历史。
- **libfx 拥有**每一个 turn 内的全部工作：模型循环、tool calls、retries、steering。fx0 用 `createFxAgent()` 建一个 agent，把每个 chat 的 messages 交给它。
- **Workflow World**（Vercel Workflow 背后的存储）是 libfx 保存每个 turn 运行过程的地方：先存 prompt，再存每一步。
- **Vercel Queues** 给每个 prompt 留一份备份：函数崩溃或触到时限时，队列在 `/api/libfx` 唤醒一个新函数，libfx 从最后保存的步骤继续。
- **AI Gateway** 收每一次模型调用：付费轮用发送者的 OAuth token 与 team，显式赞助的试用轮用服务器自己的 trial key。

两个「成本控制」细节在 agent 工程里非常少见被写明：其一，**turn 在队列投递时没有浏览器 cookie**，所以 prompt 路由把 funding 封进 Redis——每条消息记录它所启动的那一轮的 funding 归属（要么是被准入的赞助，要么是付费发送者的 OAuth grant 与 team），这防止了「agent 在后台跑完、账单挂错人」；其二，**一轮最多 64 个 model steps（含 subagent）**，README 直言这是为了让陷入循环的 agent 跑不出一张天价账单。

### 趋势 3：pengchujin/aerial-tv 严肃工程化国产 Android TV 桌面（趋势分 87）

## 最值得关注的方向

今天四个项目**不在同一条赛道上**，但共享一个更值得记的模式：**把一件已被大厂产品垄断或被忽视的日常能力，用可核验的方式重新做一遍，并把边界摊开写出来**。

- **fx0** 把 durable agent 从抽象名词变成一行 `createFxAgent()`，而且是**由做这套基础设施的公司自己公开参考实现**——这比第三方教程更可信。真正稀缺的不是 agent loop，而是那两条 README 亲口写下的工程约束：**每轮 funding 必须在 Redis 里封存**（因为队列投递没有浏览器 cookie）和**每轮 64 步上限**（因为 agent 会死循环烧钱）。这两条几乎必然出现在任何自建 agent 生产系统里，但很少有项目把它们写进 README 首页。
- **opentrap** 的价值不在技术（它明说检测靠 ZAP），而在**交互层**：它选的是「让 proxy-first 的用户不用重新学 ZAP」。这是把成熟引擎重新包装成主流工作流的标准路径，风险在 fork-star 1.1% 与 releases 为空。
- **aerial-tv** 是今日唯一一个**在真实异构硬件上被六款真机验证过**的项目，它的五层接管模型（HOME → 无障碍守护 → 通知监听复活 → 开机自启 → ADB 常开）本质上是一份「如何在敌意固件上求生」的操作手册，可迁移到任何国产电视盒子、机顶盒、车机。
- **ElyOffice** 最有价值的动作是**在 pinned commit 上重建上游并同时发布上游源码归档**——这是许可证合规的硬动作，比「我们支持 ODF 格式」这类口号具体得多。

**跨项目的共同观察**：四个项目中有三个（opentrap、aerial-tv、ElyOffice）**都在 README 里明确写了自己的失败边界**——「Linux/Windows 未跑过」「TCL 拒绝 ADB 只能走多屏互动」「需要联网、HDMI 名读不到」。这种「先说边界」的表达在 2 天内的新项目里并不常见，**但它与热度无关，是独立于 star 数的质量信号**。反过来，热度信号本身今天给出的提示是相反的：**fork-star 普遍偏低（1.1%–6.9%）**，说明这批热度更多来自曝光而非动手采用，需要 7 天数据再判断。

## 重点项目深度分析（top 3）

### Deep Dive 1：vercel-labs/fx0（一个 `createFxAgent()` 即获得 agent loop + 流式 + tool calls + retries + durable sessions + 每 turn funding 封存 + 64 步上限）

**项目定位。** vercel-labs/fx0 是 Vercel 官方 labs 账号在 2026-10-19 发布的「**开源轻量 design agent**」，2 天 296⭐ ⑂55，TypeScript，Apache-2.0，1066 KB，`subscribers_count = 0`，`open_issues_count = 1`。它的双重身份 README 讲得很清楚：**fx0 是应用，libfx 是跑在里面的 agent**，而且它同时是 libfx 的一个可用工作示例。在线可试 fx0.vercel.dev。

**为什么 fork-star 18.6% 值得单独说。** 本批四项目 fork-star 分别为 18.6% / 1.1% / 6.9% / 6.0%。fx0 是唯一显著高于平均的——对「设计 agent 网页应用」这种通常只是「用一用就走」的东西，18.6% 的 fork 比例指向的是**开发者在读它的架构而不是在收藏它**，与 README 里那张 `docs/diagrams/pieces-*.svg` 分层图和三段 TS 代码块的详尽程度互相印证。

**技术亮点（全部可核验于 README）：**
- **一行调用换四件套**：`One createFxAgent() call gives it the agent loop, streaming, tool calls, retries and durable sessions`
- **五层职责边界写死在 README**：fx0（UI/鉴权/工具/历史）· libfx（每轮内全部工作）· Workflow World（逐步落盘）· Vercel Queues（崩溃唤醒）· AI Gateway（每次模型调用的计费归属）
- **先存后 ack**：`POST /api/prompt` 在**一个 Redis 脚本**里加消息，再交给 libfx；libfx 先存再确认——保证「显示为已发送的消息不会丢失」，且重试请求落到同一轮
- **funding 封存**：队列投递无浏览器 cookie，prompt 路由把 funding 封进 Redis；每条消息记录它启动的那一轮的 funding（被准入的赞助 / 付费发送者的 OAuth grant + team）
- **64 model steps 上限（含 subagent）**：README 直言「keeps an agent stuck in a loop from running up a bill」
- **800 秒 + 队列兜底**：`app/api/libfx` 的 `maxDuration = 800`，`vercel.json` 用 `queue/v2beta` 订阅 libfx 的队列主题，`retryAfterSeconds: 5`
- **steer 语义**：空闲时发消息 = 新一轮；运行中发消息 = 插话（经 Queues 送达正在跑的那轮），试用轮刻意让每条输入各成一轮以隔离免费与付费资金
- **设计版本化**：每轮保留自己的设计版本，可重开、复制、下载 HTML
- **成本闸门**：不登录可试每 IP 五次免费 Opus 5.5 Fast，BotID 防滥用，服务器专用 Gateway key 出资；十个 `design.md` 风格起步（源自 VoltAgent 的 awesome-design-md，可自上传）

**风险。**
- **README 大量用 `elided`（截断）呈现**：`apiKey: 'sessi...ed'` 这类占位符意味着**关键接入代码在公开 README 里并不完整**，读者能理解架构但不能直接复制
- **强绑定 Vercel 生态**：World、Queues、AI Gateway、BotID 四件套全是 Vercel 服务；README 说「on Vercel 用 World + Queues，别处用本地文件」——**非 Vercel 环境下的 durable 语义是降级的**，这对想借鉴架构的团队是重要边界
- **依赖 Opus 5.5 Fast**：默认模型绑在特定模型上，模型涨价或下架会直接抬高/打断成本
- **2 天 0 subscribers**：没有深度关注者，早期信号
- **安全面**：agent 能搜索网页并抓取页面做参考——这是典型的 prompt injection 入口，README 未讨论

**是否值得跟踪。** **值得，且优先级最高。** 理由与热度无关：**它是把 durable agent 的成本与计费归属这两个最容易被忽略的工程约束，写在首页 README 里的公开参考实现**。哪怕 fx0 本身失败，这两条约束也会留在使用者的系统里。

### Deep Dive 2：opentrap/opentrap（Burp 式工作流 + OWASP ZAP 引擎 + 内置 Chromium 开箱 TLS 拦截 + AGPL-3.0）

**项目定位。** opentrap/opentrap 是 `opentrap` 组织在 2026-10-19 发布的「**Burp Suite 的免费开源替代**」，2 天 177⭐ ⑂2，Java，AGPL-3.0，19229 KB，19 个 topics，`open_issues_count = 0`，`subscribers_count = 1`。徽章自标 `status: active development`、`contributions welcome`、Java 17+、Linux。

**技术亮点：**
- **引擎复用而非重造**：检测能力明确依赖内置 OWASP ZAP——README 的定位句是「on top of the trusted OWASP ZAP detection engine」
- **内置 Chromium 开箱 TLS 拦截**：「One click opens Chromium already routed through the proxy and trusting its certificate authority, so TLS interception works with nothing to configure」——这消除了 proxy-first 用户最大的一段配置摩擦
- **五个工作面完整**：Proxy（拦截 + 内置浏览器）· Target（site map 树 + 请求列表 + 每条发现附 advisory 含请求与响应）· Collaborator（OOB DNS/HTTP 全量留档）· Intruder（四种攻击类型 + payload 集与处理，实时表含 status/length/timing）· Dashboard（crawl 完成 + active audit 运行 + 按严重度实时排序）
- **AGPL-3.0 无许可门禁**：README 明说「nothing locked behind a licence」，且主张「built to be improved by the people who use it rather than steered by a single vendor's roadmap」
- **19 个 topics 是明确的 SEO/发现位设计**：含 `burp-alternative`、`burp-suite`、`owasp-zap`、`burp` 三个关键词，直接打「Burp 替代品」搜索意图

**风险。**
- **releases 为空**：GitHub API 返回空数组，README 的 AppImage 下载链接指向 `releases/latest`——**当前大概率下不到**。这是最直接的可采用性阻塞
- **fork-star 1.1%（本批最低）**：177⭐ 只有 2 fork，社区尚未进入动手阶段，与「contributions welcome」的自我定位存在张力
- **仅 Linux 声明**：AppImage 是唯一明确分发物，macOS/Windows 未提
- **AGPL-3.0 的商用摩擦**：企业安全工具常需嵌入既有平台，AGPL 的传染性是现实采用障碍——README 未讨论
- **0 open issues 的解读**：2 天新项目更可能是「还没人提」，不能读作质量背书
- **ZAP 集成的耦合度未知**：是嵌入 JVM 还是外部进程，决定了升级 ZAP 的成本，README 未说

**是否值得跟踪。** **值得，但定位要放在「交互层重构」而非「检测能力突破」**——检测来自 ZAP，价值在于把 proxy-first 用户不需要重新学一遍这一点做到位。**观察重点：releases 何时出现、macOS/Windows 是否跟进、fork 是否从 2 涨起来。**

### Deep Dive 3：pengchujin/aerial-tv（国产电视五层接管 + 六款真机验证矩阵 + 权限明示表 + 一条 curl 还原）

**项目定位。** pengchujin/aerial-tv 是 pengchujin 个人在 2026-10-20 发布的「**给国产电视的一块干净桌面**」，2 天 524⭐ ⑂36（fork-star 6.9%），Kotlin，MIT，3132 KB，Android TV 5.0+，中文主 README + README.en.md，官网 aerial.qust.me，`open_issues_count = 39`（本批最高，说明有真实用户在提交问题），`subscribers_count = 0`。

**技术亮点：**
- **五层接管模型**（README 逐层解释，见趋势 3）
- **无障碍守护的隐私承诺**：桌面守护「只看哪个窗口到了前台，**不读屏幕内容**」
- **通知监听只借绑定不读内容**：明示「不读取任何通知」，借此获得系统约 0.5 秒内的复活重绑

## 风险与机遇

### 机会

1. **「先说边界」正在成为可观察的质量信号，且与热度解耦。** 今日三个项目（ElyOffice 的「Linux/Windows 未跑过」、aerial-tv 的五条已知限制、opentrap 的「nothing locked behind a licence」）都在 README 首页写明失效条件。这类表达值得在评估任何新项目时作为**独立于 star 数的检查项**。
2. **agent 基础设施开始公开「失败模式」而不只是「成功路径」。** fx0 把 funding 归属与 64 步上限写在 README 首页——这类内容目前稀缺。任何打算自建 agent 生产系统的人都应把它当作设计清单读一遍。
3. **「敌意固件求生手册」是可迁移的。** aerial-tv 的五层接管模型不限于电视：机顶盒、车机、智能屏、定制 ROM 手机面对的是同一类问题（厂商只认自家桌面 / 待机杀第三方 / 拦自启动）。
4. **交互层重构仍有空间。** opentrap 证明「成熟引擎 + 熟悉界面」的组合在安全工具里仍有位置，且这层重构成本远低于重造引擎。
5. **中文原创项目在 GitHub 上能拿到全球 star。** aerial-tv 是纯中文 README 起步，2 天 524⭐，且已有多台国产机型（小米 / TCL / 索尼国行）的验证笔记。

### 风险

1. **本批热度信号整体偏弱，且方向明确。** 4 个项目 fork-star 中位在 6.5%，opentrap 仅 1.1%，ElyOffice 仅 6.0%，且三个项目 `subscribers_count` ≤ 2。**这批 star 更接近「曝光量」而非「采用量」**——这是可核验的元事实，但它意味着：**今天不该基于这批热度做技术选型决策。**
2. **durable agent 基础设施对单一云厂商的耦合。** fx0 的 World + Queues + AI Gateway + BotID 全在 Vercel，非 Vercel 环境是降级路径。若 Vercel 调整定价或模型供应，参考实现的经济模型会变。
3. **AGPL 与桌面单平台的组合限制采用面。** opentrap 的 AGPL-3.0 在企业安全工具链里是现实摩擦，加上仅 Linux AppImage，实际可部署面比 star 数暗示的窄。
4. **高危权限组合缺少外部审计。** aerial-tv 的无障碍 + 通知监听 + `WRITE_SECURE_SETTINGS` 三件套虽有「不读」承诺，但用户无法独立验证承诺是否被遵守；这类项目一旦出现滥用，影响面是全设备。
5. **上游自建带来的维护债。** ElyOffice 在 pinned commit 上自行构建 LibreOffice 与 MuPDF，代价是每次上游安全更新都要人工跟进（README 未说明更新策略），且新用户需承受约一小时的 LibreOffice 构建。
6. **「2 天内爆发」的重复造轮子风险。** Android TV 桌面赛道今日已有第 5 个项目（tv-vibehack / free-my-tv / tv-detox / tv-home / dumbtv / aerial-tv），其中 free-my-tv 今日已到 1678⭐ ⑂172。赛道已验证，但**同质化严重**，差异化正在从「能不能装」转向「在什么机型上能活下来」——aerial-tv 的六机型矩阵正是这个转向的第一个样本。
